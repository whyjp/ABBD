# ABBD setup

**Reader.** Setup reads code with the abbd skill's reader, `../abbd/references/reader.md`. Follow it for every reading step below. It needs only the abbd CLI, and it says when pstack may serve as an optional engine.

Setup asks the human one thing only, how dense the overview should be (step 8), and only when a human is in the conversation. The first state you commit is the baseline; the human reads it in the blueprint and the PR, and there is no alignment step.

## Steps

1. List unit candidates from the layout, entry points, manifests and schemas. A unit is something a human would say "this change must not touch that" about: a responsibility (`MOD`), an external contract (`IF`, `EVT`, `DATA`, `CFG`), a user-facing feature (`FEAT`). Imports, calls and file placement are material for finding units, never units.

   Then choose the levels the blueprint draws, before any script:
   - The overview draws the parts a reader reasons about when explaining the system: 4 to 12 top-level modules, and the external systems it talks to as contracts. Folders a framework imposes, such as `app/`, `components/`, `lib/` or `src/`, are not parts. The modules under them are. One root package that holds most of the system is several parts, its responsibilities. Where no code rule splits it, the script reports its files or types as they are, and the supplement groups them into those parts (step 4).
   - What most parts use, such as shared types, a UI kit, providers or small helpers, is one shared module, the layer the others stand on. Its incoming lines do not count toward the density. A helper only one part uses sits inside that part.
   - Group until each level reads. Modules that serve one responsibility and change together are one part, along a grouping the project shows: a package, a directory, a family of implementers, a section of its docs. Grouping to bring a level within these bounds is required. Grouping modules that share no responsibility, only to hide their lines, is not allowed.
   - Each module's page draws 2 to 16 parts, the bounds `abbd lint` holds every page to: its responsibilities, its subpackages, or one family of implementers of an interface it holds, such as every output format. A part is several files that change together, never one file per box. A module too small for two parts gets no page of its own. A top-level one is a leaf of the overview with no units inside. A nested one folds its files into the module around it.
   - Keep the lines few, about 2 a box at most, past the lines into the shared module. More means the parts are cut too fine, or a shared module is drawn as a peer.
   - Name each unit by its role, such as `radix router` or `cart`, taken from the code that defines it (a package comment, the main type, the route), never by its path.
   - The script decides the units and their names (step 3), and a parent it gives outranks the supplement's, so choose the levels in the script where the code shows them. The supplement cannot rename a unit the script reports, and cannot move one the script places in a module. It can place a unit the script leaves on the overview inside a module, with `parent_evidence` (step 4).
2. Read the candidates in slices, per the reader's "At setup" section: at most five workers, each run locally without worktree isolation so it sees uncommitted code, each reporting in the extraction format below. Every unit the layout does not show comes with verbatim `evidence`, and every coupling it reads, whether the layout shows it or not, comes with `via`, a `phrase` that says what crosses it, and verbatim `evidence`, and a unit inside a module names that module as `parent`. Skip the slices only for a repository of fewer than 10,000 lines of non-test code, however many candidate modules it has: read it yourself in one pass, with the same evidence rules, and say in the reply that you did. Merge the slices by `ref`: keep one entry where two slices describe one unit, with the evidence of both, and where two slices gave one `ref` to different units, rename each with its module's ref as a prefix (`db:env`, `table:env`), so every ref is unique before step 4.
3. Build the lever, per the reader's "At setup" section. 3a, 3b, 3b2 and 3b3 serve a repository a bundled front-end reads, 3c and 3d one it does not read, 3d2 any repository with Go code, and 3e to 3g every script.

   **3a. Cargo or CMake: run a bundled front-end.** Start from the bundled front-end when the repository builds with a system abbd reads. `abbd extract cargo` reads a Cargo workspace and `abbd extract cmake=<DIR>` the CMake project whose top `CMakeLists.txt` sits in `<DIR>`, such as `cmake=build/cmake`. Name both, as `abbd extract cargo cmake=native`, for a repository with both. Each prints the extraction JSON from the build system's own model: a module per crate or per set of targets that compile the same sources, the `artifacts` each builds, and its dependencies on the others with `via` `import`, `macro`, `build-feature` or `link`. A static and a shared build of one library are one `MOD` with both artifacts. A plain Rust library or proc-macro crate is a module with no artifact. A target is left out when a word of its name is `test`, `bench` or `example` (`c_test`, `db_bench`), or when it is defined in a directory named so or named `third_party`, `vendor` or `external`. A module's anchors are the directories of the sources it compiles and of the headers it lists. CMake configures in `$ABBD_CACHE_DIR`, outside the repository. Pass CMake cache options after the front-ends, as `abbd extract cmake=. -DNAME=VALUE`, to turn off what the configure cannot do here, such as the option that builds tests and so wants googletest's git submodule, and register them in the command: `abbd setup -- abbd extract cmake=. -DNAME=OFF`. A configure that fails says so and lists the option( names of the project's CMake files, build and test ones first (`cmake -LH` lists them all); check submodules out with `git submodule update --init` only where no option turns the part off. A library of one target is one module, however many responsibilities it holds, so split it as step 1 says in the wrapper of 3b: replace a module whose anchors are several source directories with one `MOD` for each directory, anchored by the directory and one file of it, and move each of its links to the directories whose files `#include` the other side's headers, read from those lines.  The CMake front-end needs CMake 4.2 or later, the first release whose file API records which targets a target links directly apart from those `add_dependencies` only builds first. It refuses an older CMake and names the version it found. Get 4.2 or later from the official release at https://cmake.org/download/, `pip install cmake`, the Kitware apt repository on Debian or Ubuntu, `brew install cmake` on macOS or `winget install Kitware.CMake` on Windows, and put it first on the `PATH`. Where only an older CMake is at hand, describe the modules in the supplement instead. Never re-derive crates, targets or linkage by hand.

   **3b. Register the front-end, or wrap it.** When those modules are all the topology needs, register the front-end itself, as `abbd setup -- abbd extract cmake=<DIR>`; a Cargo workspace registers it wrapped in the Rust relater instead (3b2), and a CMake project with C or C++ code wrapped in the C relater (3b3). Otherwise write `.abbd/extractor/extract.<ext>` to run the front-end, keep its units and relations, and add only what the build model cannot show: contracts, routes, configuration and source-level couplings. Setup and sync pass the path of the abbd that runs the script in `$ABBD_BIN`, so the script runs `"$ABBD_BIN" extract cargo`, never an `abbd` it finds on the `PATH`, which can be another version that reads the build differently. Where no toolchain can configure the project, give the artifacts in the supplement instead, with the line that declares each target as evidence.

   **3b2. A Cargo workspace: wrap the front-end in the Rust relater.** For a Cargo workspace, wrap the front-end in `abbd relate rust`, as `abbd setup -- abbd relate rust -- abbd extract cargo` (`rust=<DIR>` for a workspace whose `Cargo.toml` sits in `<DIR>`). It runs rust-analyzer, from `$ABBD_LSP_RUST` or the `PATH`, once with default features and once with all features, for `x86_64-unknown-linux-gnu` on every host. Tests, benches, examples, build scripts and proc macros are left out. A relation found under only one feature set carries it as `when`. Its relations are the Go relater's, plus `macro` for a macro invoked with `!` or a proc macro named in an attribute. A facade crate, such as one that only re-exports others with `pub use` or `pub extern crate`, gets an `import` from each unit that names it and an `import` to each crate it re-exports. The command names on stderr the files no feature set compiles, such as a `cfg(windows)` module. A unit holding such a file keeps the script's `depends_on` the relater found no sign of. Where rust-analyzer is missing, the command says how to get it: `rustup component add rust-analyzer`, the release binary from https://github.com/rust-lang/rust-analyzer/releases, or `brew install rust-analyzer` on macOS.

   **3b3. A CMake project: wrap the front-end in the C relater.** For C and C++ code, wrap the front-end in `abbd relate c`, as `abbd setup -- abbd relate c -- abbd extract cmake=<DIR>`, with `c=<DIR>` naming the same directory and the same `-D<NAME>=VALUE` cache options after it as after the front-end, so both use one build tree. It reads each source's compile command from the CMake file API in that tree, so every generator works. For a build CMake does not run, such as Make with Bear or Meson, name the directory that holds its `compile_commands.json` instead, as `c=build`, and that file is read as it is. It runs clangd, from `$ABBD_LSP_C` or the `PATH`, and keeps clangd's index in `$ABBD_CACHE_DIR`, never in the repository. A function belongs to the unit that defines it, wherever a header declares it. Its relations are the Go relater's, plus `callback` where the code takes another unit's function as a value, `macro` for a function-like macro, and `trait` for a C++ base class. A name tested only by `#if` or `#ifdef` is no use. A struct of function pointers or a function-pointer alias with a brace initializer is a table. Under the plug-point rule in 3g, the units whose functions fill it `provides` a contract unit anchored at the type, and the units that call through a member of it `consumes` it. Without such a contract unit, each calling unit `depends_on` each filling unit via `callback`, since the host's code runs the filler's. The command names on stderr the sources the compile database does not compile, and each file's lines its configuration leaves out by `#if`. It reads the one configuration the database holds, so a relation that only another platform's build compiles is missing. Where clangd is missing, the command says how to get it: the release from https://github.com/clangd/clangd/releases, `apt install clangd` on Debian or Ubuntu, `brew install llvm` on macOS, or `winget install LLVM.LLVM` on Windows.

   **3c. No supported manifest: write `extract.<ext>`.** Without a supported manifest, write `.abbd/extractor/extract.<ext>`, a script that prints the extraction JSON from the code alone: imports, routes, schemas, manifests, and each contract's `signature` and `digest`. It runs from the repository root, sorts its output, and uses no clock, network or model. Pick anchors mechanically and stably: every non-test file of a package plus its directory, or a file plus the symbol that defines a contract. Find modules and contracts from the code, never from a list the script keeps by hand. Walk the tree for manifests such as `go.mod`, `package.json`, `Cargo.toml` or `pyproject.toml`, and find routes, commands and environment reads by the calls that register or read them, so a module or contract added later is a unit at the next sync. Setup and sync name each manifest that no unit anchors code under as `uncovered:`. Have it fail when a unit has fewer than two anchors or an anchor names a symbol its file does not declare.

   **3d. A flat tree: group files into modules from code evidence.** A tree with no package boundaries, such as a flat directory of C files, still has modules. The script groups files from what the code shows, by a rule it applies to every file: the include or import graph (files that include one header and few others), a shared file-name prefix, a header that declares a part's API, or a directory. A table of files the script keeps is a hand list unless each row names the code that shows the grouping, such as the header that includes those files, and a hand list is not allowed. Where only reading shows which files belong together, give the module in the supplement as a grouping, with `evidence` quoting that code, its members' code included (step 4). A file added later then joins its module at the next sync.

   **3d2. Go code, with any script: wrap it in the Go relater.** For Go code, wrap whatever prints the units in the bundled relater, as `abbd setup -- abbd relate go -- go run .abbd/extractor/extract.go` (`go=<DIR>` for a module whose `go.mod` sits in `<DIR>`). It reads the module with go/types, resolves calls through interfaces and func values with VTA, leaves tests out and reads one fixed configuration, GOOS=linux, so every host prints the same bytes. That drops the files only another platform or cgo builds, and the command counts them on stderr. It replaces the `depends_on` between units whose Go code it read with what the code does: `call`, `trait` where a type implements another unit's interface, or `import` where the code uses a type or constant and never calls, each with up to three quoted lines. A blank import, such as a plugin bundle, is an `import`. It never makes a unit, and adds a `provides` or `consumes` only for an interface a contract unit anchors by its symbol, where the script has none. So the script need not guess Go `depends_on` at all.

   **3e. Configuration contracts.** Read configuration, such as the environment variables a `CFG` contract lists, only from the code that runs in production. Skip test, end-to-end and tooling config by its file, such as `playwright.config.ts`, a `jest` or `vitest` config or a CI workflow, the same way anchors skip test files. Never drop a variable by its name. `NODE_ENV` or `CI` can gate runtime behaviour, such as whether a login is refused or a cookie is `secure`, and then it is part of the contract.

   **3f. Conditions.** The bundled front-ends print no `when`, so a script that runs one adds it, or the supplement gives it. Give a relation that holds only under a condition its `when`, as the build says it. For Cargo: `cargo metadata` does not name the feature that enables an `optional` dependency, so read it from the package's `features` map, each feature that lists `dep:<name>`, or the implicit feature of the dependency's own name when no feature lists `dep:<name>` (`feature = "sinks-kafka"`), and join several (`feature = "a" | feature = "b"`). A dependency under `[target.'cfg(...)']` takes its cfg, and a dev or build dependency takes `dev` or `build`. For CMake, the file API reports only the configured result, not which `if()` or `option()` branch ran or the generator expression, so read those conditions from the CMakeLists text, or give them in the supplement: list the edge the script prints, with the condition as its `when` and the `if` line as evidence. The script's line then shows that condition, and it stays through every sync. Setup and each sync report a supplement condition that differs from one the script prints as a `conflict:`, and so is a supplement scope that differs from the script's. There the script's scope shows, and the supplement's stays stored until the supplement drops it. A CMake link's `PRIVATE`, `PUBLIC` or `INTERFACE` goes in `when` when the link has no condition, and the page shows it as the link's scope. A link with both a scope and a condition keeps the condition and drops the scope, because a scope is not a condition and `PRIVATE | WIN32` would read as either one. A condition from the supplement shows over a scope the script prints. Print each edge once: join the conditions of an edge listed more than once (`cfg(unix) | cfg(windows)`), and give no `when` when any listing has none. Parse refuses an edge given twice with different conditions.

   **3g. Check the script, give each relation a `via`, orient plug points.** Diff its output against the slices' result until every difference is explained. Give every relation the script prints a `via` wherever the code says how it arises: `call` for a package or command the code calls, `data` for a file or table it reads or writes, `config`, `callback`, and `import`, `trait`, `macro`, `build-feature`, `link` or `convention` for a coupling that exists only in design or at build time. The drawing dots a line whose relations arise only in design and draws the rest solid, so a relation with no `via` reads as run-time. `abbd status` counts those in its `via:` line. For a plug-point contract, a callback table, a trait or a weak symbol the host calls through, the modules that implement it or register an implementation `provides` it, and the host that calls through it `consumes` it. Registering an implementation is providing, not consuming, and `abbd lint` names a callback table or trait that looks reversed on a `direction:` line.
4. Write `.abbd/extractor/supplement.json` with what only reading tells:
   - `purpose` and `responsibility` for script units, repeating `ref`, `kind`, `name` and one anchor of the unit they describe, with no `evidence`. The anchor is one the script prints for that unit, not any file of it. When that anchor is also held by the unit's module, such as the directory of an inside module, the innermost unit is matched. Give a module an anchor only it holds, such as its entry symbol, never the first file of a part inside it: a module and its part that share the anchor describe the same code, and setup refuses both
   - units the script cannot see, such as a shared table or a wire format, with `evidence` instead of anchors and their module as `parent`, by the supplement's ref or the script's; the module need not be restated. A quote may sit on an anchor of that parent or of a module around it, as long as the parent holds some anchor the unit does not. A quote on an anchor of any other script unit of the same kind makes setup refuse the unit and name both. A contract the script reports no `signature` for keeps the one the supplement gives, as INFERRED. Parent a contract to its module, and to a part of it only when that part has two or more things inside: a contract inside a part makes the part a page of its own, and `abbd lint` names a page of one box in a `level` line
   - couplings the script cannot see, such as a shared table, an execution order, a trait used through generics, a callback, a plugin loaded by name, a helper process started, a component registered with a registry, a flag passed through config, a build feature or a convention two units keep in step, each with `via`, `phrase` and `evidence`. A plug point goes as step 3g says: its implementers provide it and the host that calls through it consumes it. Every supplement coupling cites `evidence`, a `provides` one included. Name each end by the supplement's ref or the script's. An end the script reports needs no entry of its own in the supplement
   - a `phrase` for the couplings the script reads, starting with those between top-level modules, which the overview draws. Every overview line takes at least one, since a line without one says nothing at rest: its plain 호출 or 임포트 shows only in the tooltip. Once the overview record (step 7) chooses lines, only those take one. A line is the pair of boxes its relations join, and a relation to a contract counts on the line to the module that provides it. `abbd lint` names each unphrased line with its relations, so phrase one of those edges. Repeat the edge with `via`, `phrase` and `evidence`. The script's claim still holds the edge, and the phrase only labels its line. A phrase takes at most 24 characters and reads in the project's `language` (step 6): an identifier may stand in it, but a bare identifier such as `Matcher` fails `abbd lint`'s prose check, so add a word of the language that says what crosses
   - a grouping the project shows that the script cannot see: a subsystem its docs name, a skill family, or an abstraction the code shows (a layer, a family of implementers of one interface). Add it as a `MOD` whose `evidence` quotes the project naming or showing it (the README section, manifest, entry point or code), and give each member that part as `parent` with `parent_evidence` quoting the project placing it there. Its quotes may sit on its members' files, since no other code holds a grouping of them: restate each member with its `ref`, `kind`, `name`, one anchor and the grouping's ref as `parent`, and setup keeps the grouping a module of its own around them. A grouping holds two or more members: setup refuses one that fewer than two script units name as their parent, since it would only rename its member, and counts a member only by its first restatement, because a later restatement of the same unit is dropped. A quote on a file of a script unit that does not name the grouping as its parent is refused. Add one when step 1's bounds need it, never for members that share no responsibility. Sync's fallback places a crowded level's units in the directories their code lives in, and never moves a unit a reader placed
   The file is `{"units": [...], "relations": [...]}` in the extraction format below, and its units never list `entries`, which the script reports and setup refuses in a supplement:

   ```json
   {"units": [
     {"ref": "cmake:db", "kind": "MOD", "name": "db", "anchors": [{"path": "db"}],
      "purpose": "…", "responsibility": "…"},
     {"ref": "wal", "kind": "DATA", "name": "write-ahead log", "parent": "cmake:db",
      "evidence": [{"path": "db/log.cc", "lines": "12", "quote": "…"}]}],
    "relations": [
     {"from": "cmake:db", "to": "cmake:table", "kind": "depends_on", "via": "call", "phrase": "…",
      "evidence": [{"path": "db/db.cc", "lines": "3", "quote": "…"}]}]}
   ```

5. Before the first setup, write the project's `language`, `name` and `purpose` into `.abbd/project.yaml`, as step 6 says, so the first blueprint is titled and written in that language. Setup keeps them. Then run setup:

   ```
   abbd setup --supplement .abbd/extractor/supplement.json -- <interpreter> .abbd/extractor/extract.<ext>
   ```

   - `not deterministic`: the script printed different output across three runs, one with a different `PYTHONHASHSEED` and `PERL_HASH_SEED`. Sort what it prints and remove the variation.
   - `fix the script, or cite the code`: a supplement unit matches no script unit and cites no evidence. Teach the script the unit, add `evidence`, or drop it.
   - `would merge into it`: a supplement unit with evidence shares an anchor with a script unit that is not its parent. Name that unit as `parent` if the unit sits inside it, restate that unit with this one as its `parent` if this one groups it, quote code of its own, or drop the evidence if it describes that script unit.
   - `cites no evidence`: a supplement coupling has no quote. Add one or drop it.
   - `describes the same code as another supplement unit` or `shadows the script's ref`: two units share the anchor that names them, often a module and its first part. Give the module an anchor only it holds, as step 4 says.
   - `is not a relation ABBD knows`: a module or feature `provides` a contract, anything `consumes` a contract, anything `depends_on` any unit, a module, feature or `EXEC` `runs_on` an `EXEC`, and a module or `EXEC` `posts_to` an `EXEC`.

   A rerun finds a script unit again by its anchors, while it shares two of them, or all of them, with the stored unit, and a supplement unit by its `ref`. Replace a script unit's anchors past that and sync takes it for a new unit under a new ID, and lists the old ID as `unmatched` from then on, so keep two anchors through each change. `abbd forget <ID>` removes an unmatched unit once nothing else in the state names it.

   Once setup passes, run `abbd lint`. The `level` lines at the end of its report name each view drawn at the wrong level, too coarse, too fine or too dense, and say what to change in the units. Change the script or the supplement as it says and rerun setup, until no `level` line is left or you can say in the reply why one stays. Step 9 records that reason. Fix the levels before anything else: the hard breaches of a dense view come from its units, and most go once its level reads.
6. The project's `language` in `.abbd/project.yaml` is a BCP-47 tag, such as `ko`, the language the human writes to you in the conversation. Ask once only when the conversation shows none, as when it holds only commands; with no human in the conversation, leave it out and abbd takes the OS's locale. Every text below is written in it, as `abbd brief <MOD-ID>` says. The project's `name` and a one-paragraph `purpose` there open the overview with what the project is for. Then, for each top-level module, read it per the reader and store its Overview and Key Concepts with `abbd understand <MOD-ID> <FILE> --reader "<WHO>"`. A directory group that sync made counts as a top-level module, because the overview draws it like any other. Any module takes a text, so do the same for a module inside another when the project's own docs describe it on its own, or when its page is dense enough to list focus views, since a reader of a tangle leans on the text most. Write the texts in the order a reader meets the pages. The top-level modules come first, then the modules one level below them that take a text, then the deeper ones. A page without its text has no account of what the module does. Its text describes its own subtree, and its parent's text still describes all of it. Write the text as the code is now, in the present tense. Leave out dates, issue and PR numbers, and tags such as "migrated from X", because git keeps the history. Keep each section under 2,000 characters of prose, and split a longer one under `###` headings or into shorter sections. `abbd understand <MOD-ID> <FILE>` and `abbd status` report each section over that length and each phrase that reads as history. Neither fails the check, because a version number or a name can read as history too. `abbd understand <MOD-ID> <FILE>` refuses only a text whose first section, the summary a page shows before it folds the rest, runs over 2,000 characters. While the reader is in a top-level module, store at least one `decisions` note for it with `abbd understand <MOD-ID>.decisions.<KEY> <FILE> --evidence PATH:LINES:QUOTE`, saying what the code chose over what, so its page carries the reason a reviewer weighs a change against. Open the text with a short summary of the module, under 2,000 characters, because the page shows the first section and folds the rest, and `abbd understand <MOD-ID> <FILE>` refuses a longer one. Name each Key Concept after the file it lives in or the unit's ID in backticks, such as `route.go` or `MOD-0042`, so the page sets the concept beside that unit's box. Store what the reader calls Gotchas as `failure` or `semantics` notes with evidence, and How It Works as a flow with `abbd flow <KEY> <FILE>`, not in the text.
7. Write the overview record: the summary a person reads first, as they would sketch the system by hand. It is a primary flow in numbered stages, a few named zones, and the lines a person needs to understand the structure, each with a word. The blueprint is not meant to draw all the code. A line redundant for understanding stays off the overview, and its relations stay one level down, on the stage, focus and inside views. A line a person needs that the overview lacks is a defect. Run `abbd overview` for a draft and save its whole output as the FILE: it opens and closes its frontmatter with `---` lines and stores unchanged, so write the parts into it and keep both lines. It lists the boxes the overview draws with the stage each stands at, the stages, zone candidates from the stacks' layers and the folders, and every pair of boxes a stored relation joins, strongest first, each with its relations and a quote to cite: a relation's own, or else a line of the from box that names what it runs to, which you read before you keep. A zone names boxes from that list. A line's end may also be a unit inside a box, and the line is drawn from that box. Choose from the draft, read the code each choice rests on per the reader, and write the parts below in the project's `language`. A line's word says what crosses or what the caller does with the other box, a verb or noun phrase in the project's language: an identifier may appear inside it, but a bare identifier is not the word. The primary flow runs from where input enters the system to where output leaves, so name both ends' stages, and holds per-run stages only. Wiring done at set-up (registration, construction, CLI and test tooling) stays off the overview's lines unless understanding needs it, and then its word says it happens at set-up.
   - **The primary flow.** Choose the execution or data path a person would narrate to explain what the system does, such as one command's run from parsing to writing its output, or a request from its route to the store. Take 2 to 8 stages in the order the code runs them, each with a short name, a one-line role and the units that run it. Cite two lines for each stage: the line of the entry point, config or pipeline code that puts the stage in its place, such as the call in sequence or a dispatch table's entry, and a line in the code of the stage's own units. abbd refuses a layer none of whose quotes lies in the code of the stage's units and checks no more, so the entry point's line, which lies in the entry point's code, is the claim you read and stand behind, and the other quote is what the check rests on. One quote may serve two neighbouring stages, as the call that ends one stage and enters the next. Add `symbol:`, the function that holds the quote, only when several units anchor its file, so abbd can tell whose code it is. Name each stage's units from the draft's boxes. A box that holds units of several stages stands at the first stage that names it or a unit inside it, so a path through units of one box draws as that one box: name an inner unit only where a box serves a later stage too, and leave a path inside one box to that module's own stack or flow. Leave off the flow the units no stage runs; the overview places them by their lines. A system that starts, wires itself and then moves data narrates the data's path, with start-up stages first only where the hand-offs between them are what a reader must know, such as configuration read, then the pipeline built. A library whose path is one call into one box takes the 2 stages it has; never split a box to lengthen the flow. Store it as a stack with `primary: true` under the question, with `abbd stack <KEY> <FILE>`, as the abbd skill's step 8 says. A repository with no path anyone would narrate, such as a library of peers, stores none; say so in the reply.
   - **Zones.** Name a zone only where the repository shows one: a stack's layer, a directory, a family of parts its docs name. The draft's zone candidates are leads, and a zone the repository does not show is dropped. Cite a line in the code of the zone's units that shows they belong together, such as a package comment, a module header or the build target that groups them, since abbd refuses a zone none of whose quotes lies there; a docs heading may stand beside it. Name the boxes it holds, each in one zone at most, up to 8 zones. Leave zones out where the code shows none.
   - **Lines.** Choose as many lines as understanding needs, up to 20; fewer is fine. Prefer a candidate whose relations run (`posts_to`, `call`, `data`, a trait or a callback) over one that only wires (`config`, `convention`, `load`, `spawn`), and that over one that only imports. Leave off a line that says nothing another line or the flow's order does not, such as the use of the shared module most boxes import. Keep every line a person needs to follow the flow or the data: the hand-off from one stage to the next, the store the stages write and read, the call out to an outside system. When a line you need has no candidate, no relation under it is stored: read the code where it crosses, record it with `abbd record relation <FROM> <KIND> <TO> --via <VIA> --phrase "<PHRASE>" --evidence <PATH:LINES:QUOTE>`, run `abbd overview` again, and choose it.
   - **Words.** Give each line a word that names what crosses it, and take the word from a line of code you quote as the line's `evidence`: the candidate's quote, or the line where the thing crosses, such as the call, the file write or the type handed over. Say what crosses in the project's `language`, translating the meaning of the quoted code rather than copying it. A proper name or an identifier, such as a protocol, a product or an environment variable, may stand in the word, but a bare identifier is no word. Name the thing itself, never the via in other words. Write no quantifier (each, every, all, only, first, a plural that means all) and no negative (no, never, does not) unless the quoted line or a search you made shows it; a quote shows one case, so name that case. A zone's name follows the same rule. Both take at most 4 words and 24 characters.
   - Store it with `abbd overview <FILE>`, which refuses a part the state does not bear out and says why. From then on `abbd lint` asks a phrase only of the lines you chose (step 8). Then run `abbd sync` and read the overview in the next step.
8. Look at the drawings. Serve `.abbd/blueprint` over a local HTTP server on a free port, such as `python -u -m http.server 0 --directory .abbd/blueprint`, which prints the port it took (`-u` prints it even when the output goes to a file), since some browsers and harnesses refuse a `file://` page. Open `index.html` from it in a browser 1600px wide, check that the page's title names this project, since another server may already hold a port, then take a screenshot of the overview and of the densest module page, and read the images. Revise the units and rerun setup when a view reads badly: a box an engineer of the project would not name, a tangle whose lines you cannot follow end to end, a page that repeats its module, a line between top-level modules with no phrase. Check too that each page reads the way the readers described the code, and that no page one click from the overview still says its description is missing. Read the primary flow left to right and each chosen line without hovering. Only while the page does not draw your zones or your lines' words, read them in `.abbd/blueprint/graph.json`, under `zones` and `lines`, and check each word against its quote. When a line you need is missing or a word misleads, go back to step 7. Then read the `described:` line of `abbd status`, which `abbd lint` repeats. Each unit and contract it names is a box that says only its kind, so give it a responsibility in the supplement and rerun setup. A module or feature with a text takes its line with `abbd understand <ID> <FILE> --sentence TEXT`. Only for one the human stated, record it with `abbd record fact ID.responsibility --value TEXT --source REF`. `abbd brief <MOD-ID>` drafts one for each such box of a module from the Go doc comment of its anchored symbol, or else from its file's header comment, and drafts none where neither says anything. The draft is a lead for the reader, not a finding: keep it when the code bears it out, rewrite it when it does not, and write only what you read. Setup is not done while the line names any unit.
   Then read the overview's density: `abbd lint --json` gives it as `totals.density` of the view named `overview`, the lines it draws per box in tenths. When it is over 17 and `.abbd/project.yaml` has no `overview_cut` line, ask the human whether the overview should draw only its main lines and show the rest as a `+N` on each box that opens the box's own view. Write the answer as `overview_cut: true` or `overview_cut: false` in `.abbd/project.yaml` and rerun `abbd sync`. This is how the human likes the overview drawn, not a check of the blueprint, so a stored answer is never asked again. With no human in the conversation, as in a headless or swarm run, leave the line out and say in the reply how dense the overview is and that `overview_cut: true` draws only its main lines.
   Then read `lint: phrases:` in `abbd lint`. It names each line the overview record chose, or each overview line while the record chooses none, by the boxes at its ends, whose relations carry no live phrase, and lists those relations. A line shows a phrase once half its relations carry it. Give one of the relations it lists a phrase in the supplement, or with `abbd record relation <FROM> <KIND> <TO> --via <VIA> --phrase "<PHRASE>" --evidence <PATH:LINES:QUOTE>` for one you read, until it names none.
9. Run `abbd lint --record` to record the hard breaches that remain as the repository's routing debt, and name each in the reply. The first record refuses while a view with hard breaches has a `level` line. Go back to step 5 for it, or, for a level step 5 lets stay, rerun as `abbd lint --record --keep-level <VIEW>=<REASON>`, once per such view, which writes the reason into `.abbd/lint-debt.yaml`. A `level` line is never debt.
10. Run `abbd install`. It writes a short block between `<!-- abbd:begin -->` and `<!-- abbd:end -->` into `CLAUDE.md` at the project root, so any assistant asks `abbd explain <QUERY>`, `abbd path <A> <B>` and `abbd impact <QUERIES>` before it greps, and runs `abbd sync` and puts `abbd diff` in the PR after it changes code. A rerun replaces the block and keeps the rest of the file.
11. Add `.abbd/state.yaml merge=union` to `.gitattributes`, so a merge of two synced branches does not stop on the state. The abbd skill says how to resolve it.
12. Run `abbd sync` once more, since the `.gitattributes` edit changed the working tree the state's fingerprint covers, commit `.abbd/`, `.gitattributes` and `CLAUDE.md` with the code, and run `abbd status --check`, which exits 0. Tell the human where the blueprint is. From here on the abbd skill reads and queries the blueprint.

## Extraction format

```json
{
  "units": [
    {"ref": "billing", "kind": "MOD", "name": "billing",
     "anchors": [{"path": "billing"}, {"path": "billing/charge.go", "symbol": "Charge"}]},
    {"ref": "api", "kind": "IF", "name": "http api", "signature": "GET /charges", "digest": "3f9a1c0d",
     "anchors": [{"path": "api/http.go", "symbol": "Serve"}, {"path": "api/http.go", "symbol": "Routes"}]},
    {"ref": "charges", "kind": "DATA", "name": "charges table", "parent": "billing",
     "evidence": [{"path": "billing/charge.go", "lines": "41", "quote": "INSERT INTO charges"}]}
  ],
  "relations": [
    {"from": "billing", "to": "api", "kind": "provides",
     "evidence": [{"path": "api/http.go", "lines": "8", "symbol": "Routes", "quote": "func Routes() {"}]},
    {"from": "ledger", "to": "charges", "kind": "consumes", "via": "data", "phrase": "SELECT amount",
     "evidence": [{"path": "ledger/book.go", "lines": "12-13", "quote": "SELECT amount FROM charges"}]}
  ]
}
```

- `kind` is one of `MOD`, `IF`, `EVT`, `DATA`, `CFG`, `FEAT`, `EXEC`. Only contracts carry a `signature`. An `EXEC` is an execution context: a thread, a worker pool, an event loop, an async runtime, or the tasks one spawn site starts, as one unit with its owning module as `parent` and the spawn site as `evidence`.
- `run` is how an `EXEC` runs, its shape and its count, such as `"tick 1"`. The shape is `tick` (a periodic loop), `wait` (blocks on a queue or condition), `ready` (a readiness loop such as select, epoll or a reactor), `complete` (a completion queue), `steal` (a work-stealing pool) or `inline` (runs on its caller). The count is `1`, `N` or `pool`. Only an `EXEC` carries one, and its box says it on its last line, such as TICK · 1.
- `digest` fingerprints the code a contract's meaning lives in, so `abbd diff` sees a change of meaning under the same signature.
- `artifacts` is the set of what the build makes of a `MOD`, each `exe`, `static`, `shared`, `module` or `cdylib`. Its box says it on its last line, such as 공유 라이브러리.
- `entries` lists a contract's parts one by one when it has several a reader names on their own: routes, RPC methods, a command's flags, a table's columns. Each is `{"name", "shape"}`, spelled as the code registers it, such as `{"name": "GET /charges/{id}", "shape": "-> Charge"}`. Keep in `signature` only what every entry shares, such as a base path, and never join the entries into it, or a change to one reads as a change to all. abbd keys each entry by its name in lower-case letters, digits and hyphens, so `GET /charges/{id}` is `get-charges-id`. Two names that reduce to the same key are refused. Give one a `"key"` of its own. The script reports entries and the supplement does not. An entry's meaning is a reader's note, `<ID>.entries.<KEY>`, never text the script copies from comments.
- A relation's `entries` names the entries of its `to` contract it uses, by name, when the code spells them where it uses them: the route a page fetches, the flag a skill passes. Leave it out when the code does not say.
- For a contract that holds data, such as a table, a file format or a message, make each field an entry: `{"name": "amount", "shape": "numeric(12,2)", "required": true}`. Print `shape` as the type the code declares, from the schema, the struct or the type definition, never a type guessed from sample values. Set `required` only where the code says so, and leave it out otherwise: `NOT NULL` or a primary key in SQL, a field without `omitempty` or `?`, a schema's `required` list, or proto2 `required` against `optional`. A nested field is named under its parent, as in `items.id`. The blueprint draws the fields as a table with their type, whether each is required, and who writes and reads it, and `abbd diff` reports a field's type change and a change to whether it is required as lines of their own.
- A field's writer is a `provides` relation and its reader a `consumes` relation, each with the field in `entries`. Emit them where the code names the field: an `INSERT` or `UPDATE` column list, a keyed struct literal, an assignment to the field, a `SELECT` column or a read of the field. Leave a module that moves the whole record without naming a field, such as the code that serializes it, as a plain relation without entries.
- `ref` is the unit's name within the extraction, stable across runs. `relations` name units by `ref`; `kind` is `depends_on`, `consumes`, `provides`, `runs_on` (the unit's code runs on that `EXEC`, or an `EXEC`'s tasks run on that runtime) or `posts_to` (the unit hands work or data to that `EXEC`). A `posts_to` quotes the producer and the consumer, so it is refused with fewer than two `evidence` items.
- `via` is `import`, `trait`, `callback`, `macro`, `config`, `build-feature`, `data`, `convention`, `call`, `link` (an artifact linked or compiled in at build time), `load` (a library or plugin loaded by name at run time), `spawn` (a process started), or, for a hand-off between execution contexts, `queue`, `channel`, `signal` (a semaphore, condition variable or notify) or `proxy` (a message to another loop, such as an EventLoopProxy).
- `when` is the condition a relation holds under, one line of at most 60 characters, such as `feature = "sinks-kafka"`, `cfg(unix) | cfg(windows)` or `dev`, or a link scope, `PRIVATE`, `PUBLIC` or `INTERFACE`. Leave it out for a relation that always holds. In the supplement, a `when` on an edge the script prints gives that edge its condition when the script gives none or only a scope, and needs `evidence`, the line the condition is written on. One that differs from the script's condition, or a scope that differs from the script's scope, is a `conflict:`. A line's tooltip lists its conditions and `abbd explain <ID>` prints them, each marked with the supplement's origin when the line is the script's (`when WIN32, inferred`). `abbd evidence` lists the condition's quote as `FROM.KIND.TO.when`. `abbd record evidence FROM.KIND.TO.when --evidence PATH:LINES:QUOTE` refreshes it and `abbd retract FROM.KIND.TO.when --reason TEXT` removes it, and a dead one stays counted until then.
- `phrase` says in at most 4 words and 24 characters what crosses a coupling: an endpoint, a message, a query, a file or a command. Examples are `HTTP /api/v1`, `schema fetch`, `Cypher`, `NDJSON /ingest push`, `IsReady 조회 (health)` and `샘플 조회 SQL`. It never restates the via, in its own words or in others. An `import` edge is not `model types`, and a `call` edge is not `function call`. Name the thing itself, such as `Unit, Evidence, Claim` for the types one package takes from another or `LoadUnits` for the loader a page calls. Never give many edges one generic phrase such as `shell command`. If nothing more specific than the via crosses, leave `phrase` out. The blueprint draws it beside the line, marked as the supplement's words, INFERRED. Quote the code where the thing crosses, so the phrase goes when that code changes. Only the supplement gives a phrase, never the script.
- `evidence` is a list of `{"path", "lines", "symbol", "quote"}`; `lines` and `symbol` are optional. The quote is verbatim; whitespace does not matter, and it must sit within three lines of `lines`. A unit or coupling only a reader found lives while any of its quotes is in its file. A quote its file no longer holds drifts, and dies at a sync of a later revision unless `abbd record evidence <TARGET> --evidence <PATH:LINES:QUOTE>` refreshes it.
- `parent` names, by ref, the module that contains a unit. A unit with no parent is drawn on the overview; a unit with one is drawn inside its module. In the supplement, `parent_evidence` is the code that places a unit there; without it the unit's own `evidence` stands in. A parent from the supplement is INFERRED and is stored beside the script's. The script's parent outranks it, and a human's outranks both. `abbd record parent ID PARENT --evidence ...` places one unit later.
- The script's output carries no `purpose` or `responsibility`. Unknown fields are rejected.

Rerunning setup replaces every claim the last supplement made and finds its units again by `ref`, so keep each unit's ref stable. Older scripts and supplements spell it `key`, and abbd still reads that, but a path-like key with enough entropy trips gitleaks' `generic-api-key` rule, so write `ref`. What a reader stored through abbd record and what the human stated stay. A state from before writers existed is converted once with `abbd migrate`, which needs this supplement to tell its claims from a reader's.
