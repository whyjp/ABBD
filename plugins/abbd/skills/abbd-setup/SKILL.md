# ABBD setup

**Reader.** Setup reads code with the abbd skill's reader, `../abbd/references/reader.md`. Follow it for every reading step below. It needs only the abbd CLI, and it says when pstack may serve as an optional engine.

Setup asks the human one thing only, how dense the overview should be (step 7), and only when a human is in the conversation. The first state you commit is the baseline; the human reads it in the blueprint and the PR, and there is no alignment step.

## Steps

1. List unit candidates from the layout, entry points, manifests and schemas. A unit is something a human would say "this change must not touch that" about: a responsibility (`MOD`), an external contract (`IF`, `EVT`, `DATA`, `CFG`), a user-facing feature (`FEAT`). Imports, calls and file placement are material for finding units, never units.

   Then choose the levels the blueprint draws, before any script:
   - The overview draws the parts a reader reasons about when explaining the system: 4 to 12 top-level modules, and the external systems it talks to as contracts. Folders a framework imposes, such as `app/`, `components/`, `lib/` or `src/`, are not parts. The modules under them are. One root package that holds most of the system is several parts, its responsibilities.
   - What most parts use, such as shared types, a UI kit, providers or small helpers, is one shared module, the layer the others stand on. Its incoming lines do not count toward the density. A helper only one part uses sits inside that part.
   - Group until each level reads. Modules that serve one responsibility and change together are one part, along a grouping the project shows: a package, a directory, a family of implementers, a section of its docs. Grouping to bring a level within these bounds is required. Grouping modules that share no responsibility, only to hide their lines, is not allowed.
   - Each module's page draws 2 to 16 parts, the bounds `abbd lint` holds every page to: its responsibilities, its subpackages, or one family of implementers of an interface it holds, such as every output format. A part is several files that change together, never one file per box. A module too small for two parts gets no page of its own. A top-level one is a leaf of the overview with no units inside. A nested one folds its files into the module around it.
   - Keep the lines few, about 2 a box at most, past the lines into the shared module. More means the parts are cut too fine, or a shared module is drawn as a peer.
   - Name each unit by its role, such as `radix router` or `cart`, taken from the code that defines it (a package comment, the main type, the route), never by its path.
   - The script decides the units and their names (step 3), and a parent it gives outranks the supplement's, so choose the levels in the script where the code shows them. The supplement cannot rename a unit the script reports, and cannot move one the script places in a module. It can place a unit the script leaves on the overview inside a module, with `parent_evidence` (step 4).
2. Read the candidates in slices, per the reader's "At setup" section: at most five workers, each run locally without worktree isolation so it sees uncommitted code, each reporting in the extraction format below. Every unit the layout does not show comes with verbatim `evidence`, and every coupling it reads, whether the layout shows it or not, comes with `via`, a `phrase` that says what crosses it, and verbatim `evidence`, and a unit inside a module names that module as `parent`.
3. Build the lever, per the reader's "At setup" section. Start from the bundled front-end when the repository builds with a system abbd reads. `abbd extract cargo` reads a Cargo workspace and `abbd extract cmake=<DIR>` the CMake project whose top `CMakeLists.txt` sits in `<DIR>`, such as `cmake=build/cmake`. Name both, as `abbd extract cargo cmake=native`, for a repository with both. Each prints the extraction JSON from the build system's own model: a module per crate or per set of targets that compile the same sources, the `artifacts` each builds, and its dependencies on the others with `via` `import`, `macro`, `build-feature` or `link`. A static and a shared build of one library are one `MOD` with both artifacts. A plain Rust library or proc-macro crate is a module with no artifact. Test, example and bench targets are left out. CMake configures in `$ABBD_CACHE_DIR`, outside the repository. The CMake front-end needs CMake 4.2 or later, the first release whose file API records which targets a target links directly apart from those `add_dependencies` only builds first. It refuses an older CMake and names the version it found. Get 4.2 or later from the official release at https://cmake.org/download/, `pip install cmake`, the Kitware apt repository on Debian or Ubuntu, `brew install cmake` on macOS or `winget install Kitware.CMake` on Windows, and put it first on the `PATH`. Where only an older CMake is at hand, describe the modules in the supplement instead. Never re-derive crates, targets or linkage by hand. When those modules are all the topology needs, register the front-end itself, as `abbd setup -- abbd extract cargo`. Otherwise write `.abbd/extractor/extract.<ext>` to run the front-end, keep its units and relations, and add only what the build model cannot show: contracts, routes, configuration and source-level couplings. Setup and sync pass the path of the abbd that runs the script in `$ABBD_BIN`, so the script runs `"$ABBD_BIN" extract cargo`, never an `abbd` it finds on the `PATH`, which can be another version that reads the build differently. Where no toolchain can configure the project, give the artifacts in the supplement instead, with the line that declares each target as evidence. Without a supported manifest, write `.abbd/extractor/extract.<ext>`, a script that prints the extraction JSON from the code alone: imports, routes, schemas, manifests, and each contract's `signature` and `digest`. It runs from the repository root, sorts its output, and uses no clock, network or model. Pick anchors mechanically and stably: every non-test file of a package plus its directory, or a file plus the symbol that defines a contract. Find modules and contracts from the code, never from a list the script keeps by hand. Walk the tree for manifests such as `go.mod`, `package.json`, `Cargo.toml` or `pyproject.toml`, and find routes, commands and environment reads by the calls that register or read them, so a module or contract added later is a unit at the next sync. Setup and sync name each manifest that no unit anchors code under as `uncovered:`. Have it fail when a unit has fewer than two anchors or an anchor names a symbol its file does not declare. Read configuration, such as the environment variables a `CFG` contract lists, only from the code that runs in production. Skip test, end-to-end and tooling config by its file, such as `playwright.config.ts`, a `jest` or `vitest` config or a CI workflow, the same way anchors skip test files. Never drop a variable by its name. `NODE_ENV` or `CI` can gate runtime behaviour, such as whether a login is refused or a cookie is `secure`, and then it is part of the contract. The bundled front-ends print no `when`, so a script that runs one adds it, or the supplement gives it. Give a relation that holds only under a condition its `when`, as the build says it. For Cargo: `cargo metadata` does not name the feature that enables an `optional` dependency, so read it from the package's `features` map, each feature that lists `dep:<name>`, or the implicit feature of the dependency's own name when no feature lists `dep:<name>` (`feature = "sinks-kafka"`), and join several (`feature = "a" | feature = "b"`). A dependency under `[target.'cfg(...)']` takes its cfg, and a dev or build dependency takes `dev` or `build`. For CMake, the file API reports only the configured result, not which `if()` or `option()` branch ran or the generator expression, so read those conditions from the CMakeLists text, or give them in the supplement: list the edge the script prints, with the condition as its `when` and the `if` line as evidence. The script's line then shows that condition, and it stays through every sync. Setup and each sync report a supplement condition that differs from one the script prints as a `conflict:`, and so is a supplement scope that differs from the script's. There the script's scope shows, and the supplement's stays stored until the supplement drops it. A CMake link's `PRIVATE`, `PUBLIC` or `INTERFACE` goes in `when` when the link has no condition, and the page shows it as the link's scope. A link with both a scope and a condition keeps the condition and drops the scope, because a scope is not a condition and `PRIVATE | WIN32` would read as either one. A condition from the supplement shows over a scope the script prints. Print each edge once: join the conditions of an edge listed more than once (`cfg(unix) | cfg(windows)`), and give no `when` when any listing has none. Parse refuses an edge given twice with different conditions. Diff its output against the slices' result until every difference is explained. Give every relation the script prints a `via` wherever the code says how it arises: `call` for a package or command the code calls, `data` for a file or table it reads or writes, `config`, `callback`, and `import`, `trait`, `macro`, `build-feature`, `link` or `convention` for a coupling that exists only in design or at build time. The drawing dots a line whose relations arise only in design and draws the rest solid, so a relation with no `via` reads as run-time. `abbd status` counts those in its `via:` line. For a plug-point contract, a callback table, a trait or a weak symbol the host calls through, the modules that implement it or register an implementation `provides` it, and the host that calls through it `consumes` it. Registering an implementation is providing, not consuming, and `abbd lint` names a callback table or trait that looks reversed on a `direction:` line.
4. Write `.abbd/extractor/supplement.json` with what only reading tells:
   - `purpose` and `responsibility` for script units, repeating `ref`, `kind`, `name` and one anchor of the unit they describe, with no `evidence`. When that anchor is also held by the unit's module, such as the directory of an inside module, the innermost unit is matched
   - units the script cannot see, such as a shared table or a wire format, with `evidence` instead of anchors and their module as `parent`, by the supplement's ref or the script's; the module need not be restated. A quote may sit on an anchor of that parent or of a module around it, as long as the parent holds some anchor the unit does not. A quote on an anchor of any other script unit of the same kind makes setup refuse the unit and name both. A contract the script reports no `signature` for keeps the one the supplement gives, as INFERRED
   - couplings the script cannot see, such as a shared table, an execution order, a trait used through generics, a callback, a plugin loaded by name, a helper process started, a component registered with a registry, a flag passed through config, a build feature or a convention two units keep in step, each with `via`, `phrase` and `evidence`. A plug point goes as step 3 says: its implementers provide it and the host that calls through it consumes it. Name each end by the supplement's ref or the script's. An end the script reports needs no entry of its own in the supplement
   - a `phrase` for the couplings the script reads, starting with those between top-level modules, which the overview draws. Every overview line takes at least one, since a line without one says nothing at rest: its plain 호출 or 임포트 shows only in the tooltip. Repeat the edge with `via`, `phrase` and `evidence`. The script's claim still holds the edge, and the phrase only labels its line
   - a grouping the project shows that the script cannot see: a subsystem its docs name, a skill family, or an abstraction the code shows (a layer, a family of implementers of one interface). Add it as a `MOD` whose `evidence` quotes the project naming or showing it (the README section, manifest, entry point or code), and give each member that part as `parent` with `parent_evidence` quoting the project placing it there. Add one when step 1's bounds need it, never for members that share no responsibility. Sync's fallback places a crowded level's units in the directories their code lives in, and never moves a unit a reader placed
5. Run setup:

   ```
   abbd setup --supplement .abbd/extractor/supplement.json -- <interpreter> .abbd/extractor/extract.<ext>
   ```

   - `not deterministic`: the script printed different output across three runs, one with a different `PYTHONHASHSEED` and `PERL_HASH_SEED`. Sort what it prints and remove the variation.
   - `fix the script, or cite the code`: a supplement unit matches no script unit and cites no evidence. Teach the script the unit, add `evidence`, or drop it.
   - `would merge into it`: a supplement unit with evidence shares an anchor with a script unit that is not its parent. Name that unit as `parent` if the unit sits inside it, quote code of its own, or drop the evidence if it describes that script unit.
   - `cites no evidence`: a supplement coupling has no quote. Add one or drop it.
   - `is not a relation ABBD knows`: a module or feature `provides` a contract, anything `consumes` a contract, anything `depends_on` any unit, a module, feature or `EXEC` `runs_on` an `EXEC`, and a module or `EXEC` `posts_to` an `EXEC`.

   Once setup passes, run `abbd lint`. The `level` lines at the end of its report name each view drawn at the wrong level, too coarse, too fine or too dense, and say what to change in the units. Change the script or the supplement as it says and rerun setup, until no `level` line is left or you can say in the reply why one stays. Step 8 records that reason. Fix the levels before anything else: the hard breaches of a dense view come from its units, and most go once its level reads.
6. First write the project's `language` into `.abbd/project.yaml` as a BCP-47 tag, such as `ko`, the language the human writes to you in the conversation. Ask once only when the conversation shows none, as when it holds only commands; with no human in the conversation, leave it out and abbd takes the OS's locale. Every text below is then written in it, as `abbd brief <MOD-ID>` says. Then write the project's `name` and a one-paragraph `purpose` into `.abbd/project.yaml`, so the overview opens with what the project is for. Then, for each top-level module, read it per the reader and store its Overview and Key Concepts with `abbd understand <MOD-ID> <FILE> --reader "<WHO>"`. A directory group that sync made counts as a top-level module, because the overview draws it like any other. Any module takes a text, so do the same for a module inside another when the project's own docs describe it on its own, or when its page is dense enough to list focus views, since a reader of a tangle leans on the text most. Write the texts in the order a reader meets the pages. The top-level modules come first, then the modules one level below them that take a text, then the deeper ones. A page without its text has no account of what the module does. Its text describes its own subtree, and its parent's text still describes all of it. Write the text as the code is now, in the present tense. Leave out dates, issue and PR numbers, and tags such as "migrated from X", because git keeps the history. Keep each section under 2,000 characters of prose, and split a longer one under `###` headings or into shorter sections. `abbd understand <MOD-ID> <FILE>` and `abbd status` report each section over that length and each phrase that reads as history. Neither fails the check, because a version number or a name can read as history too. `abbd understand <MOD-ID> <FILE>` refuses only a text whose first section, the summary a page shows before it folds the rest, runs over 2,000 characters. While the reader is in a top-level module, store at least one `decisions` note for it with `abbd understand <MOD-ID>.decisions.<KEY> <FILE> --evidence PATH:LINES:QUOTE`, saying what the code chose over what, so its page carries the reason a reviewer weighs a change against. Open the text with a short summary of the module, under 2,000 characters, because the page shows the first section and folds the rest, and `abbd understand <MOD-ID> <FILE>` refuses a longer one. Name each Key Concept after the file it lives in or the unit's ID in backticks, such as `route.go` or `MOD-0042`, so the page sets the concept beside that unit's box. Store what the reader calls Gotchas as `failure` or `semantics` notes with evidence, and How It Works as a flow with `abbd flow <KEY> <FILE>`, not in the text.
7. Look at the drawings. Open `.abbd/blueprint/index.html` in a browser 1600px wide, take a screenshot of the overview and of the densest module page, and read the images. Revise the units and rerun setup when a view reads badly: a box an engineer of the project would not name, a tangle whose lines you cannot follow end to end, a page that repeats its module, a line between top-level modules with no phrase. Check too that each page reads the way the readers described the code, and that no page one click from the overview still says its description is missing. Then read the `described:` line of `abbd status`, which `abbd lint` repeats. Each unit and contract it names is a box that says only its kind, so give it a responsibility in the supplement and rerun setup. A module or feature with a text takes its line with `abbd understand <ID> <FILE> --sentence TEXT`. Only for one the human stated, record it with `abbd record fact ID.responsibility --value TEXT --source REF`. `abbd brief <MOD-ID>` drafts one for each such box of a module from the Go doc comment of its anchored symbol, or else from its file's header comment, and drafts none where neither says anything. The draft is a lead for the reader, not a finding: keep it when the code bears it out, rewrite it when it does not, and write only what you read. Setup is not done while the line names any unit.
   Then read the overview's density: `abbd lint --json` gives it as `totals.density` of the view named `overview`, the lines it draws per box in tenths. When it is over 17 and `.abbd/project.yaml` has no `overview_cut` line, ask the human whether the overview should draw only its main lines and show the rest as a `+N` on each box that opens the box's own view. Write the answer as `overview_cut: true` or `overview_cut: false` in `.abbd/project.yaml` and rerun `abbd sync`. This is how the human likes the overview drawn, not a check of the blueprint, so a stored answer is never asked again. With no human in the conversation, as in a headless or swarm run, leave the line out and say in the reply how dense the overview is and that `overview_cut: true` draws only its main lines.
   Then read `lint: phrases:` in `abbd lint`. It names each overview line, by the boxes at its ends, whose relations carry no live phrase. A line shows a phrase once half its relations carry it. Give one relation of each a phrase in the supplement, or with `abbd record relation <FROM> <KIND> <TO> --via <VIA> --phrase "<PHRASE>" --evidence <PATH:LINES:QUOTE>` for one you read, until it names none.
8. Run `abbd lint --record` to record the hard breaches that remain as the repository's routing debt, and name each in the reply. The first record refuses while a view with hard breaches has a `level` line. Go back to step 5 for it, or, for a level step 5 lets stay, rerun as `abbd lint --record --keep-level <VIEW>=<REASON>`, once per such view, which writes the reason into `.abbd/lint-debt.yaml`. A `level` line is never debt.
9. Run `abbd install`. It writes a short block between `<!-- abbd:begin -->` and `<!-- abbd:end -->` into `CLAUDE.md` at the project root, so any assistant asks `abbd explain <QUERY>`, `abbd path <A> <B>` and `abbd impact <QUERIES>` before it greps, and runs `abbd sync` and puts `abbd diff` in the PR after it changes code. A rerun replaces the block and keeps the rest of the file.
10. Add `.abbd/state.yaml merge=union` to `.gitattributes`, so a merge of two synced branches does not stop on the state. The abbd skill says how to resolve it.
11. Commit `.abbd/`, `.gitattributes` and `CLAUDE.md` with the code, and tell the human where the blueprint is. From here on the abbd skill reads and queries the blueprint.

## Extraction format

```json
{
  "units": [
    {"ref": "billing", "kind": "MOD", "name": "billing",
     "anchors": [{"path": "billing"}, {"path": "billing/charge.go", "symbol": "Charge"}]},
    {"ref": "api", "kind": "IF", "name": "http api", "signature": "GET /charges", "digest": "3f9a1c0d",
     "anchors": [{"path": "api/http.go", "symbol": "Serve"}, {"path": "api/http.go", "symbol": "Routes"}]},
    {"ref": "charges", "kind": "DATA", "name": "charges table", "parent": "billing",
     "evidence": [{"path": "billing/charge.go", "lines": "41", "quote": "INSERT INTO charges"}]}
  ],
  "relations": [
    {"from": "billing", "to": "api", "kind": "provides"},
    {"from": "ledger", "to": "charges", "kind": "consumes", "via": "data", "phrase": "SELECT amount",
     "evidence": [{"path": "ledger/book.go", "lines": "12-13", "quote": "SELECT amount FROM charges"}]}
  ]
}
```

- `kind` is one of `MOD`, `IF`, `EVT`, `DATA`, `CFG`, `FEAT`, `EXEC`. Only contracts carry a `signature`. An `EXEC` is an execution context: a thread, a worker pool, an event loop, an async runtime, or the tasks one spawn site starts, as one unit with its owning module as `parent` and the spawn site as `evidence`.
- `run` is how an `EXEC` runs, its shape and its count, such as `"tick 1"`. The shape is `tick` (a periodic loop), `wait` (blocks on a queue or condition), `ready` (a readiness loop such as select, epoll or a reactor), `complete` (a completion queue), `steal` (a work-stealing pool) or `inline` (runs on its caller). The count is `1`, `N` or `pool`. Only an `EXEC` carries one, and its box says it on its last line, such as TICK · 1.
- `digest` fingerprints the code a contract's meaning lives in, so `abbd diff` sees a change of meaning under the same signature.
- `artifacts` is the set of what the build makes of a `MOD`, each `exe`, `static`, `shared`, `module` or `cdylib`. Its box says it on its last line, such as 공유 라이브러리.
- `entries` lists a contract's parts one by one when it has several a reader names on their own: routes, RPC methods, a command's flags, a table's columns. Each is `{"name", "shape"}`, spelled as the code registers it, such as `{"name": "GET /charges/{id}", "shape": "-> Charge"}`. Keep in `signature` only what every entry shares, such as a base path, and never join the entries into it, or a change to one reads as a change to all. abbd keys each entry by its name in lower-case letters, digits and hyphens, so `GET /charges/{id}` is `get-charges-id`. Two names that reduce to the same key are refused. Give one a `"key"` of its own. The script reports entries and the supplement does not. An entry's meaning is a reader's note, `<ID>.entries.<KEY>`, never text the script copies from comments.
- A relation's `entries` names the entries of its `to` contract it uses, by name, when the code spells them where it uses them: the route a page fetches, the flag a skill passes. Leave it out when the code does not say.
- For a contract that holds data, such as a table, a file format or a message, make each field an entry: `{"name": "amount", "shape": "numeric(12,2)", "required": true}`. Print `shape` as the type the code declares, from the schema, the struct or the type definition, never a type guessed from sample values. Set `required` only where the code says so, and leave it out otherwise: `NOT NULL` or a primary key in SQL, a field without `omitempty` or `?`, a schema's `required` list, or proto2 `required` against `optional`. A nested field is named under its parent, as in `items.id`. The blueprint draws the fields as a table with their type, whether each is required, and who writes and reads it, and `abbd diff` reports a field's type change and a change to whether it is required as lines of their own.
- A field's writer is a `provides` relation and its reader a `consumes` relation, each with the field in `entries`. Emit them where the code names the field: an `INSERT` or `UPDATE` column list, a keyed struct literal, an assignment to the field, a `SELECT` column or a read of the field. Leave a module that moves the whole record without naming a field, such as the code that serializes it, as a plain relation without entries.
- `ref` is the unit's name within the extraction, stable across runs. `relations` name units by `ref`; `kind` is `depends_on`, `consumes`, `provides`, `runs_on` (the unit's code runs on that `EXEC`, or an `EXEC`'s tasks run on that runtime) or `posts_to` (the unit hands work or data to that `EXEC`). A `posts_to` quotes the producer and the consumer, so it is refused with fewer than two `evidence` items.
- `via` is `import`, `trait`, `callback`, `macro`, `config`, `build-feature`, `data`, `convention`, `call`, `link` (an artifact linked or compiled in at build time), `load` (a library or plugin loaded by name at run time), `spawn` (a process started), or, for a hand-off between execution contexts, `queue`, `channel`, `signal` (a semaphore, condition variable or notify) or `proxy` (a message to another loop, such as an EventLoopProxy).
- `when` is the condition a relation holds under, one line of at most 60 characters, such as `feature = "sinks-kafka"`, `cfg(unix) | cfg(windows)` or `dev`, or a link scope, `PRIVATE`, `PUBLIC` or `INTERFACE`. Leave it out for a relation that always holds. In the supplement, a `when` on an edge the script prints gives that edge its condition when the script gives none or only a scope, and needs `evidence`, the line the condition is written on. One that differs from the script's condition, or a scope that differs from the script's scope, is a `conflict:`. A line's tooltip lists its conditions and `abbd explain <ID>` prints them, each marked with the supplement's origin when the line is the script's (`when WIN32, inferred`). `abbd evidence` lists the condition's quote as `FROM.KIND.TO.when`. `abbd record evidence FROM.KIND.TO.when --evidence PATH:LINES:QUOTE` refreshes it and `abbd retract FROM.KIND.TO.when --reason TEXT` removes it, and a dead one stays counted until then.
- `phrase` says in at most 4 words and 24 characters what crosses a coupling: an endpoint, a message, a query, a file or a command. Examples are `HTTP /api/v1`, `schema fetch`, `Cypher`, `NDJSON /ingest push`, `IsReady 조회 (health)` and `샘플 조회 SQL`. It never restates the via, in its own words or in others. An `import` edge is not `model types`, and a `call` edge is not `function call`. Name the thing itself, such as `Unit, Evidence, Claim` for the types one package takes from another or `LoadUnits` for the loader a page calls. Never give many edges one generic phrase such as `shell command`. If nothing more specific than the via crosses, leave `phrase` out. The blueprint draws it beside the line, marked as the supplement's words, INFERRED. Quote the code where the thing crosses, so the phrase goes when that code changes. Only the supplement gives a phrase, never the script.
- `evidence` is a list of `{"path", "lines", "symbol", "quote"}`; `lines` and `symbol` are optional. The quote is verbatim; whitespace does not matter, and it must sit within three lines of `lines`. A unit or coupling only a reader found lives while any of its quotes is in its file. A quote its file no longer holds drifts, and dies at a sync of a later revision unless `abbd record evidence <TARGET> --evidence <PATH:LINES:QUOTE>` refreshes it.
- `parent` names, by ref, the module that contains a unit. A unit with no parent is drawn on the overview; a unit with one is drawn inside its module. In the supplement, `parent_evidence` is the code that places a unit there; without it the unit's own `evidence` stands in. A parent from the supplement is INFERRED and is stored beside the script's. The script's parent outranks it, and a human's outranks both. `abbd record parent ID PARENT --evidence ...` places one unit later.
- The script's output carries no `purpose` or `responsibility`. Unknown fields are rejected.

Rerunning setup replaces every claim the last supplement made and finds its units again by `ref`, so keep each unit's ref stable. Older scripts and supplements spell it `key`, and abbd still reads that, but a path-like key with enough entropy trips gitleaks' `generic-api-key` rule, so write `ref`. What a reader stored through abbd record and what the human stated stay. A state from before writers existed is converted once with `abbd migrate`, which needs this supplement to tell its claims from a reader's.
