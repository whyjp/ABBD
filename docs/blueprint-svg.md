# Blueprint drawing rules

A person should understand and judge an architecture from `.abbd/blueprint/index.html` quickly. What makes a blueprint hard to read is not the number of relations. It is lines that run the same way but are drawn apart, lines that run against the eye or out of their way, and views that try to show too much at once. The bar is a diagram a person polished by hand in a tool like draw.io, not a dump of extracted edges. So the blueprint follows three principles, and every rule below comes from one of them.

- **Decomposition.** The blueprint is a tree of views, all drawn the same way. The overview shows the top level. Every unit that holds others has a view of its children, with that unit's contracts on the frame. A box that holds units opens its view. Each view stays small because the state is decomposed, never because relations are left out.
- **Convergence.** Lines that come from one place travel together as one trunk and branch only near their ends. Lines that go to one place, or to boxes side by side that the same places reach, merge midway into one trunk and split only in the gap above them. Every trunk carries a count. A reader follows one trunk instead of a braid.
- **Flow.** A drawing reads top to bottom and left to right. What calls or uses sits above and to the left. What it calls or uses sits below and to the right. Lines point down or right, and run on the grid in the spaces between boxes, the short way. The few that must climb are drawn dashed and faint, so they mark the exception without pulling the eye from the flow.

`internal/screen/legible.go` checks every rule on the rendered SVG, which is what a reader sees. `internal/screen/trace.go` traces every relation along the drawn ink, the way a reader follows a line, for rules 16 to 23. `internal/screen/fixtures_test.go` applies the checks to every view of four real states: this repository, ripgrep, Orca and pstack's skill tree. The rule numbers below match the checker's messages. `abbd lint` holds every drawing to the Drawing criteria below, which build on the same measures.

## Decomposition

1. **At most 16 boxes per view.** Top-level contracts don't count, because they are drawn as chips, and neither does a focus view's twin. A level that holds more is split only along a grouping the project shows (see Grouping levels). Otherwise it stays as it is, a debt of this rule, and its focus views read it one box at a time.
2. **No relation is dropped.** Every live relation between present units appears in some view. It can be a line, a bundle, a contract chip, the list of a reader's couplings under a module's inside, or the list of relations between two contracts. Each wire and chip records the stored relations it stands for, and the test compares those records with the state.
3. **Width budget.** Every drawing is at most 1320px wide. A 1600px desktop window shows that much beside the page's nav. The nav is 13rem wide, the page has a 10px gutter and a section 10px of padding, so a drawing's box is 1333px wide in that window. A 1320px budget would scroll sideways under a 15rem nav and 16px and 14px of padding. A budget of 1270px fits that wider chrome, but it draws 21 more jogs and 32 more paths that turn more than twice, so the chrome gave the width instead. A drawing wider than its box, as in a 1280px window, scrolls inside its box. A unit's page sets its text in a panel below its drawing, not in a column beside it, so a unit's view takes the same width as the overview. It used to stop at 920px. A layer that is too wide wraps into rows. A module on the overview whose chips need more than 480px wraps them into up to two rows inside its box instead of widening, so lines can pass beside it; the last row folds what still does not fit into one `+N` chip that names them all. A frame never grows past the budget: chips that do not fit on their side move to the other side, and those that fit on neither fold into one `+N` chip. On a 390px screen the drawing scrolls inside its box and the page itself never scrolls sideways.

## Focus views

Some views stay a tangle however they are laid out: their boxes use each other many times over. Orca's desktop main process holds 15 units and draws 78 relations, and the median relation crosses 9 others. pstack's twelve families use each other in 42 of 66 pairs. A reader cannot follow one box's lines through all the others. So such a view is also read one box at a time, through views derived from it (`focus.go`).

A view is dense when it draws more than two relations per box on average. Each box of a dense view then gets a focus view. A focus view of box X in view V is a partial graph of V:

- **Selected.** X and the boxes of V that X uses or that use X: the ring.
- **Drawn.** Only the lines with an end at X. A line between two ring boxes is left out here and drawn in the focus view of either of them.
- **Lifted.** X's lines to anything outside V's scope stay on the frame, lifted to the largest unit that holds their end, exactly as in V. On the overview, a contract X provides brings the modules that use it, and a contract X uses brings the modules that provide it.
- **Collapsed.** Nothing new. A ring box that holds units stays one box, as in V.
- **Placed.** Callers above X, what X uses below it, and X at the middle of the drawing. The lines from the frame to X run down the same middle, so they drop straight into it, and each row of the ring packs around them. A row that cannot reach that far without passing the width budget moves in only as far as it must.
- **Mental map.** The boxes of each ring row stand left to right in the order they stand in V, so a box the reader found left of another in V is still left of it here. A ring too wide for one row splits into rows that each take every k-th box: each row still runs across V from left to right, and a box of one row stands over a gap in the next, where its line passes down. A test holds the order and the centred focus across the fixtures.
- **Twins.** A ring box that both uses X and is used by it is drawn twice, once on each side, so every line of the view reads down and no line between the pair runs both ways through a bundle. The second box is a twin: a unit of the drawing only. Its tooltip and its sub-line say it is also drawn above, and rule 1 counts it once.
- **Width.** A focus view takes the width budget every view takes, and its unit boxes show only the last segment of a path-like name, as frame ports do.
- **Back to the stored graph.** Every line keeps the stored relations it stands for, as in V. Each ring box opens its own focus view, X opens its inside when it has one, and the section links back to V.

A focus view stores nothing: it is cut from V's own lines at render time, never found again, so it draws no line, chip or box that V lacks. V stays as it is, and every relation V draws has a box at one end, so it is drawn in that box's focus view too. A test holds both directions across the fixtures. A reader who only wants to follow one box need not leave V. A line's ink is drawn in pieces: its own stub, the buses it rides, and their drops. So each line also gets a route, one path along its whole way from the shape it leaves to the shape it reaches. The route is drawn unseen above all the ink and takes no pointer, so the pointer always rests on ink and the ink keeps its title, which names every line it carries. Each piece of ink names every route that runs along it, so pointing at a stub, a bus or a drop shows each of those lines as its route, whole and in its own colour, with the line's word, count and origin marks, while every other piece of ink fades and only the shapes at those lines' ends stay lit. While the pointer rests on a box or a frame chip, or a box that is a link has the keyboard's focus, all the ink and every dot fades, and exactly the box's own relations show: each line in or out with an end there, as its route, and the shapes at their other ends. A box colours every one of those routes its own colour, whatever the line's kind, which its dash and arrowhead still show. A chip wears no unit's colour, so it leaves each route the line's own, and a contract chip on a box dims and lights with its box. Every box and chip no relation of the view joins to it fades too (`hover.go`). A route's arrowheads paint in the route's colour, set on the route, so no engine draws them black. The page holds no script, so this is plain CSS: one rule per shape number and one per route number, and each route carries, as inline variables, the colour each of its end boxes gives it. `hover_line_test.go` points at every piece of ink and every shape of every fixture. It holds that ink lights exactly the routes that run along it, each whole between its two shapes and lying on its own ink, and that a shape lights exactly its one-hop neighbours, in one colour, with no lit stroke reaching any other shape. 14 stretches of bus track carry no line's way, between two lines' drops on a shared track. Cutting those tracks back raised the fixtures' weighed sums past their ceilings (eval/lint/decisions.tsv rows 58 and 59), so that count may only fall. 40 lines ride a bus past where they leave it and come back along another track, a routing defect hover shows rather than hides, and that count may only fall too. A drawing with more than 48 shapes or 96 routes takes no part, since a shape or a line the rules cannot name would fade whatever is pointed at. Only the pages with a drawing carry the rules. A box that opens nothing takes no keyboard focus, so it follows the pointer only. Hover and focus take part only where a pointer can rest, and focus only when it came from the keyboard, so a tap or a click never leaves a view faded. Under a dense view the page also lists every focus view as a row of links, and a box of V that opens nothing else opens its focus view. A focus view of the overview sits on the page of its unit, not on the overview's page (see Pages). The graph file holds no drawing.

A focus view never groups, and neither does any other view. The renderer draws no box the state lacks, so a cycle is drawn in the view of the unit that really holds it: its units keep their own boxes, the lines that close it climb dashed under rule 13, and each of its boxes is read on its own through its focus view.

## Convergence

4. **One bundle per place and direction.** Lines of one kind that leave one edge of a box share a departure bus: one stub out of the box, then one trunk down through every row at least two of its lines still pass, heading row by row toward the places they reach. A line leaves the trunk in the gap above the first row it would pass alone. Lines of one kind that reach one edge of a box share an arrival bus: one trunk through every row they pass, one track in the gap above the box, and a drop into each chip. A line joins that trunk once it is off its departure trunk, so lines from different places merge midway and split only at the end; a line that rides its departure trunk into its last gap steps onto the arrival track where the trunk crosses that gap. Boxes side by side in one row that are reached from exactly the same places share one arrival bus that splits only in the gap above them. Boxes reached from places that only overlap get a bus each: a shared trunk would draw a path from every one of its places to every box it splits to (rule 18). The one exception is a shared bus. Two or more boxes that the same two or more places all reach, by lines of one kind running down, in one row or in several, may share one arrival bus. Its track gathers those places' lines and drops into each of the boxes, so a place that reaches them all does not split in two right below itself. A place whose every line of that kind rides it drops its stub straight onto that track. Every other line into one of those boxes joins the shared bus's drop there, on a track of its own that ends on the drop. Every place on a shared bus reaches every box it feeds, so the bus joins no two places that no line joins (rule 18). Where shared buses are drawn, they take the place of the same-row bus above. The renderer draws such a view both ways, with shared buses and without, and keeps the shared buses only when a reader pays less. It weighs each way on the routed ink. It counts the pairs of lines of one kind where one ends on the other though some place on one never reaches a box on the other, the crossings, how far lines of different bundles run side by side, and the bends and jogs along each line's whole way. The shared buses stay only with no more of the first three and fewer of the last. In a focus view, a line between rows next to each other whose two boxes' spans meet joins no bus and drops straight from one box into the other. Every line there has the focus at one end, so its bus would only gather lines that could each drop straight, and turn each of them twice. A hub still takes its lines into it as one bundle (H2). There the other lines on that edge spread to make room between the straight drops, and a bus with no side left there for its `×N` moves past the next pin into the empty room. In every view, a line that is not pinned keeps between the pinned lines on either side of it, with room for the lines between, so keeping the order never pushes a pinned line off its x, such as a chip's line pinned over its chain. Lines that all ride one departure bus, one into each box, get no second bus: they split off the departure track straight into their boxes. Frame ports folded into one `+N` chip are one place, so their lines share the chip's slots and buses. A line between two modules that use each other reads both ways, so two such lines that share a bus join their far ends, which may not relate (rule 18). The renderer draws each of them on buses of its own pair, and keeps the bundled drawing only where drawing them apart runs a line more than rule 15 allows out of its way or climbs more lines than rule 13 allows. The checker counts each of them as a bundle of its own, as it does a straight drop. Each drop shows how many of the bus's lines reach that box as `×N`. The checker counts lines that leave or reach a box edge beside the bundle of their kind, and expects 0 of each. It groups the lines by their kind alone. It used to group them by every class a line carries, and hover gives each line classes of its own, so it saw almost no split. Grouped by kind, it finds 139 lines leaving beside a bus in 105 focus views and 25 arriving beside one in 25, and every one of them drops straight from box to box, as this rule asks of a focus view. A line that drops straight needs no bundle, so the checker leaves it out, and the fixtures still hold 0. Without the straight drops, on the routing before them, the checker grouped by kind finds none.
5. **At most 4 lines per channel.** Vertical lines closer than 12px count as one channel. A fifth line takes a lane past a wider gap.
6. **Parallel lines stay apart.** Two lines never run closer than 5px to each other for more than 24px, except within 26px of a shared end.
7. **At most 2 crossings per drawn line, counted after bundling.** A drawn line is counted where it arrives: a bus is one line however many pieces draw it. Lines run on a grid, so every crossing is at a right angle.
14. **No braids.** Lines of different bundles may run side by side within one channel for at most 200px per drawn line, summed over every pair, away from their ends. Lines that run that far together belong on one trunk.

The lines that leave one edge of a box and the lines that reach it share that edge's slots, so a line arriving at a box's bottom never lands on a line leaving it there. A line that passes a row never takes the x of a line passing the row next to it, since the two would meet in the gap between the rows and read as one. A line's stub, or its drop, keeps clear of the chains passing the row next to its box edge for the same reason.

Each trunk runs down the chain of one of its lines, its lead. A departure trunk takes the chain of its deepest line nearest the box. An arrival trunk takes the chain of the line that joins it first. The bus's stub or drop stands right over that chain, so the trunk leaves or enters its box without a bend. Only one departure track may meet an arrival trunk, at the trunk's top. Any other line that leaves a departure trunk for that arrival trunk steps down off its departure track onto a short track of its own, which ends on the trunk. That step stands between the two trunks and never past the departure trunk, where its track would hook back. It takes the first x no passing line and no other step uses, two lanes or more off the arrival trunk, then one lane off. Where the trunks stand too close for that, it stands halfway between them. A line that rides its departure trunk into its last gap steps down onto its arrival track at an x that no other step and no passing line uses. It steps down where the trunk ends when it can, and above its own end when the trunk runs on below. Where every x from there to its end is taken, it takes the nearest free x past its end or behind the trunk, up to 32 lanes out. Only when none of those is free does it step where it would first have, on a line already there. A step and a short track also keep clear of the stubs of the boxes above their gap, with shared buses drawn or not. A step keeps clear of a line of its own trunk that drops to its end in that gap, when its arrival track also carries lines from other places. A line that drops from its box straight onto an arrival trunk's top holds that top, so a departure track bound for the trunk steps down onto a short track of its own instead. Each of these keeps a reader on the trunk from turning onto ink that leads to places the trunk's lines never reach (rule 18). The last three came with the wide drawings, where boxes stand in line more often and their stubs met other lines' steps. Without them Orca's desktop main process drew 22 phantom pairs and `src/` drew 2.

Two modules on the overview that depend on each other directly are joined by one line with a head at each end, drawn the way the eye reads, instead of two lines of which one would climb. Its tooltip names both directions and it stands for both relations.

## Legibility

8. **Labels are whole.** A chip is never cut: it is as wide as its label up to 220px, and a longer label wraps onto more lines, so the chip stays inside the edge it sits on and inside the canvas. A name wraps to two lines and widens its box. It is cut only past the hard width (280px for a module box, 220px for a unit box), and then the tooltip carries the full name. No label is wider than its box.
9. **Nothing overlaps.** No two boxes or chips overlap, and no line passes through a box it does not join.
10. **A port sits on the side its lines flow from.** On a unit's frame, a contract the unit provides and a caller from outside sit on the top edge. What the unit uses sits on the bottom edge, even a contract it also provides. While the view is layered, the frame's top and bottom take part as two extra nodes, so a unit that meets a port on top rises toward it and one that uses a port below sinks toward it. A filled chip is a contract the unit provides and an outlined chip is one it uses. A module outside that meets several boxes with no contract would send a line from its chip to each of them, across the page. So the renderer also draws such a view with one dashed chip per box and edge for the modules outside that meet that box, named while the names fit 24 characters and counted as `+N` past that, with every name in its tooltip. Each box then takes one line from its chip. choose keeps that drawing only where it crosses no more than the least of the others and reads better, and the focus views of a gathered view gather their box's chips the same way. On the fixtures it cut the weighed sum over the views both drawings hold from 9812 to 8116 and placement from 326 to 252. Five views are no longer dense, so their 30 focus views are gone.
11. **A box's colour names it, a line wears the colour of the box it leaves, and orange marks a bypass.** Each unit drawn as a box takes one of six colours from a fixed palette (`hues.go`): blue, teal, magenta, purple, cyan and orchid. The box shows it as a 4px accent bar down its left edge and a border of the same colour mixed 80% with the box fill. A contract drawn as a box, because no module in the view provides it, takes no colour. Two units are joined when some view draws a line between their boxes, whether the line runs through a contract's chip or not. The colours are chosen once, over every view's joins together, so a unit wears one colour in every view that draws it. The unit whose joined units already hold the most colours is coloured first, then the one joined to the most, then by ID, so the same state always gives the same colours. Each takes the colour fewest of its joined units hold, and among those the colour its siblings use least. Enforced: across the fixtures no two boxes a drawn line joins share a colour, 0 of 1167 pairs. A unit joined to more than six others could still share one. A line is drawn in the colour of the box it leaves, and so are its head, its label and the dots on its ink. A line that leaves only a frame's chip takes the colour of the box it reaches. Ink whose lines leave boxes of different colours, such as an arrival trunk several places share, is drawn in a neutral grey, and so is a dot where such ink meets. So a reader follows one box's lines by their colour until they merge. A view that draws a lead (see Lead, zones and dress) is the other exception: every line but the lead rests in that grey, its heads, labels and dots too, and a pointed-at box still lights its lines in its colour. The one exception besides is a direct dependency that skips the contract boundary the overview shows, the overview's main architecture warning. It is drawn in a reserved orange whatever box it leaves, with an open head, at the 1.5px of any other line: drawn 2.6px, a view where most lines skip the boundary read as one orange web, and three blind judges preferred the thin line on 3 of the 4 overviews it changes and on none the thick one, and so are its dots and its label. No palette colour is orange, ochre or green, since a reader with protanopia or deuteranopia would see those as the warning. The kind is in the arrowhead and the weight. A use through a contract ends in a filled head. A direct dependency ends in an open head. A unit that provides a contract is drawn 2px thick and ends in a hollow head. A line between two modules that use each other has an open head at each end. Every colour, the grey and the orange stand at least 3:1 against the page and the box fill, in the light theme and the dark one, and so do the climbing tint (rule 13) and the border mix. The palette's colours and the grey stand at least 25 apart in CIELAB. Every one of them stands at least 30 from the orange, for normal vision and under a full protanopia or deuteranopia (Machado et al. 2009). Tests hold all three. The colour never stands alone. The open head says the same thing as the orange, a box's name says what its colour does, and where a line runs says which box it leaves. A line a pstack reader found (판독) starts with a hollow purple dot. A line a human stated (확인) starts with a filled green dot. A line with no dot was extracted from the code (추출). The dot's tooltip says what the word means. 판독 means a reader read the relation, ABBD checks on every sync that the quoted code still exists, and no human has confirmed it.
12. **Unwired contracts are grouped.** A contract that no inside unit is recorded as meeting is not spread along the frame. It is listed below the drawing's text panel as a chip group, with a shared first word shown once (`abbd`: diff, evidence, ...).
24. **A line that passes over another breaks the one beneath.** Where a vertical line crosses a horizontal one, the horizontal line is cut for 4px on each side of the vertical one. That reaches at least 2px past the widest stroke, the 3.2px lead. The cut is a gap with no arc, so it reads as one line passing over the other, and a dot reads as a join. A dot joins only ink of its own kind (rule 17), so the crossing is left whole only where a dot of the kind both lines share sits on it. The horizontal line is always the one cut, whatever order the lines are drawn in, so the same state draws the same gaps. A crossing within 6px of a turn of either line is not cut, since there it reads as one line ending on the other. A crossing within 8px of the end of the horizontal line is not cut either, since the cut would leave a stub under 4px. Nor is a crossing where the cut would also cut the horizontal line's own vertical ink. Two crossings on one stretch less than 12px apart share one cut, so no sliver under 4px is left between them. The cut is an SVG mask on the horizontal line's path (`marks.go`). The mask's id hashes only that line and its holes on the canvas, so a change to one line renames no other line's mask. Its path keeps its points, so the checker's ink graph still reads the crossing as a crossing. Enforced on the rendered SVG. Every such crossing has a hole through the whole width of the stroke beneath, every hole sits on a crossing, and no stretch of ink under 4px is left beside a hole. The fixtures draw 1114 holes at 1268 crossings of two strokes. That is more than rule 7's 313 crossings, because rule 7 leaves out crossings near a line's end and between pieces of one bus, and a reader sees both.
25. **A line says what crosses it.** A stored relation may carry a phrase, a reader's few words for what crosses it, such as a route, a message or a query (`HTTP /api/v1`, `schema fetch`, `Cypher`). The phrase is a note beside the edge's claims, with its own writer, and never a claim (`docs/identity-and-precedence.md`). It may also say how the coupling arises, its `via`, which is a call, data, a convention, a config, an import, a trait, a callback, a macro or a build feature. A line prefers the phrase. A line whose relations all carry one phrase says it. Any other line where a relation carries a phrase says the phrase the most relations carry, the first by name among equals. When at least half its relations carry that phrase it adds 등, as in `quote check 등`. When fewer do it keeps only the phrase's first name, so a comma list never reads as several of the rest, and adds 외 and how many relations do not carry it, as in `click.style 외 32` on a line of 40, so a phrase that names a few relations of many never passes for the line. A path that stands for several lines, as a bus does, counts lines instead, a line carrying a phrase when any of its relations does, so the lines that carry the phrase and N add up to the bus's `×N`. The drop that shows an arrival bus's count speaks for every line the count counts, those the bus's other drops draw included. A relation that merged requests share counts once. A line with no phrase whose relations all name one `via` carries that word, in Korean (호출, 데이터, 관례, 설정, 임포트, 트레이트, 콜백, 매크로, 빌드 기능). A line with none of these carries no word. The tooltip of every line lists each phrase its relations carry, each with whose words it is and how many of the line's relations carry it, as in `charge post (판독) 2/10`, so a phrase that names one relation of ten does not pass for the line. A reader's phrase reads 판독 even on a line the script read. A bare 등 was the rule before this one. On the held-out runs of `eval/skill-polish` and the zero-base runs of click, express and hyperfine, 363 lines named a phrase fewer than half their relations carry, 151 of them labelled, such as `diff --check 등` for 1 of 40 relations, picked only by name. Dropping such a phrase for the via word, the strict share threshold, cut the overviews' phrase labels from 62 to 15, the outcome a blind judge rejected below. The count keeps them at 68 and misstates none. Before a bus counted lines, `외` counted relations while `×` counted lines, so `git query 외 23` stood beside `×9` on this repository's overview, and a relation that two merged requests carried was counted twice, as on a focus line of 17 relations of which 12 were distinct. The word is set in 11px text of the line's colour (rule 11). A phrase is set in italic and a via word upright, so a reader tells the reader's words from how the coupling arises. It is always set upright and horizontal, never turned, since a turned 10px Hangul word does not read at 1x. It sits above or below a horizontal stretch of the line, 3px off it, or beside a vertical stretch, 4px off it. Horizontal stretches are tried first, nearest where the line leaves first. It keeps 10px from the stretch's ends, where a turn stands. It keeps 2px from every box, chip, the frame, count, dot, origin mark, arrowhead, other label and other line's stroke, and it stays on the canvas. A line parallel to its stretch keeps 8px off it, more than twice the 3px it stands off its own line, so a word never floats between two parallel lines where either could own it. The area it keeps clear covers its glyphs to the half pixel, since a word of odd width is centred on a whole pixel. A bus whose lines all say one word carries it once, anywhere along the bus. Otherwise a line is labelled only on ink that is its own, such as the drop into its box, since a word on a shared trunk would name lines it does not stand for. A word is at most 170px wide, which holds a phrase of 24 lower-case letters, or about 21 with 등. A phrase wider than that keeps the names before its commas that fit, with 등, so `COMP_WORDS, COMP_CWORD` reads `COMP_WORDS 등`. A comma inside brackets, as in `f(a, b)`, does not split it. When even its first name does not fit, the next phrase by count speaks, but only one at least half the relations carry, so a phrase of 1 in 10 never speaks for a line whose phrase of 9 in 10 is too wide. A line with no phrase that fits falls back to the via word its relations share, and with none keeps the phrases in the tooltip only, as does a line with no stretch that holds its word. Before this, click's zero-base overview labelled the bus into its process environment `설정` though all three of its relations carry phrases: no phrase was lost where the lines merge, the first by name was too wide and the via word spoke. `TestLabelAudit` checks the label each line draws against the lines it speaks for and its bus's `×N` over every view of the fixtures, this repository's own `.abbd` and any root in `ABBD_LABEL_ROOTS`. It fails on a label that says 등 for a phrase fewer than half carry, gives a wrong 외 N or a comma list before 외, names a phrase alone that not all carry, shows a via word while a relation carries a phrase, or whose 외 N and carrying lines do not add up to the `×N` beside it, and on a line that holds a relation twice. A phrase is at most 24 characters and 4 words, and it is drawn only while the code its note cites is as quoted and a claim shows on the edge. Enforced on the rendered SVG. Every label is upright, on the canvas, beside a stretch of its own line, and 2px off every mark and line. The fixtures hold no phrase. The lines with a word and no label have no stretch that holds it, which a longer phrase makes more likely. The module pages of this repository go from 31 to 46 paths labelled with a phrase, and from 104 to 99 labels in all, since a phrase is longer than a via word and finds room less often. Falling back to the via word when the phrase is too wide adds 2 via-word labels to this repository's module pages 3 to storefront's overview and 2 to its module pages, and changes no label in gin, httpie or the fixtures. The fixtures hold no phrase, so their drawings do not change.

## Lead, zones and dress

A view reads first by its lead, its bands and its filled box, the way a diagram an engineer polished by hand does (`lead.go`, `zone.go`, `dress.go`). None of them adds a line or moves a box, so every rule above measures the same ink with or without them.

- **Lead.** One way through the view, drawn 3.2px in the colour of the box it starts from, its lines numbered from 1 in a badge. It follows a stored flow where the state holds one: its steps in order from the first the view shows, a step on a box already on the lead adding nothing, each new box joined by the line from the box on the lead that ran a step last and uses it, or by its own line to the step before's box. With no flow stored, it starts at the one box no other box in the view uses and that uses others, and follows the line that stands for strictly the most relations, box by box, until two lines tie. A view where either reading gives fewer than two hops draws no lead. Every other line rests thin and grey (rule 11). The badge sits halfway along its line where it keeps off every box, label, count and other badge, else at the nearest twentieth that does, else up to 6px to one side.
- **Zones.** A tinted band with a small-caps title behind the boxes of one grouping the state shows: a stored stack's layers, numbered from the top, else the boxes whose code sits in one directory, two at least and not every box, plus the contracts no module in the repository provides. A band is drawn only where its padded area holds no other box, frame chip or band, so it never asks the layout for room. Its title takes the corner above or below that the fewest lines, labels and counts cross.
- **Dress.** The lead's entry is filled with its colour, or, in a view with no lead, a hub: a box that at least four lines and half again as many as any other box touch. Every box carries a last line in small capitals, its kind and its role (진입점, 허브, 외부), where its chips leave room. A line of 30px or more whose relations all arise by convention, import, trait, macro or build feature is dotted; a shorter one stays solid, since a dotted stub under other lines leaves the pointer only its gaps.

The setup skill does not yet ask readers to store flows, so most held-out runs get an inferred lead or none.

## Flow

13. **Lines read down and right.** The checker takes every line where it arrives at a box or a chip. The line runs forward when its end lies below its start, or level with it and to the right. A line that provides a contract reads from the contract to the unit that meets it, so it counts the other way round. A line that runs back, up or left, must be dashed, and the checker expects 0 back lines drawn solid. At most one line, or 20% of the arriving lines if that is more, may run back. The count says how many lines climb, not how far. A climb across the whole view costs a reader more than one across a row, so the metrics table (`ABBD_METRICS`) also records the dashed ink in pixels. In Orca's mobile app it is 37% of all ink, and in desktop main 31%. The dash is thin and drawn in a lighter tint of its own colour, 70% of it mixed with the page and still at least 3:1 against the page, and its arrowhead keeps the full colour. A dot that only climbing lines meet at takes the same tint. In Orca's cyclic insides the climbing lines are about a third of all ink, and at full strength a dash pattern pulls the eye harder than a solid line.
15. **Lines take the short way.** No line runs more than 240px longer than the shortest grid path between its ends. A line that passes rows runs down its chain (see below). A line to a frame chip whose chain lies more than 160px off the way between its ends passes the rows on its own instead, since the chips are set out after the layout, and its chain keeps no room. A seated drawing sets the chips in the layout, so each stands over its chain (Chips seated in the layout). A line that passes rows on its own keeps the x it passed the row above at wherever the row lets it, so it turns only where a box stands in its way, steps aside toward its end when it must, and reaches across to its end in the last gap. A line with no chain takes a lane in the space between two boxes, at least 13px from any chain, or passes beside the row straight down where it is headed, a lane outward from any line already there.

The layout keeps rule 13 by layering what uses what: a unit sits above everything it uses, and a cycle's edges are reversed for the layering only (Eades, Lin and Smyth's greedy order), so few lines climb. It is a heuristic, not the fewest. A local search that moved one place at a time to where fewer pairs point back was measured and dropped. It cut the crossings from 342 to 301 across the fixtures, but the drawn climbing lines went from 87 to 92, the dashed ink rose, and three views gained phantom pairs. Fewer reversed pairs in the order do not mean fewer dashed lines on the page, because a reversed pair's lines then bundle differently. The numbers are in `eval/render-r6/`.

The rows are then laid out as a proper layered graph, the way Sugiyama, dot and ELK do (`layered.go`). The data shape is rows of items, where an item is a box or a dummy. Each pair of places more than one row apart gets a chain: one dummy in every row between them, as wide as the lanes its lines need. A frame's top and bottom take part as a row above the first and a row below the last.

- **Ordering.** Each row is sorted by the weighted mean position of its neighbours in the row above, then below, and adjacent items swap while that crosses less. The order with the fewest crossings over all adjacent rows, dummies included, is kept. A box joined to nothing in the rows next to it stands last in its row, so it never pushes aside the lines that pass it. A layer too wide for the budget wraps into rows, and a person stacks those rows by where each box's lines go. The boxes with lines to what lies below, or to the frame's bottom, go in the last row, so their lines leave from the bottom row and pass no box of their own layer on the way down. The boxes with no line below fill the rows above, near the lines that reach them. Each group keeps the order the crossing count chose, and the rows are ordered again with the chains the wrapping adds. This holds only where the boxes with a line below fit in the last row. Where they spill into a row above, some of their lines pass a row of their layer anyway, and the layer wraps in the crossing order alone. In Orca's `native/`, `windows-agent-hook` is the one box of twelve with a line down to the frame. It used to stand in the third of four rows, and its line ran down between two boxes of the fourth. ## Tracing

A reader answers "what does X use" by following X's lines. Rules 16 to 23 measure that walk. The checker builds the ink graph of a drawing: straight pieces of one kind, which join where one ends on another or where a dot sits, and which only cross otherwise. A reader follows a vertical piece the way it was drawn and a horizontal piece either way, since a bus's track carries lines both ways. A traced relation is the path through that graph, with the fewest bends, from where its line leaves its start to an arrowhead on its end. The relations the checker expects are the pairs of places the view requests before routing, so a relation the routing drops is lost. A relation whose end has no shape on the drawing is lost too. A chip that stands for several frame ports carries every port's id, and ink to it traces each of their relations. The expected pairs are still the renderer's own requests: a stored relation the view never asks for is not caught by this check.

16. **Few bends on a traced path.** Target: at most 4 per relation, and a median of at most 2 per view. One crossing costs a reader about as much as 38 degrees of turning (Ware et al. 2002). Measured, not yet enforced. A line that spans rows runs straight down its chain, so it turns only where it leaves its start's track and where it reaches its end's. A line that steps from one bus to another turns twice more at the step. A jog is a stretch shorter than 24px between two turns, a sideways step a person drawing by hand would not make. The checker counts the jogs on every traced path, and the hand reference has 1 where the renderer has 3 on this repository's overview, down from 14. With `ABBD_JOGS` set it lists each path that jogs, by its turning points.
17. **A dot at every split and merge.** Where ink of one kind goes three or more ways, the renderer draws a dot in the colour of the lines through it, grey where they differ, and orange on a bypass (rule 11). Where a line crosses onto a trunk that runs on past it, the dot is the only mark that says they join. A dot counts only for ink of its own kind: it neither joins nor marks lines of another. Every split counts on its own, however close it sits to another or to a box. Enforced: 0 points without a dot.
18. **No phantom paths.** The ink joins two places only when a relation does. An arrival bus is shared only by lines from exactly the same places, or, on a shared bus, by places that each reach every box it feeds. Only one departure track meets an arrival trunk, at its top, and every other line steps between buses where no reader can follow it the wrong way (rule 4). Two-headed lines are drawn apart where that keeps rules 13 and 15 (rule 4). On the held-out gin and httpie overviews that took the phantom pairs from 12 and 7 to 0. Measured: every view's phantom pairs are in the metrics table, 69 across the fixtures, down from 191. pstack's overview holds 52 of them. There two modules that use each other are joined by one line that reads both ways. Of the other 17, 14 are in pstack's insides, 2 in Orca's and 1 in this repository's `internal/store`. The 205 focus views hold none, since a twin keeps every line one way (Focus views).
19. **Few crossings on a traced path.** Target: at most 3 per relation, and a median of at most 1. Measured, not yet enforced. The rows are ordered on whole paths, chains included. Splitting buses for rule 18 still adds lines, and so crossings, in the densest views.
20. **Long lines get their own lanes.** Every line that passes a row has a dummy there, a slot of its own in the row's order, instead of a corridor beside the row. The beside share measures how much ink runs alongside a row of boxes, with a target under 15%. It counts a straight chain through a row as much as a corridor, so it did not fall with the dummies: 0.088 to 0.111 on this repository's overview, and 0.163 to 0.119 on pstack's.
21. **Boxes keep their size.** The tallest box is at most 1.5 times the median box's height. On the overview a chip stands for the contracts one drawn line carries. It is named when it is one contract and counted (`계약 N개`) when it is more, with the names in its tooltip. The contracts no line in the view reaches fold into one `+N 계약` chip. A box may be wide so the lines below it drop straight. Enforced.
22. **A count belongs to one line.** Each `×N` sits within 10px of the stretch of ink it counts, at least 5px closer to it than to any other stretch, and at least 5px closer to its own line's ink than to any other line's, so a count drawn across another line does not pass for that line's. A gap that holds a bus's stub or drop keeps 16px between the box and the nearest track, so the count fits beside it. A count never sits on a box or on a frame's chip. Measured: 27 counts across the fixtures' views fail it, 4 of them nearer another line than their own.
23. **Every view has a title and a key.** Target for a later round.

`eval/render-r1/reference-self.svg` is this repository's overview laid out by hand, the way a person would in draw.io, with the same boxes and relations. `TestReferenceRanksFirst` fails when a measure rates the renderer above it, which would mean the measure counts the wrong thing. That is how rule 21 came to bound height and not area: the hand-laid CLI box is wide so its lines drop straight.

## Drawing criteria

The user set out how a drawing should stand and turn, in six areas: where modules stand, how often a line may turn, how turns and bundles go with relations, where a module that many use stands, where a module that only uses or is only used stands, and where a frame's chip stands. The criteria below make that draft precise. Each one is numbered, measured on the rendered SVG, and named in `abbd lint`'s report (`internal/screen/lint.go`). Where a criterion restates a rule above, it names the rule and adds only what the rule leaves out.

A hard criterion must hold. A repository records the hard breaches its drawings already have in `.abbd/lint-debt.yaml`, by view and criterion, as debt. `abbd lint` exits 1 on a hard breach past its view's debt, and marks each breach in its JSON with `debt` true or false. A target criterion is minimized. Each breach is listed. B1 and B2 add up to the excess turns, the measure to lower, and the placement criteria to the placement debt. The same file sets the ceilings of these totals (What a change is weighed by). Each fixture under `internal/screen/testdata` keeps such a file too, and `TestLintFixtures` holds each fixture to it with the same gate `abbd lint` uses.

The terms are these.

- **Row.** A band of boxes whose heights overlap, counted from 0 at the top. The layout's layer is not in the SVG, so the checker reads rows. A layer that wraps (rule 3) is several rows. A frame's top chips stand above row 0 and its bottom chips below the last row.
- **Column.** Two shapes stand in one column when their x spans overlap.
- **Line.** A traced relation (Tracing), from the shape it leaves to the shape it reaches, along the way with the fewest turns. Its turns are rule 16's bends.
- **Obstacle.** A box or chip, other than the line's two ends and what stands on them, that blocks every way with the line's base turns. Within a column the base way is one straight drop between the two facing edges, anywhere across the span the two ends share. Between columns it is a corner of two turns. It runs down from anywhere along the upper end's edge, across at some height, and down onto anywhere along the lower end's edge. The checker tries every height between the edges on a 4px step and keeps 1px clear of every shape. When no base way fits, the shapes that stand in the band between the facing edges, across the span the base way may use, are the obstacles. When no shape stands there, the reason is that the rows leave no room.
- **Hub.** A box that 3 or more places in its view use, boxes and chips together. Across the 274 views of the fixtures, 604 used boxes have 1 user, 114 have 2 and 189 have 3 or more, and in 228 views the median box has fewer than 3 users. A fixed count keeps a box a hub whatever else its view holds. Of the 303 boxes with 2 users or more, 51 break H1. Of the 189 with 3 or more, 15 do.
- **Source and sink.** A source is a box that uses another box and that no box uses. A sink is a box that boxes use and that uses no box. Lines to the frame's chips do not count, since rule 10 places those.

### Placement

- **P1. A user stands above what it uses.** Target. For each relation between two boxes, the user's row is lower in number than the used box's. A relation whose user stands in the same row or below is a breach, with both boxes. It measures how many rows the user stands short of standing above, 1 in the same row and 2 one row below, allowed 0. Rule 13 bounds how many lines may climb, and O3 says which may. P1 lists every one, but for two boxes joined by one line with a head at each end (a mutual wire, which the overview draws for two modules that depend on each other directly). That line reads both ways, so no row order holds both of their relations, and the pair stands well in one row or in rows next to each other. Counted as two relations, a pair stacked a row apart broke P1 once and a pair in one row twice, so P1 paid a row of height for a direction the line does not have. A pair that stands further apart is one breach, with how many rows it stands past rows next to each other, so P1 still asks it to stand closer. The overview's folding tactic leaves out of its ranking every pair of modules that use each other, also those joined through contracts by two one-headed lines. It need not match P1: such a pair drawn in one row breaks P1 for each line, and the chooser passes over a folded drawing that stands more boxes off what they join than the plain one.
- **P2. Boxes used by exactly the same places stand in one row.** Target. Boxes whose sets of users are equal and not empty form a group. A group that stands in more than one row is a breach, allowed 1 row. This is the placement rule 4 counts on when it gives such boxes one arrival bus that splits in the gap above them. The draft said boxes joined to the same partner. In a dense view nearly every box shares a partner with another, so the criterion takes rule 4's reading. A focus view's twins are left out.
- **F1. A frame chip stands over or under the boxes its lines reach.** Target. The chip's x span meets the span from the left edge of the leftmost of those boxes to the right edge of the rightmost. A breach gives the gap in pixels, allowed 0. The draft said the box its line reaches. A chip whose lines reach several boxes cannot stand over each, so it stands over the span they cover. Rule 10 still chooses the edge. A chip on a module's edge on the overview stands on its box and is not held.

### Bends

- **B1. A line turns no more than its ends allow.** Target. The allowance follows from where the line's two ends stand and from the shapes around them, never from the drawn route. A route that leaves on a side, or comes back past its start, buys no turns by it. The checker judges the line from the upper end down.
  - Within one column, when the straight drop between the two ends is clear, the line may turn 0 times.
  - Within one column, when every straight drop is blocked, it may turn 2 times. That is how rule 4's exit bundle runs, out of the box, aside past the obstacle and down. The breach names the obstacle.
  - Between columns, when a corner fits, it may turn 2 times. A line leaves its box's bottom edge and reaches the top edge of what it uses (rules 4 and 10), so between columns it cannot turn fewer than twice. The draft allowed 1, and Staircases first reads those two as a corner and no step.
  - Between columns, when every corner is blocked, it may turn 4 times, and the breach names the obstacle.
  - Between two ends that share a row, it may turn 4 times. No line in the fixtures has such ends.

  Each line that turns more is a breach, with its turns, its allowance, the turns in excess, and the obstacle or the reason. Measured over the fixtures, 1145 lines break B1. 728 of them have no step, since they turn twice where their ends allow 0. Orca's `src/` has such a spot at the `native/` chip, whose line to desktop main turns twice in a clear column. Only 3 lines stand in a column whose drop and corners are all blocked, so allowing them 2 where 4 is the fewest they can turn adds 6 excess turns.
- **B2. No jogs.** Target. A jog is a stretch shorter than 24px between two turns (rule 16). Each line with one is a breach, allowed 0, with its turning points.
- **B3. A line never rides past its turn and comes back.** Target. A line turns back where one stretch runs one way, the next crosses, and the one after runs back the other way, such as a line that runs right along a bus past the drop it needs, steps down a lane and runs back left to it. A hand-drawn line turns where it has to. Each line that turns back is a breach, allowed 0, with how many times and how far it rode past, the shorter of the two stretches that run against each other. Lines that share one turn-back, as the lines of one trunk do, count it once, on the first line traced along it. A back line, one that runs up to its end or leftward along its row, climbs out through a gutter and turns back by its nature, so rule 13 counts it and B3 leaves it out.
- **B4. A line never runs as a doubled track beside itself.** Target. Two stretches of one traced line, or of two subpaths of one drawn bundle, that run the same way in parallel, apart but within 12px, for 24px or more read as one line drawn twice. Two stretches that run against each other are a turn-back, which B3 counts, and a pair of a bundle's subpaths along a pair a traced line already counts is that line's. Each line or bundle with such a pair is a breach, allowed 0, with how many pairs it has.

  The **detours** of a drawing are the turn-backs B3 counts plus the pairs B4 counts. They have a ceiling of their own (What a change is weighed by). Most turn-backs on the fixtures rode around a row on a gutter rather than along one bus, and most of those along a bus came from where a departure trunk that runs on below steps down onto an arrival track: every pair of buses stepped down above its lead line's end, so its other lines rode past their own drops and came back. A pair now steps down on the trunk itself when every place on its arrival bus already reaches every place the trunk leads to below, so the join adds no phantom pair. Otherwise it steps down above its end, or at the clear x nearest it on the trunk's side, and a line whose end lies under the trunk where another pair steps down on it runs straight on down. On the 244 views of the fixtures that takes the detours from 159 to 137 and the weighed sum from 8086 to 7713 (`eval/lint/decisions.tsv` rows 67 to 75). No line runs beside itself. The turn-backs left ride around rows whose gaps between boxes are full, which is placement, not routing.

The **excess turns** of a drawing are each line's turns past its B1 allowance, summed over the lines, plus every jog. They are the measure a change to the renderer lowers. They are not the steps of Staircases first. A step is a turn past a line's second, whatever its ends allow, so a line that turns twice in a clear column has no step and 2 excess turns, and a line between columns that turns 4 times around an obstacle has 2 steps and no excess turn. `abbd lint` still reports the steps, beside the excess turns.

### Bends and relations

- **J1. A bundle splits only next to where it goes.** Hard. A split is a dot where the lines of its kind arrive as one strand, from one side, and leave it on two sides or more, toward two places or more. It stands in a row, or in the gap above or below a row, where one of those places stands. A frame's chips count as a row. Merges are not held, since rule 4 merges lines from different places midway on purpose. A dot where lines arrive from two sides is a merge, or a merge and a split at once, and is not held either. The draft said a bundle parts only at its ends, which would hold merges too, so the existing rule wins there. Measured, the fixtures have 847 dots whose lines go to two places or more. 49 of them carry lines from two places or more. 789 are splits by the strand reading, and all 789 stand next to a row they split toward, so the tighter reading adds no breach.
- **J2. Every split and merge carries a dot.** Hard. This is rule 17. A breach gives the point.
- **J3. The ink joins no two places that no relation joins.** Hard. This is rule 18 held at zero, as the user's draft asks, where rule 18 only measured. A breach gives the two places and the way between them. pstack's overview carries its 52 phantom pairs as debt.

### Hubs

- **H1. A hub stands below the middle of its users.** Target. The hub's centre x lies between the leftmost and the rightmost centre x of the places that use it, within 1px. A breach gives how far outside it stands. That it stands below them is P1's.
- **H2. The lines into a hub gather into one trunk.** Target. The forward strokes of one kind that end on a hub belong to one bundle, one drawn net. A breach gives the number of bundles, allowed 1. Rule 4 bundles a kind's lines per edge. H2 holds the hub to one bundle across its edges. The dashed lines that climb to a hub are left out, since rule 13 bounds them and O3 says which may climb. Counted with them, 30 of H2's 36 breaches in the fixtures came from cycles. Without them it has 6.

### One-way boxes

- **O1. A box that only uses stands in the top rows.** Target. Every box in a row above a source, among the boxes that join another box, is a source too. So a source in the second row of a wrapped top layer holds, and a source below a box that is used breaks it. A source whose only frame lines run to bottom chips is left to rule 10, which pulls it down.
- **O2. A box that is only used stands in the bottom rows.** Target. Every box in a row below a sink, among the boxes that join another box, is a sink too. A sink whose only frame lines run to top chips is left to rule 10, which lifts it.
- **O3. A line climbs only to close a cycle.** Hard. A relation whose user stands in a row below what it uses is a breach, unless what it uses reaches the user back through the view's relations between boxes. Rule 13 bounds how many lines climb and draws them dashed. O3 says which may.

### The rules

- **R. The rules hold.** Hard. Rules 1 to 15 as `legible.go` checks them, rule 2 as the trace checks it (no relation without ink), and rule 21. Each broken rule is one breach. The fixtures' debt is the views `fixtures_test.go` lists.

### One screen

- **S. The drawing fits one screen.** Target. The screen is a browser viewport of 1600x1000 CSS pixels at 100% zoom. There the drawing box is 1335px wide, so a drawing fits at most 1320px wide. Its height is what the page leaves under the header and the drawing's heading, 118px down, with 22px kept below: 860px, less what the page sets between the heading and the drawing. The overview loses 37px for each kind of question it lists (flows, stacks, tables) and 29px for each question, plus 4px, so three questions of three kinds leave it 658px. A module's page loses 22px to its one-line note and a focus view's page 45px to its two-line note. These were measured on the page at that size. A question that wraps, a smaller window, a larger zoom or a display scaled past 100% (a 1920px screen at 125% is a 1536px viewport) leaves less, so S holds the common desktop case, not every screen. A drawing past that makes the reader scroll to see it whole, and a hand-drawn diagram never asks that. Each view past it is one breach, with its size and how far past it runs. The **overflow** is the number of such views. It has a ceiling of its own, held like the weighed sum. When S was set, 7 of the fixtures' 244 views broke it (pstack's overview and 6 of Orca's module pages), and 2 of the 158 views of six held-out runs (the overviews of httpie and hyperfine). The overview is drawn with its plain ranking unless a folded or entering one (`overviewTactics`) fits where the plain one does not, or has fewer hard breaches, and stands no more boxes off what they join. Whether a drawing fits is weighed right after its hard breaches, and how far past it runs only after what lint weighs. A new ranking moves every box's centre and so every focus view seated by them, and taking one only to save turns let one new relation between two modules redraw ripgrep's overview at 1234x740 in place of the plain 1308x652 that fits.

### Levels

- **L. Each full view stands at one level.** Report only. The overview and every module's page have a level, and a feature's page does not. The overview draws 4 to 12 modules, the parts an engineer names when explaining the system, and a contract no drawn module provides does not count. A nested module's page draws at least 2 boxes, a top-level module's page 0 or at least 2, and any page at most 16 (rule 1). A view of 4 or more boxes draws at most 2 lines a box, past the lines into a hub. Only lines between two of the view's boxes count, once whichever way they run, never those to a frame's chips or to a loose contract. A hub is a box at least 3 boxes and half of the others use, such as shared types, listed as `hubs`, at most the 2 most used, and none when as many boxes qualify as do not. The first `abbd lint --record` of a repository refuses while a view with hard breaches has a level line, unless `--keep-level VIEW=REASON` keeps it, which writes the reason under `levels` in the debt file. `abbd lint` prints a `level` line for each view that misses, with what to change in the units, and `--json` lists every full view under `levels`. It never fails lint and is never debt, since the renderer cannot fix it: the reader's choice of units does (abbd-setup, step 1).

### What a change is weighed by

`abbd lint` gives each view, and all of them, these totals. They are the hard and target breaches, the breaches of each criterion, the excess turns, the placement debt, the crossings, the weighed sum, and the path measures of the trace. The **placement debt** is the breaches of P1, P2, H1, H2, O1, O2 and F1 added up. The **weighed sum** is the crossings plus 4 for each excess turn (`stepCrossings`), so a turn saved may cost at most 4 crossings. A change to the renderer is held by this gate, and `abbd lint` holds a repository to it.

1. No view has more hard breaches of a criterion than its debt records.
2. The weighed sum stays at or under its ceiling, and so does the overflow, the views that break S.
3. The placement debt stays at or under its ceiling plus 2% of it, rounded down. A change that saves turns may move a few boxes, and the next kept change starts from the new total.
4. The traced bends and the paths that turn more than twice are tie-breakers. Between two changes that weigh the same, the one with fewer wins. Neither has a ceiling.
5. The phantom pairs and the climbing lines have no ceiling of their own. J3 holds the phantoms at their debt, and rule 13 bounds the climbing lines.
6. Any view whose weighed sum rises by more than 8 needs a look by eye, even when the totals fall. `eval/lint/compare.py` lists those views.
7. After each kept change, `abbd lint --record` lowers the debts and the ceilings to what the drawings measure. It never raises a ceiling. A total the gate lets pass its ceiling, as the placement debt may by 2%, keeps the ceiling it had, so the slack cannot ratchet a ceiling up one kept change at a time. Raising a ceiling is an edit to the file that a review sees.
8. The detours (B3, B4) stay at or under their ceiling. A line that rides past its turn and comes back, or runs beside itself, is what a person polishing the drawing by hand removes first, so no change may add one, whatever it saves elsewhere.

`abbd lint` checks the first three and the eighth over every view and fails when one breaks. With a VIEW it checks only the first. `TestLintFixtures` checks each fixture against its own `.abbd/lint-debt.yaml`, and fails as well when a debt or a ceiling stands above what the fixture measures, so a kept change always lowers them. ## Flows

A layered view answers "what uses what". A flow answers one question about the order things happen in, such as what `abbd sync` does. It is the numbered figure of the per-module docs agents write: one question, a caption, and steps in execution order, each on the unit whose code runs it, with what the step does, a note (a cache, a TTL, a skip rule), how it fails, and the units it calls.

- **Stored as facts with evidence.** A flow is `.abbd/flows/<key>.md`, written by `abbd flow KEY FILE`. Each step records who wrote it. A reader's step is INFERRED and a human's, with `--source`, is USER_STATED, and the flow is USER_STATED only when a human wrote every step; in a mixed flow the page marks the human's steps. A reader may replace only a human's STALE steps: each current human step must come back as written and in its order, and keeps the human's word. A step that went STALE is kept in the file's `retired` list with the code it was written against. A reader's step that says the same words, in any case or spacing and on any unit, is refused while it cites a file whose code changed under the retired step, however many stores ago that step left the flow. A human's store, with `--source`, is not refused and clears the retired steps it says again. abbd forgets a retired step once its code is back as it was, its unit leaves the state, or every file it cites is gone. A retired step keeps no `calls`. This shows only that the same words do not come back unread on changed code. It cannot show that a reader who rewords a step read the code again. Deleting the flow file, or a hand edit that deletes `retired`, forgets the retired steps. Every step cites the code it rests on, each quote held once in its file. One quote at least lies in code that the step's own unit, or a unit inside it, anchors more closely than any other unit does, or that a contract the step's unit provides anchors so, as a command's handler is the code of the command line that provides it. A quote in a file several units share counts for the unit whose anchor names it best. An anchor with a symbol holds only a quote that names that symbol. The quote's `symbol` is the reader's claim: abbd ranks the quote by it and does not check that the quote lies in that symbol's code. A root anchor of `.` holds only the files no closer anchor names, and a unit the step calls lends it no code. Each step is stamped with the lines around its quotes, so an edit there stales that step alone. A flow stores no unit and no relation. Its steps name stored units, and a call is drawn only where a live stored relation joins the step's unit, or a unit inside it, to the called unit, so a chip never draws an edge the graph lacks. A step whose unit or call the state lost, whose code moved, whose quotes all lie outside its unit's code, or that cites no code, is STALE, and `abbd status --check` fails until the flow is read and stored again.
- **Drawn in HTML.** The figure is a numbered list, not an SVG. The browser wraps every line, so no label is cut. The steps read top to bottom in their order, and the only lines are the arrows from each step to the next: no crossings, no bends. Consecutive steps on one unit share one cell beside them, which groups by the stored unit only. At 560px and below the cell stands above its steps.
- **Linked into the tree.** A step's unit opens its own inside, or else the inside of the nearest unit that holds it. A call opens the same way, and a contract with neither opens the inside of the module that shows its notes. Each flow has a page of its own. The overview lists every flow by its question, its step count and how many of its steps are STALE, and each module's inside lists the flows with steps on the units it holds, by step number.

## Stacks

A flow answers in what order things happen. A stack answers what the layers of a part of the code are, such as the layers of the abbd CLI. It is the layer figure of the per-module docs agents write. It has one question, a caption, and layers from the top down, each a named layer with a one-line role and the stored units it holds.

- **Stored as facts with evidence.** A stack is `.abbd/stacks/<key>.md`, written by `abbd stack KEY FILE`. It keeps a flow's rules for who wrote each part, for a human's word and for retired parts, with a layer's name and role in place of a step's words. A retired layer is forgotten once one of its own units leaves the state. A store warns on a role over 80 characters, as on a step's `does`. A layer holds each unit it names and every unit inside it, and a unit sits in one layer only. So abbd refuses a draft that names a unit in two layers, or names a unit in one layer and a unit that holds it in another, or names both in one layer. A stack has two to eight layers, and its layers name 16 units at most. Every layer cites the code it rests on, each quote held once in its file. One quote at least lies in code that one of its units, or a unit inside one, anchors more closely than any other unit does, or that a contract one of them provides anchors so, by the rule a flow's step follows. Each layer is stamped with the lines around its quotes, so an edit there stales that layer alone. A stack stores no unit and no relation, and it invents no grouping, because a layer is a list of stored unit IDs. A layer whose unit the state lost, whose code moved, or whose quotes all lie outside its units' code is STALE. So is a stored stack that holds a unit twice after the unit moved under another. `abbd status --check` fails until the stack is read and stored again. In a human's stack, the layers such a break names are open to a reader as a STALE layer is. The reader may replace them, and any of them that comes back as written keeps the human's word, so CI does not wait on the human.
- **Breaches.** A breach is a live stored relation by which a unit a lower layer holds uses a unit a higher layer holds. Only `consumes` and `depends_on` are uses. A `provides` is no breach. It runs from a lower unit to a contract an upper layer homes, so the lower layer serves the upper one, which is dependency inversion and not a use. A relation within one layer, one that skips layers downward, and one with an end no layer holds are no breach. abbd derives the breaches from the state each time and never stores them. `abbd stack KEY FILE` says how many it found, `abbd status` lists each with its ends, their layers and the relation's origin, and the page draws each one. A breach never fails the check. It is debt in the code or a layer drawn wrong, and only a design call clears it.
- **Drawn in HTML.** The figure is a list of bands from the top down, not an SVG. Each band shows its number, name and role beside the units it holds, so the browser wraps every line and no label is cut. A band's breaches sit under its units as chips marked ↑, each naming its two ends and the higher layer it reaches. At 560px and below the band's name and role stand above its units.
- **Linked into the tree.** A unit opens its own inside, or else the inside of the nearest unit that holds it, as a flow's step does. Each stack has a page of its own, which marks its STALE layers and its breaches. The overview lists every stack by its question and its layer count, with how many layers are STALE and how many breaches it has. Each module's inside lists the stacks whose layers hold its units, by layer number.

## Tables

A flow answers in what order and a stack answers in what layers. A table answers which part does what to which thing, such as which part of the CLI reads and writes which `.abbd/` file. It is the matrix figure of the per-module docs agents write. It has one question, a caption, a head of columns, and rows. Each row is one stored unit with a short statement in each cell it fills.

- **Stored as facts with evidence.** A table is `.abbd/tables/<key>.md`, written by `abbd table KEY FILE`. It keeps a flow's rules for who wrote each part, for a human's word and for retired parts, with a row's cells in place of a step's words. A human's column head is the human's word, as the question and the caption are. A reader may change only a column whose unit left the state, by dropping its unit or pointing it at another. A retired row's cells may not come back on its changed code under any column, so renaming a column does not make them new. A table has two to 8 columns and two to 16 rows. A column is a short label of 32 characters at most, named once, and it may name the stored unit it stands for. A row names its unit and fills one cell at least. A column the row leaves out is an empty cell. A unit heads one row, and every cell sits under a column the head names. A store warns on a cell over 80 characters. Each row cites the code that shows its cells, each quote held once in its file and one at least in the code of the row's own unit, by the rule a flow's step follows. Each row is stamped with the lines around its quotes, so an edit there stales that row alone. A row whose unit the state lost, whose code moved, or whose quotes all lie outside its unit's code is STALE. So is a stored table whose column names a unit the state lost. `abbd status --check` fails until the table is read and stored again. A table stores no unit and no relation.
- **Cells read against the relations.** A cell under a unit's column says what the row's unit does to that unit, so abbd reads it against the strongest live stored relation from the row's unit, or a unit inside it, to the column's unit or a unit inside it. A cell that says something with no relation under it is unbacked. An empty cell over a relation is unsaid. abbd derives both from the state each time and never stores them. `abbd table KEY FILE` says how many it found, `abbd status` lists each with its row, its ends and the relation's origin, and the page marks each one. Neither fails the check. The graph may lack a coupling a reader can record, or the cell may be read wrong, or the table may miss a use, and only a reader of the code can say which. A cell under a plain column is read against nothing.
- **Drawn in HTML.** The figure is an HTML table, not an SVG. The head names each column, and a column that stands for a unit links to the inside that shows it. Each row's head is its unit, a chip that opens its own inside, or else the inside of the nearest unit that holds it, with the row's quotes folded under it. Every cell wraps. A cell under a unit's column carries the relation's verb as its title. An unbacked cell has a dashed outline, and an unsaid cell shows ◦ with the relation's verb. At 560px and below each row folds to one card, its unit on top and each filled cell under its column's label.
- **Linked into the tree.** Each table has a page of its own, which marks its STALE rows and its unbacked and unsaid cells. The overview lists every table by its question, with its rows and columns, how many rows are STALE and how many cells are unbacked or unsaid. Each module's inside lists the tables whose rows its units head, by row number.

## Pages

Every sync rewrites the blueprint, and `.abbd/` is committed with the code. So the pages a code change rewrites are part of its pull request, and a reviewer reads them. The views are split across pages by their level, so that a change rewrites only the pages of the views that draw it (`site.go`).

- **`index.html` holds only the overview.** It draws the modules and the contracts between them, and lists the flows, stacks and tables by their questions and sizes. Beside each figure it shows only counts: its STALE parts, its breaches, and its unbacked and unsaid cells. It is the one page whose nav lists every module.
- **A unit drawn on the overview has a page, `<ID>.html`,** when it holds units or has a focus view on the overview. Its inside's drawing takes the section's whole width. The module's description and the list of its units sit in a panel right below the drawing, its legend and its picker, side by side where the page is wide enough and one above the other where it is not. The unwired contracts, the flows, stacks and tables the module is in, the inferred couplings with their quotes, and the contracts' entries come after that panel. The page shows its inside first, then its focus view on the overview, then the focus views of its inside. A unit with a focus view and no inside has a page with only that view.
- **Each flow, stack and table has a page of its own.** It marks the figure's STALE parts, breaches and unbacked or unsaid cells, each with why. The overview's list shows only their counts. So a figure going STALE rewrites its page and one line of the overview. A change to a STALE part's reasons or words rewrites only the figure's page, since no count moves.
- **Every other page's nav** links the overview and both indexes. A unit's page lists the modules it sits in, down to its own unit. A figure's page belongs to no module, so its crumb names the figure and its nav lists no module. No page but the overview shows counts or siblings. So a unit that comes or goes rewrites the pages of the views that draw it and the indexes, and the overview's nav only when the unit has a page, never every page.
- **`graph.json` holds the data and no drawing.** It lists the units, every live relation, each module's inside less its drawing, and the figures. A change that only moves boxes or lines rewrites the pages that draw them and leaves `graph.json` as it was.
- **A quote is cited by its file and its words.** The pages and `graph.json` leave out the quote's lines, which an edit above it moves while the quote still says the same. The store and `abbd evidence` keep the lines.
- **A crossing mask is named by its own line** (rule 24), so a change to one line renames no other line's mask.

The levels of abstraction stay as they were. The overview draws every module and every relation that crosses a module's boundary, an inside draws its units, and a focus view one unit and its ring. ## What the overview draws

Every view is deterministic, so the same state renders as identical bytes. Every view, the overview included, draws every live relation whatever its origin. A reader's coupling (판독) carries its hollow dot there too, because sync re-checks its quote on every run. A dead coupling, whose quote is gone, is drawn nowhere. The overview used to leave reader's couplings out, and on Orca (evaluation round 5) that erased every real platform boundary: the phone-to-relay WebSocket, the E2EE handshake, the push gateway and the native helper sockets were all found by readers, mostly on units inside a module.

So a relation from anywhere inside a top-level unit to another top-level unit is drawn on the overview as that unit's own: it crosses the boundary the overview shows. A unit inside a module is never drawn on the overview, and a change that stays inside a module never moves it.

## Grouping levels

A level of the tree is the one the project shows. A merge is stored only where an engineer would draw it: a directory that exists in the repository, a package or workspace, a skill family, a subsystem the project's own docs name, or an abstraction the code itself shows, such as a layer or the implementers of one interface. A merge made to make a view smaller or a dense view easier to draw goes past that, and makes the system harder to understand. The blueprint splits its views into the whole (the overview), a part (a module's inside) and one unit (a focus view), and a click on a box follows that module inside. That is how a crowded or dense level is read. The grouping is stored as units (MOD) and `parent` links, and the renderer never invents one at render time.

- **The extraction or a reader names it.** The extraction script reports the parents the code shows. The supplement step of `abbd-setup` adds only a grouping the project itself shows, as a MOD whose `evidence` quotes the project naming or showing it, and gives each member that part as its `parent`, with `parent_evidence`. `abbd record parent ID PARENT --evidence ...` places a single unit later, and `--source` records a human's statement instead. Such a parent is INFERRED or USER_STATED, and sync keeps it unless the extraction script reports a parent for that unit. A reader's parent lasts only as long as its evidence. A parent that would close a cycle is refused.
- **Sync's directories.** When a crowded level's units were placed by the script or by nobody, `abbd sync` places them in the directories their code lives in, at the shallowest depth that splits them. Inside a module it groups only the units below the module's own directory, the deepest one that holds all its anchors: a group of that directory or one above it would repeat the module, and a unit outside it stays in the module as it is. An anchor counts as a directory, and holds itself, when an anchor lies under it, so a module anchored at `src/core` spans `src/core` and not `src`. It stores each directory as a MOD unit whose anchor is that directory with the symbol `(group)`. It never moves a unit a reader or a human placed. It recomputes them on every sync and reuses IDs by directory.
