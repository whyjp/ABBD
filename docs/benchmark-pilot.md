# 벤치마크 파일럿 (부록 A 첫 칸: pstack vs ABBD)

2026-10-18 · 실행기 `benchmark/run.py` · 과제 `benchmark/tasks.json` · 숨김 테스트 `benchmark/testdata/hidden/`

## 설정

- 두 arm은 같은 모델(`sonnet`), 같은 프롬프트, 같은 작업당 예산 상한($4), 같은 기준 저장소(`samples/code-only`)를 쓴다.
- 작업마다 별도의 headless Claude Code 세션을 띄운다. arm마다 별도 worktree에서 실행한다.
- 세션은 `--setting-sources project`로 사용자 수준 플러그인·훅·설정을 끄고, `--plugin-dir`로 그 arm의 플러그인 하나만 싣는다. 격리는 세션에 보이는 스킬 목록으로 확인했다.
- 과제는 10개이고 누적된다(버그, 인터페이스 확장, 교차 모듈 데이터, 재시도, 동시성, 리팩터링, 인터페이스 변경, 설정, 버그). 각 arm은 자기가 앞선 작업에서 만든 저장소를 이어받는다.
- 채점은 에이전트가 보지 못하는 숨김 테스트로 한다. 매 작업 뒤에 그때까지의 모든 작업을 작업별로 따로 채점한다.
- 측정 도구 검증: 기준 구현 arm(`--arms reference`)에서 숨김 테스트 10개가 모두 자기 패치 전에는 실패하고, 후에는 통과한다. 5회 반복에서도 흔들림이 없었다.

## 이 숫자가 말하는 것과 말하지 않는 것

- **정확도는 천장이다.** 두 arm 모두 10/10이라, 이 과제 묶음으로는 정확도나 회귀 억제의 차이를 가를 수 없다. 과제가 너무 작고 국소적이다. 부록 B의 반증 기준("B 대비 C가 차이를 보이지 않으면 축소 검토")에 따르면, 이 파일럿은 C의 추가 정확도 효과를 아직 보여 주지 못했다.
- **비용은 늘지 않았다.** 턴 루프·verify·sync를 매번 돌고도 ABBD arm의 비용·턴 수·출력 토큰은 pstack arm보다 적거나 같았다. 하지만 arm마다 한 번씩만 돌았고 신뢰구간도 없다. 그래서 이것은 "하네스 오버헤드가 크지 않다"는 가설을 뒷받침할 뿐, 효과로 단정할 수는 없다.
- **같은 것을 쟀는지.** 두 arm은 호스트의 사용자 CLAUDE.md를 공유한다(`--setting-sources`가 CLAUDE.md는 끄지 못한다). pstack 세션이 poteto-mode 진입을 실제로 따랐는지는 확인하지 않았다.

## 첫 시도에서 드러난 제품 결함

처음 실행(커밋 477df1e)의 ABBD arm은 하네스를 쓰지 않았다. 에이전트는 abbd 스킬이 있다는 것을 알았지만 "작은 수정"이라며 턴을 건너뛰었다. 그 결과 receipt는 0건이었고 설계도는 STALE이었다. 그 상태로는 pstack 대 하네스 없음을 재게 되므로 그 arm은 중단했다. 원인은 세션 시작 훅이 안내만 하고 강제하지 않았다는 데 있다. 459fd41에서 진입을 구조로 강제했다.

- SessionStart에서 코드 변경마다 턴을 의무로 명시한다.
- Stop 훅을 두었다. 설계도가 작업 트리와 맞지 않으면 에이전트를 한 번 되돌려 sync까지 끝내게 한다.

pstack arm 결과는 ABBD 코드와 무관하므로 첫 시도의 결과를 그대로 썼다.

## 다음 칸에서 할 것

- 천장을 깨는 과제가 필요하다. 이전 결정과 충돌하는 요청, 외부 소비자가 있는 계약을 건드리는 변경, 여러 턴 전의 불변조건을 깨기 쉬운 리팩터링, 같은 영역을 다시 바꾸는 요청 같은 것이다.
- 반복 실행(최소 3회)으로 분산을 잰다.
- 사용자 본인 저장소에서 돌리고, 사용자의 기존 SSOT를 정답으로 cold-start grounding을 잰다(부록 A).
