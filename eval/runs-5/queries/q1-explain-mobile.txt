  ## Overview

  `mobile/` is an Expo React Native app that is a remote control for an Orca desktop. It runs nothing itself: every worktree list, terminal, chat, diff and file view comes from the desktop's Orca runtime over the same JSON RPC that the CLI and renderer use (`{id, deviceToken, method, params}` in, `{id, ok, result|error}` out). The phone pairs once by scanning an `orca://pair?code=...` QR code the desktop prints. After that it reaches the desktop in one of two ways: a **direct** WebSocket to the desktop's runtime server (LAN or Tailscale), or the **cloud relay** (`wss://<relay>/v1/connect/<relayHostId>`), which only forwards bytes. Both paths run an end-to-end encrypted (E2EE) channel that the desktop terminates, so the relay never sees plaintext. The phone moves between the two at runtime ("direct upgrade" and relay fallback).

  Push notifications do **not** go phone to cloud. The phone gets its native APNs/FCM token and hands it to its desktop with the RPC `notifications.registerPush`. The desktop registers the device with the cloud push gateway (`ORCA_PUSH_GATEWAY_URL`, default `https://push.onorca.dev`), and the gateway pushes an `orca` data block (`hostFingerprint`, `kind: alert|dismiss`, `notificationId`, seq/epoch, `paneKey`, `worktreeId`). The phone and one Swift module read that block. Native work lives in five small Expo modules, all bound by **string name**: gzip/UTF-8 decoding, a WKWebView "web shell" that hosts an over-the-air web build of the app served by the desktop, iOS notification dismissal, an iPad window-controls inset fix, and two-way audio for dictation.

  ## Key Concepts

  - **Pairing offer**: the desktop's `orca://pair?code=<base64url>` URL holds the endpoints, the desktop public key, a device token and optional relay invite. `src/shared/pairing.ts` writes it; `mobile/src/transport/pairing.ts` keeps its own parser "aligned" by hand.
  - **Host**: one paired desktop. The phone stores its descriptor, device token and relay credentials (keychain) and keeps a connection supervisor for each host.
  - **Direct vs relay path**: `DirectRpcClient` dials the desktop's `ws-transport` WebSocket server. `mobile-relay-physical-client` dials the relay, sends `relay-auth` and waits for `relay-hello`. The endpoint supervisor picks and switches between them.
  - **E2EE v2**: the `e2ee_hello` / `e2ee_ready` handshake (shared in `src/shared/paired-e2ee-client-handshake.ts`) plus NaCl box or libsodium framing. The desktop's `src/main/runtime/rpc/e2ee-channel.ts` is the other end, for both paths.
  - **RPC operation**: `defineRpcOperation({name, method, read})` in `mobile/src/transport/rpc-operation`. Methods are named by string (`notifications.registerPush`, `mobileWeb.bundle.range`), and each reply is checked with a zod schema on the phone.
  - **Protocol version**: `MOBILE_PROTOCOL_VERSION = 3` is a hand copy of the desktop's `RUNTIME_PROTOCOL_VERSION`. Capability negotiation then hides features the host lacks.
  - **Mobile web shell**: most screens can run as a web bundle (the Expo web export of `mobile/app`). The desktop build packages it into `out/mobile-web`, the phone downloads it with `mobileWeb.bundle.*` RPC, and it runs inside the native `OrcaMobileWebShellView` with a postMessage bridge.
  - **Push payload**: the gateway's `orca` data block. APNs nests it under `orca`, while FCM sends it flat as strings, so the reader handles both.
