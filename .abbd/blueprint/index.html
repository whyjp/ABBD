Overview

cmd/abbd is the command-line front end of ABBD. It is a single package main that dispatches about a dozen verbs. The verbs read and write the .abbd/ directory, which holds the repository's architecture topology: modules, contracts and the relations between them. The usage text calls the CLI "a lever": it runs the project's registered extraction script, keeps unit IDs stable across runs, checks that every quoted piece of evidence is still in the working tree, records what readers infer and what humans state, and re-renders the blueprint page (.abbd/blueprint/index.html plus graph.json) after every write. By design it never judges or blocks anything. Even diff --check only returns an exit code that a CI job can turn into a PR label.

The package is thin. The real logic lives in internal/ (identity for ID reconciliation, evidence for quote checking, topology for queries and diffs, screen for rendering, store for the on-disk format, gitx for git facts). cmd/abbd does four things: it parses the command line against a declarative command table, applies the CLI-level rules (what a valid record looks like, which origin wins, what to refuse), wires the internal packages together in the right order, and prints the results line by line.

Key Concepts

  • Command table (commands in main.go): each verb lists its allowed flags, how many positional arguments it takes, whether it accepts -- ARGV, and whether it writes. A writing verb triggers publish(), which re-renders the blueprint.
  • Origin: every fact and relation carries one. EXTRACTED comes from the script, INFERRED comes from a reader with evidence, and USER_STATED comes from a human with a --source. When they collide, EXTRACTED beats USER_STATED, and USER_STATED beats INFERRED.
  • Evidence (PATH:LINES:QUOTE): a verbatim excerpt of code. A finding enters the state only if its quote is live in the working tree now. A unit whose name is INFERRED (a "semantic" unit) stays present only while its evidence is live, and a relation that carries evidence goes dead once its quotes are gone.
  • Guesses mode: sync runs identity.KeepGuesses, which keeps the stored INFERRED facts because the script cannot see them. setup runs identity.ReplaceGuesses, where the supplement owns the guesses and anything it no longer says is withdrawn unless a human stated something about it.
  • Fingerprint / state.yaml: a git tree object of the working tree minus .abbd/, recorded at sync time. If it differs from the current tree, the state is STALE.
  • Understanding: pstack how's Overview and Key Concepts text for a top-level module, stored with a digest of that module's code so it can be shown as CURRENT or STALE.

Overview

internal/bootstrap is one pure function, bootstrap.Overlay in internal/bootstrap/overlay.go. abbd setup --supplement FILE calls it to fold the semantic supplement into the output of the project's deterministic extraction script. The supplement is the JSON that pstack's reader swarm writes to .abbd/extractor/supplement.json. The script reports what the code shows mechanically: imports, routes, schemas, signatures. The readers report what you only learn by reading: a module's purpose and responsibility, a table two modules share, a coupling through a callback or a config flag. Overlay combines the two into one extract.Result, and identity.Reconcile turns that result into stored units with IDs.

Overlay is as much a gatekeeper as a merger. Its rule is that code facts always come from the script: anchors, signatures, and the names of the units the script reports. The supplement can add only three things. It can add why-fields (purpose and responsibility), always marked INFERRED. It can add units the script cannot see, and each must cite verbatim evidence. It can add couplings the script did not extract, which must also cite evidence. If Overlay cannot tie part of the supplement to code, it returns an error that tells the setup author what to fix. Setup then stops before it writes anything. The package name is left over from older code: the package used to hold v1's "zero-map bootstrap" (bootstrap.go, adopt.go, since removed), and today it holds only the overlay.

Key Concepts

  • Script result (base): the extract.Result parsed from the extraction script's stdout, after setup has proved the script deterministic over three runs. Its units are the only source of anchors and signatures.
  • Supplement (doc): an extract.Result parsed from the supplement file by the same extract.Parse, so it uses the same schema and has already passed the same checks. Its keys are local to the file.
  • Anchor matching: match pairs each supplement unit with the script unit of the same Kind that shares the most anchors. Anchors compare by model.Anchor.Key(), which is path#symbol. If no unit overlaps, or two overlap equally, the match fails. Names are never compared.
  • Semantic unit: a supplement unit that carries evidence. Evidence means "the script cannot see this", so the unit is added as a new unit rather than matched. semantic() gives it the key supplement#<n>, sets its name to INFERRED, and clears its signature, digest and parent.
  • Findings: Matched counts the supplement units that landed, semantic ones included. Conflicts lists disagreements that setup prints as conflict: ... lines without stopping.
  • Errors vs. conflicts: an error stops setup before SaveProject, so nothing is written. A conflict only warns.

Overview

internal/evidence is ABBD's deterministic check that the code still shows what a reader claimed. The extraction script can't see some facts: a coupling through a convention, or a unit nothing in the code declares. When a pstack reader (or a person running abbd record) adds one, they have to cite verbatim code as a model.Evidence: a path, an optional line range, and a quote. This package answers one question about each citation: does the working tree still hold that quote, near where the citation says? It never decides whether the coupling is real. It only finds the text again, and the same tree always gets the same answer, so syncing an unchanged tree rewrites .abbd/ with identical bytes.

The package is one file of about 150 lines with two entry points. Checker.Check tests one evidence item and returns whether it is live, where it was found, and a digest of those lines. Checker.Apply runs over a list of units and writes the results into the model. An INFERRED-named unit whose evidence is all gone becomes Absent. A relation that has evidence, all of it gone, becomes Dead. Every live quote that names lines gets its Lines moved to where it was found this time. Those flags are what remove a reader's findings from the blueprint, abbd explain/path/impact, and abbd diff once the code stops showing them.

Key Concepts

  • model.Evidence (internal/model/model.go): Path (root-relative), Lines ("120" or "120-134", optional), Symbol, Quote. Span() parses Lines. With no lines, the quote is *unbounded* and may match anywhere in the file.
  • Semantic. For a unit it means Name.Origin == INFERRED (Unit.Semantic). For a relation it only means having evidence (Relation.Semantic: len(Evidence) > 0), whatever the relation's origin.
  • Checker: a project root plus a cache of each file it has loaded, by path. It is a snapshot of the tree, and callers build a new one for each command.
  • Normalized file: the file with all whitespace removed (norm), plus a map from each byte to its line number (line) and a flag saying whether whitespace came before that byte (gap).
  • Slack = 3: how many lines outside the cited range a match may sit.
  • Result{Live, At, Digest}: At is the line range where the quote was found ("7" or "4-5"). Digest is the first 8 bytes of a SHA-256 of the raw lines holding the match, in hex (16 characters).
  • Fact-level result: a unit or relation is live while *any* of its evidence items is live. A relation's digest is the digests of its live items in order, joined by commas.

Overview

internal/extract is the one place where ABBD reads the extraction JSON, the units-and-relations document that a project's extraction script prints and that the pstack-written supplement.json also uses. It is a single file, internal/extract/extract.go. Its comment calls it "the boundary where untrusted model output becomes typed units": the script was written by a model and the supplement holds a model reader's findings, so nothing downstream should have to re-check their shape. Parse decodes the JSON strictly. It normalizes every path to the forward-slash, root-relative form git reports, checks each unit and relation against the ABBD rules in internal/model, tags every value with where it came from (EXTRACTED or INFERRED), and returns a Result or the first error it hits. It never returns part of a result.

The package knows nothing about stored IDs, the .abbd/ state, or git. Its output is keyed by extractor-local key strings. internal/bootstrap (folding in the supplement) and internal/identity (matching against the stored units and assigning IDs) take it from there. It also exports NormalizeEvidence, which abbd record reuses so that a human's --evidence flags follow the same path rules as extracted evidence.

Key Concepts

  • Result: one extraction run, made of []Unit and []Relation. Relations name their ends by unit Key, not by ID.
  • Unit: a design unit before it has an ID. It has Kind (MOD, IF, EVT, DATA, CFG, FEAT), sorted and deduplicated Anchors, Name/Signature as EXTRACTED facts, Purpose/Responsibility as INFERRED facts, an opaque Digest, a Parent module key, and Evidence.
  • rawUnit / rawRelation / rawResult: the private JSON shapes, decoded with unknown fields rejected. They are the wire format; Unit/Relation are the checked, typed form.
  • Anchor: a path (plus an optional symbol) that ties a unit to code. Identity matching later runs on anchors, so their exact spelling matters.
  • Evidence: a verbatim quote (path, optional lines/symbol, quote) that a reader-found unit or coupling rests on. In Parse, a unit's evidence is also turned into anchors.
  • Origin tagging: Parse decides how much each field is trusted. Code facts are EXTRACTED, and any statement of intent is INFERRED ("Extraction reads code, so any statement of intent it makes is a guess"). It never produces USER_STATED.

Overview

internal/gitx is ABBD's only channel to git. It is a single file (internal/gitx/gitx.go, about 130 lines) holding seven stateless functions. Each one runs the git binary as a subprocess (git -C <dir> ...) and turns its output into a Go string, slice or map. It has no types, keeps no state and imports nothing from the rest of the module. The rest of ABBD uses it to answer four questions: what the working tree looks like right now (Snapshot), which files moved since the last sync (Renames), what commit we are on (Head), and what the .abbd/ files looked like at some older revision (MergeBase, Files, Show).

The main idea is the working-tree fingerprint. Snapshot turns the whole working tree into a git tree object, untracked files included and .abbd/ left out. It does this through a throwaway index, so the user's staging area is never touched. That tree hash is stored as fingerprint in .abbd/state.yaml. On the next sync, git compares the old and new trees, and its rename detection tells identity.Reconcile which file paths moved. abbd status and the blueprint compare the stored fingerprint with a fresh snapshot to say whether the state is stale.

Key Concepts

  • run(dir, env, args...): the one private helper. It runs git -C dir args... with extra environment variables, captures stdout and discards stderr.
  • Snapshot / fingerprint: a tree object written with GIT_INDEX_FILE pointed at a temporary file. It covers tracked and untracked, non-ignored files under dir except .abbd/. store.State.Fingerprint holds it between runs.
  • ok return value: Renames and Changed return ok=false (with no error) when the old tree object is missing from the object database, usually because git gc pruned it. Callers treat this as "rename detection is unavailable", not as a failure.
  • Default diff base: MergeBase walks an ordered list of likely default-branch names and returns the first one that git merge-base HEAD <candidate> accepts.
  • Paths relative to dir: every function reads and returns paths relative to the directory it was given. It uses -C dir, --relative and the rev:./path form to make the project root work even when it is a subdirectory of the git repository.

Overview

internal/identity decides which design unit is which across extraction runs. Every time abbd sync or abbd setup runs, the project's extraction script (plus, for setup, the semantic supplement) reports a fresh list of units that have anchors (path + symbol) but no IDs. identity.Reconcile pairs those units with the units already stored in .abbd/. A matched unit keeps its MOD-0001-style ID. An unmatched one gets a new ID above a high-water mark, so a deleted number is never handed out again. It also decides what the new run may overwrite. Code facts (anchors, signature, digest, extracted names, extracted relations) come from the extraction. Facts a human stated stay. Guesses (INFERRED facts) are kept or replaced depending on who is running. It never deletes anything. A stored unit nobody reported is marked Absent, and a partial overlap that did not count as a match is recorded as a merge candidate for a human.

The package is one file and pure: no I/O, and the output depends on the order of nothing. cmd/abbd loads the stored units, prior candidates, high-water marks and git renames, calls Reconcile, then writes the result back. Everything a human sees as "the same unit over time" (unit files, links, notes, explain output) depends on this one matching step.

Key Concepts

  • Anchor: a (Path, Symbol) pair (model.Anchor, compared by Key() = path#symbol). A unit's anchors are its fingerprint for matching. For a semantic unit, its evidence locations are added as anchors (extract.parseUnits).
  • Match rule: an incoming unit and a stored unit of the same kind can pair if they share at least 2 anchors, or if their anchor sets are identical (this is the only way a one-anchor unit can match).
  • High-water mark: the largest number ever minted for each kind (state.yaml high_water). New IDs are hw+1, so numbers are never reused.
  • Semantic unit: a unit only a reader vouches for, meaning its name is INFERRED (model.Unit.Semantic()). The script never reports it, and its evidence decides whether it is still there.
  • Guesses mode: KeepGuesses (plain abbd sync, where the script cannot see the guesses, so it leaves them alone) or ReplaceGuesses (abbd setup, where the supplement owns the guesses and withdraws the ones it no longer makes).
  • Candidate: {New, Existing, Shared}, a recorded overlap between two units that did not merge. It is persisted in .abbd/candidates.yaml and printed as X candidate-of Y via path#symbol.
  • Result: the merged Units list, plus Events (matched/new for each incoming unit), Unmatched (stored units now absent), Stated (semantic units kept only because a human said something about them), Candidates and the new HighWater.

Overview

internal/model is ABBD's vocabulary: the Go types for everything stored in .abbd/architecture/*.md and .abbd/features/*.md, plus the rules that decide which of those values are legal. It is one file, internal/model/model.go (about 420 lines), and it imports only the standard library. Every other package depends on it: extract, bootstrap, identity, evidence, store, topology, screen, and cmd/abbd. It contains no I/O, no git, and no rendering. It defines what a design unit is (a module, an external contract, or a feature), how units relate, and, most importantly, where each value came from.

The package exists to keep provenance honest. Every name, purpose, signature, and relation is tagged EXTRACTED (the project's deterministic script read it from code), INFERRED (a pstack reader guessed it and quoted code as evidence), or USER_STATED (a human said it, and the record says where). Unit.Validate enforces the rules that follow from those tags: a guess needs a quote, a human statement needs a source, and code alone can never be the origin of an intent ("why") field. The rest of ABBD relies on this: the drawn topology shows only what the code or a human vouches for, and a reader's guess stays alive only while the code still holds the quote it rests on.

Key Concepts

  • Unit: one design unit, with an ID, a Kind, a Name fact, at least one Anchor, an optional Parent module, optional why-fields (Purpose, Responsibility), an optional contract Signature, outgoing Relations, and the user-owned Notes. Each unit is serialized as one Markdown file with YAML frontmatter.
  • Kind: MOD (module), the four contract kinds IF, EVT, DATA, CFG, and FEAT (feature). Kind.Dir() maps features to features/ and every other kind to architecture/. DOM, STATE, TRN, and INV are reserved for a later domain layer and rejected for now.
  • ID: KIND-NNNN, such as MOD-0007. FormatID zero-pads to four digits, ParseID accepts four or more, and numbers are never reused (the store keeps a high-water mark for each kind).
  • Origin and Fact: Fact{Value, Origin, Source} is a single field value plus its provenance. Source is required for USER_STATED and forbidden for every other origin.
  • Anchor: {Path, Symbol}, the code location a unit's identity hangs on. Key() is path#symbol.
  • Relation: an edge stored on its From unit, with To, a RelationKind (depends_on, consumes, provides), an Origin, an optional Via (how the coupling arises), Evidence, and the Dead and Digest liveness fields.
  • Evidence: a verbatim code quote {Path, Lines, Symbol, Quote} that a semantic fact rests on.
  • Semantic, Guess, Counts, Present: small predicates that the rest of the system branches on. They have specific meanings, described below.
  • Edge: {From, Kind, To}, written as the shell-safe string MOD-0001.depends_on.MOD-0002.

Overview

internal/topology is the read-only query layer over ABBD's stored topology. It takes the []model.Unit slice that internal/store loads from .abbd/architecture/ and .abbd/features/, either from the working tree (Store.LoadUnits) or from a git revision (Store.UnitsAt). From that slice it answers the four questions the abbd CLI asks. Explain gives one unit at a glance (abbd explain). Path and Weakest give the shortest path between two units (abbd path). ImpactOf says what a change to some units reaches (abbd impact). Compare and Diff say how the topology changed since a base revision (abbd diff, and its --check CI gate). The package never writes units and imports only internal/model.

Beyond walking the graph, its job is to keep the three origins of a relation apart. EXTRACTED means the deterministic script read the relation from the code. USER_STATED means a human said it. INFERRED means a pstack reader guessed it from quoted evidence. The first two form the "drawn" topology. Inferred couplings are always listed beside them, ranked below them, or reported in a separate category, so a person reading the output can tell what the code vouches for from what a reader guessed.

Key Concepts

  • Unit (model.Unit): a module (MOD), a contract (IF, EVT, DATA, CFG), or a feature (FEAT). Each unit has a Parent (the module that contains it), Relations, and an Absent flag. Contracts also carry a Signature and a Digest, a fingerprint of the code behind them.
  • Relation kinds: depends_on (any unit to any unit), consumes (any unit to a contract), and provides (a module or feature to a contract). Relation.Dead marks an inferred relation whose evidence the code no longer holds.
  • Drawn vs. guessed: Relation.Counts() is true for a live EXTRACTED or USER_STATED relation, which is the drawn topology. Relation.Guess() is true for an INFERRED one.
  • Link (impact.go): one live relation between two present units, flattened to From/To/Kind plus Origin, Via and Evidence. Links(units) is the one graph that Explain, Path and ImpactOf all walk.
  • strength (query.go): EXTRACTED 2, USER_STATED 1, INFERRED 0. Path uses it to prefer firmer links, and Weakest uses it to report a path's least certain hop.
  • Lifting to the enclosing unit: a relation from or to an inside unit counts as its module's. Compare lifts to the top-level unit (top, between). Explain lifts to whichever unit is being explained (own).
  • Impact{Direct, Far}: the neighbourhood of a change as Item{Unit, Why} entries, split into a tier to read closely and a tier to skim.
