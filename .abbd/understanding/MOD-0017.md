## Overview

`internal/extract`는 ABBD가 추출 JSON을 읽는 곳이다. 추출 JSON은 프로젝트의 추출 스크립트가 찍는 unit과 relation 문서이고, pstack의 supplement도 같은 스키마를 쓴다. 파일은 `extract.go` 하나이고, 패키지 주석은 이곳을 "the boundary where untrusted model output becomes typed units"라고 부른다. 스크립트는 모델이 썼고 supplement는 모델 reader가 썼으므로, 이 패키지가 모양을 한 번 검사하고 하위 코드는 다시 검사하지 않는다. `Parse`는 스크립트 출력을, `ParseSupplement`는 supplement를 읽는다. 둘 다 모르는 field를 거부하는 엄격한 디코딩을 한다. 모든 경로를 정규화하고, 모든 unit과 relation을 `internal/model`의 규칙으로 검사하며, 각 fact에 writer를 준다. 온전한 `Result`나 첫 error를 돌려주고, 결과의 일부만 돌려주는 일은 없다.

이 패키지는 `internal/model`에만 기댄다. 저장된 ID, `.abbd/` 상태, git을 모르며, 출력은 각 unit의 추출기 안 ref로 키가 매겨진다. unit은 그 ref를 `ref`나 `key`로 쓰고, `parseUnits`는 둘을 다른 값으로 함께 쓴 unit을 거부한다. gitleaks의 `generic-api-key` 규칙이 엔트로피가 충분한 경로 모양의 `key` 값을 비밀로 읽기 때문이다. `cmd/abbd`는 `sync`, `setup`, `migrate`에서 `Parse`를 부르고, `setup`과 `migrate`가 쓰는 `readSupplement`에서 `ParseSupplement`를 부른다. `internal/bootstrap`이 두 결과를 접어 합치고, `internal/identity`가 결과를 저장된 unit과 맞추어 ID를 매긴다. `NormalizeEvidence`도 export된다. `abbd record`는 모든 `--evidence`를 이것으로 거치므로, 기록된 인용문도 추출된 인용문과 같은 경로 규칙을 따른다.

## Key Concepts

- **`Result`** (`extract.go`): 추출 한 번의 결과로, `Unit` 조각 하나와 `Relation` 조각 하나다. relation은 양 끝을 ID가 아니라 unit의 `Key`로 이름 짓고 자신의 `Writer`를 가진다.
- **`Unit`** (`extract.go`): ID를 받기 전의 설계 unit이다. `Kind`, 정렬하고 중복을 없앤 `Anchors`, `script`가 쓴 `Name`과 선택적 `Signature`, `Purpose`와 `Responsibility`, 실행 맥락의 `Run`, 불투명한 `Digest`, 자신을 품은 module이나 feature의 `Parent` 키와 `ParentEvidence`, 그리고 `Evidence`를 가진다. 파싱은 `Placed`와 `SupplementRef`를 비워 두고, `bootstrap.Overlay`가 채운다.
- **`Placement`** (`extract.go`): writer 하나의 parent 주장으로, 키와 evidence를 가진다. overlay가 supplement의 것을 `Placed`에 더하고, `identity`가 각각을 스크립트의 것 옆에 parent 주장으로 저장한다.
- **전송 형태** (`extract.go`): `Doc`, `DocUnit`, `DocRelation`은 extraction JSON의 유일한 정의로, `parseUnits`가 `DisallowUnknownFields`로 디코딩한다. 같은 타입을 bundled front-end(MOD-0058)도 찍으며, `Doc.Encode`는 unit을 ref로, anchor와 artifact를 정렬하고 relation을 양 끝으로 정렬해 같은 코드에서 같은 바이트를 낸다. `Unit`과 `Relation`은 검사를 마친 타입 있는 형태다.
- **Unit 검사** (`extract.go`): `parseUnits`는 kind를 검증해 모르는 kind와 예약된 도메인 kind를 거부한다. 이름과 anchor 하나 이상을 요구한다. `signature`는 계약(`IF`, `EVT`, `DATA`, `CFG`)에만 허용한다. `run`은 실행 맥락(`EXEC`)에만 허용하고, `model.ParseRun`이 `tick 1`처럼 shape와 count로 읽히는지 검사한 뒤 정규형으로 남긴다. 외부 라이브러리(`EXT`)는 parent를 가질 수 없고, supplement가 내면 거부한다. 매니페스트가 선언하므로 추출만 알린다.
- **키와 parent 검사** (`extract.go`): 키는 겹치지 않는다. parent는 다른 module이나 feature의 키여야 하고, 이는 `model.Kind.Holds`가 허용하는 두 kind다. `parentCycle`이 고리를 거부한다. `ParseSupplement`는 `foreignParents`를 켜므로, supplement에 없는 parent 키는 `bootstrap.Overlay`가 스크립트에 대고 풀도록 남는다.

### Relater

- **bundled relater** (MOD-0060 internal/extract/relate): 추출이 이름 지은 unit 사이에 코드 수준 관계를 더하는 하위 모듈로, `Names`가 나열하는 것은 `go`, `rust`, `c`, `ts`, `python` 다섯이다. `Relate`는 `RELATER[=DIR]` spec마다 그 디렉터리에 relater의 매니페스트(`go.mod`, `Cargo.toml`, `compile_commands.json`이나 `CMakeLists.txt`, `tsconfig.json`이나 `package.json`, `pyproject.toml` 같은 python 프로젝트 파일)가 있는지 보고, 읽은 사실(call, callback, import, trait, macro)을 모은다. 저장소 밖 캐시 디렉터리와 CMake 캐시 옵션도 relater에 넘긴다. `go`는 go/types로 패키지를 읽고 VTA로 호출을 풀며(테스트는 빼고, 어느 호스트에서나 같도록 GOOS=linux, GOARCH=amd64, CGO_ENABLED=0으로 고정), `rust`는 Cargo 워크스페이스를 rust-analyzer(`$ABBD_LSP_RUST`나 PATH)로 읽는다. rust는 언어 서버 클라이언트인 MOD-0061 `internal/extract/lsp`로 서버를 stdio로 띄워 색인이 끝나길 기다린 뒤 심볼의 참조와 구현을 묻는다. 타깃은 `x86_64-unknown-linux-gnu`로 고정하고, 테스트와 빌드 스크립트와 proc macro는 켜지 않는다. 워크스페이스에 feature가 있으면 기본 feature와 모든 feature를 차례로 읽어 합치고, 한쪽에서만 찾은 relation은 그 설정 이름을 `when`에 단다. 읽은 코드가 두 끝 unit에 모두 닿는 코드 근거 `depends_on`(via가 비었거나 call, trait, macro, import)은 추출의 것을 대신하고, 설정이나 spawn 같은 그 밖의 relation은 건드리지 않고, 이름으로 등록한 콜백은 코드만으로 보이지 않을 수 있으므로 via가 callback인 추출의 `depends_on`도 남긴다. 다만 컴파일되지 않은 코드를 가진 unit은 일부만 읽은 것이므로, 그 unit에서 나가는 추출의 `depends_on`은 relater가 그 link의 흔적을 찾았을 때만 대신하고 아니면 남긴다. 읽지 못한 코드는 relater 이름과 이유와 경로로 이뤄진 `Unread`로 돌려준다. unit은 만들지 않으며, `provides`와 `consumes`는 추출에 아직 없는 곳에만 더한다. 한 link는 가장 좋은 via(call, callback, trait, macro, import 순서)의 relation 하나가 되고, 인용은 직접 호출을 먼저 최대 세 줄이다. `frontend.SpecOf`는 front-end와 relater가 함께 쓰는 `NAME[=DIR]` 읽기다. `abbd relate`가 이것을 부른다. 내부에서 `found`는 relater 하나가 읽은 사실과 그 코드가 닿은 unit, link별 `when`, 읽지 못한 파일의 묶음이고, `held`는 module이나 feature의 anchor 경로와 깊이다. `pair`는 Go의 타입과 그것이 바뀌어 담기는 interface의 짝이며, go의 trait 사실은 두 패키지가 import로 이어졌거나 이 짝이 있을 때만 나온다.

### Front-end

- **bundled front-end** (MOD-0058 internal/extract/frontend): 빌드 시스템이 스스로 아는 모델을 읽어 같은 `Doc`을 돌려주는 하위 모듈로, `Names`가 나열하는 `cargo`, `cmake`, `msbuild` 셋이다. `msbuild`만 매니페스트 없이 `NAME=FILE`로 파일 하나를 받으며, 그 파일이 `.sln`, `.slnx`, `.vcxproj`가 아니면 거부한다. `Extract`는 `FRONTEND[=DIR]` spec마다 저장소 루트와 그 디렉터리, 빌드 캐시를 담은 `tree`에서 front-end를 돌리고, 캐시가 저장소 안에 있거나 두 spec이 같은 ref의 unit을 만들면 거부한다. front-end가 풀지 못한 것은 `Doc.Notes`에 모았다가 표준 오류로만 내보낸다. `abbd extract`가 그 문서를 찍으므로, front-end의 출력도 스크립트의 출력처럼 `Parse`의 검사를 거친다. `cmake` front-end는 무엇이든 구성하기 전에 PATH의 CMake에 `cmake -E capabilities`로 버전을 묻고, 4.2보다 낮으면 구성이 먼저 실패하는 곳에서도 거부한다(`cmakeVersion`, `oldCMake`). 빌드 트리 이름에 그 버전을 넣으므로, 옛 CMake가 만든 트리를 그것을 다시 쓰지 못하는 새 CMake가 만나는 일이 없다.

### C relater

- **c relater** (MOD-0060 internal/extract/relate): `c`는 C와 C++ 코드를 clangd(`$ABBD_LSP_C`나 PATH)로 읽는다. 디렉터리의 `compile_commands.json`을 그대로 쓰고, 없으면 CMake 프로젝트를 cmake front-end와 같은 빌드 트리에서 구성해 file API로 각 소스의 컴파일 명령을 다시 만든다(`frontend.CMakeCompiles`). `c=FILE`로 Visual Studio 솔루션이나 프로젝트 파일을 받으면 msbuild front-end가 읽은 구성에서 `cl.exe`가 컴파일하듯 명령을 만든다. 이 경우 읽는 소스는 기본 150개까지이며 첫 것부터 경로순으로 읽고(`ABBD_C_MAX_SOURCES`가 바꾸고 0이면 한도가 없다), 한도를 넘은 소스는 읽지 못한 것으로 둔다. 컴파일러가 찾지 못한 헤더도 `Unread`의 `Lead` 줄로 돌려준다. 테스트가 아닌 소스마다 명령 하나를 캐시의 컴파일 데이터베이스에 쓰므로, clangd의 색인도 저장소가 아니라 캐시에 놓인다. 다른 unit이 이름 붙일 수 있는 선언마다 참조를 물어, 호출은 call, 값으로 쥔 함수는 callback, 매크로는 macro, 타입과 상수는 import로 삼는다. 함수 포인터 필드를 가진 구조체를 중괄호로 채운 표는 호스트가 그 표로 부르는 callback이나 provides와 consumes가 된다. 컴파일 데이터베이스가 컴파일하지 않는 소스는 읽지 못한 것으로 두고, 읽은 파일 중 `#if`가 뺀 코드를 가진 것은 `Unread`의 gated 묶음으로 경로와 줄 수를 돌려주어 그 코드 안 관계가 빠졌음을 밝힌다.

### Script relaters

- **ts와 python relater** (MOD-0060 internal/extract/relate): `ts`는 TypeScript와 JavaScript를 `$ABBD_LSP_TS`나 PATH의 typescript-language-server로, `python`은 Python을 `$ABBD_LSP_PYTHON`이나 PATH의 pyright-langserver로 읽는다. 둘은 같은 `scripting` 읽기를 쓰고, 언어마다 다른 것은 `scriptLang`이 담는다. ts는 워크스페이스의 `tsconfig.json`이나 `jsconfig.json`을 서버가 그대로 따르게 하고, 서버 옆에 설치된 TypeScript 5.x의 `tsserver.js`를 찾아 넘긴다. 테스트와 의존성과 빌드 산출물, 숨은 디렉터리는 걷지 않고, python은 밑줄로 시작하는 이름도 남의 것으로 치지 않는다. 파일을 모두 연 뒤 다른 unit이 이름 붙일 수 있는 최상위 선언마다 참조를 물어, 다른 unit의 참조를 상속이나 구현이면 trait, 호출이면 call, 나머지는 import로 삼는다. 메서드는 묻지 않는다. 서버가 받는 쪽 타입을 풀지 못하면 `toString` 같은 흔한 이름이 엉뚱한 unit을 가리키기 때문이다. 구조 분해로 묶인 변수와 리터럴 기본 내보내기도 묻지 않는다. 서버가 심볼을 나열하지 못한 파일은 읽지 못한 것으로 돌려준다. 단계마다 시작할 때와 30초마다 표준 오류에 `relate:` 줄로 파일이나 선언이 몇 개 중 몇 개 끝났는지와 경과 시간을 알리며(`progress`), 읽은 결과는 이 줄이 있든 없든 같다.

### 저장소 밖

- **저장소 밖 코드와 서드파티 라이브러리** (MOD-0060 internal/extract/relate): relater는 저장소 루트 밖 경로와 어떤 unit의 anchor도 품지 않은 경로를 읽지 않으므로 표준 라이브러리, 시스템 헤더, 의존성 패키지의 코드는 unit도 relation도 되지 못한다. 테스트가 go, c, rust, ts, python 각각에서 이를 지킨다(`stdlib_test.go`). 서드파티 라이브러리는 대신 `Libraries`(`libs.go`)가 큰 덩어리 하나로 더한다. `go.mod`의 직접 `require`, `package.json`의 `dependencies`·`peerDependencies`·`optionalDependencies`, `Cargo.toml`의 `[dependencies]`·`[build-dependencies]`와 대상별 형태가 선언한 라이브러리마다 kind `EXT` unit 하나를 내고, 그 anchor는 선언한 매니페스트 줄을 라이브러리 이름을 symbol로 삼아 가리킨다. 그 라이브러리를 import하는 코드를 가진 module마다 via import인 `depends_on` 하나를 내고 import 줄을 최대 세 줄 인용하며, 호출 하나하나는 선이 되지 않는다. 어느 코드도 import하지 않으면 매니페스트를 품은 module이 쓰는 것으로 보고 선언 줄을 인용한다. dev와 test 의존, `// indirect`, `workspace:`나 `path` 같은 저장소 안 패키지는 빼고, 쓰는 module이 없는 라이브러리는 이름을 note로 돌려준다. `testdata`, `Cargo.toml` 옆의 `target`, `node_modules`나 `vendor` 같은 의존성 디렉터리의 매니페스트와 코드, 테스트 코드는 읽지 않고, 읽지 못한 디렉터리는 건너뛰며 note로 밝힌다. Rust는 문자열과 주석을 뺀 뒤 경로의 첫 마디만 crate 이름으로 읽고(`crate`, `self`, `super`는 뺀다), npm은 블록 주석을 지운 뒤 `import`·`export`·`require` 문맥과 여러 줄 import를 닫는 `} from`의 지정자만 읽는다.

### Relation checks

- **Relation 검사** (`extract.go`): 두 끝은 달라야 한다. 스크립트 출력에서는 둘 다 있는 ref여야 한다. supplement에서는 끝이 스크립트만 알리는 ref일 수 있으므로, `parse`는 거기서 kind만 검사하고 `RelationKind.Joins`는 두 kind를 아는 overlay에 맡긴다. 그 밖에는 `RelationKind.Joins`가 kind가 양 끝에 맞는지, `Via.Validate`가 via를, `model.ValidatePhrase`가 구절을 검사한다. 구절은 supplement만, 그리고 evidence와 함께만 줄 수 있다. evidence는 정규화된다. `RelationKind.Quoted`는 kind가 요구하는 evidence 개수를 검사하므로, `posts_to`는 생산자와 소비자를 함께 인용하는 2개 이상의 항목이 없으면 거부된다. 이 검사는 스크립트와 supplement 모두에 걸린다. 한 edge의 두 줄이 같은 구절에 다른 이름을 주면 거부된다. relation의 `symbols`는 구절을 나르는 코드의 이름으로 `ValidateSymbols`가 인용 안에 있는지 검사한다. 구절은 relation과 따로 `Result.Phrases`로 간다. edge 하나는 구절 하나를 가지므로, 한 edge의 두 줄이 다른 구절을 주면 거부된다. 파싱된 relation의 writer는 모두 `script`이고, overlay가 supplement 자신의 결합을 writer `supplement`로 덧붙인다.
- **Entry** (`extract.go`): 계약의 `entries`는 route, method, flag, field처럼 코드가 쓰는 대로의 부분이고, 각각 `name`과 선택적 `shape`, `required`를 가진 `model.Entry`다. `normalizeEntries`는 공백을 자르고 코드의 순서를 지키며, `key`가 없는 entry에 `model.EntryKey`가 이름에서 줄인 키를 준다. 계약이 아닌 unit의 entry와 키를 공유하는 두 entry는 거부한다. relation의 `entries`는 `to` unit의 entry를 이름이나 키로 가리키고, `entryKeys`가 그것을 그 unit entry의 정렬된 키로 바꾸며, unit이 나열하지 않은 이름은 거부한다. 한 edge의 relation 두 줄은 entry를 합쳐 relation 하나가 된다. 주장 하나가 edge 하나를 쥐기 때문이다. entry를 이름 짓지 않는 줄은 모든 entry를 쓰므로 그 relation을 통째로 남긴다. `ParseSupplement`는 entry를 아예 거부한다. entry는 코드가 쓰는 것이라 스크립트만 알린다.

### Path normalization

- **경로 정규화** (`extract.go`): `normalizePath`는 역슬래시를 슬래시로 바꾸고 경로를 다듬어 정리하며, 비었거나 절대이거나 루트 밖으로 나가는 경로를 거부한다. anchor는 git이 알리는 루트 기준 경로와 같게 비교되어야 한다. identity 맞추기가 그 위에서 돌기 때문이다.
- **Evidence** (`extract.go`): `path`, 선택적 `lines`와 `symbol`, `quote`를 가진 원문 그대로의 인용이다. JSON은 항목의 상태를 정하지 않는다. `NormalizeEvidence`는 경로를 정규화하고 symbol을 다듬은 뒤 `model.Evidence.Validate`를 돌리며, 이 검사는 `.abbd/`나 `.git/`의 인용도 거부한다. unit의 evidence는 anchor도 되므로 reader의 unit이 안정된 정체를 얻는다.
- **Writer 표시** (`extract.go`): 이름, signature, relation은 writer `script`, 곧 EXTRACTED를 받는다. JSON의 purpose, responsibility, run은 writer `supplement`, 곧 INFERRED를 받는다. "Extraction reads code, so any statement of intent it makes is a guess, and it ranks with the supplement's"라는 이유다. 이곳은 `reader`나 `human` 값을 만들지 않는다.
- **Artifact** (`extract.go`): unit의 `artifacts`는 정렬해 두는 스크립트 fact 하나로, build가 그 unit에서 만드는 것을 `exe`, `static`, `shared`, `module`, `cdylib`로 나열한다. parse는 `MOD`가 아닌 unit의 artifact, ABBD가 모르는 종류, 두 번 나온 종류를 거부한다.
- **조건** (`extract.go`): relation의 `when`은 `Relation.When`으로 남고, relation이 성립하는 조건인 feature, cfg, `dev`, link scope를 이름 짓는다. `model.ValidateWhen`은 `model.MaxWhen`자를 넘거나 한 줄을 넘는 조건을 거부한다. 다른 `when`으로 다시 나온 edge는 거부되고, error는 조건을 `a | b`로 합치거나 link scope를 빼라고 말한다. scope는 조건이 아니기 때문이다.

### CMake front-end options

- **cmake 옵션과 target** (`internal/extract/frontend/cmake.go`): 빌드 트리 이름에 CMake 버전과 캐시 옵션을 넣으므로, 옛 CMake가 만든 트리나 다른 옵션으로 구성한 트리를 만나는 일이 없다. `ExtractWith`는 `-DNAME=VALUE` 캐시 옵션을 configure에 넘기고, 구성이 실패하면 빠진 하위 디렉터리를 끄는 옵션을 알리고 프로젝트의 CMake 파일이 선언한 option( 이름을 build·test 쪽부터 나열한다. 이름에 `test`, `bench`, `example` 낱말이 있는 target과 `test`, `third_party`, `vendor`, `external` 같은 디렉터리의 target은 module이 아니다. module의 anchor는 컴파일하는 소스뿐 아니라 target이 나열한 헤더의 디렉터리도 담는다.
