SSOT Architecture Map · Feature Map을 표준 문서 구조로 삼고, 에이전트가 매 턴 구현·실행 검증·문서/그래프 갱신을 한 완료 단위로 수행하는 개인용 개발 하네스. 빈 저장소든 코드만 있는 저장소든 하네스가 그 구조를 직접 만들어 준다.

"For My"는 경쟁·수익화를 목표로 하지 않는다는 선언이지 범용성을 배제하는 말이 아닙니다. 사용자가 운용해 온 SSOT Architecture/Feature Map 구조가 곧 이 하네스의 표준 문서 구조이며, 빈 저장소·코드만 있는 저장소·비슷한 문서가 있는 저장소 어디서 시작하든 하네스가 그 구조를 생성하고 유지합니다. 근거 어휘를 origin / verification / confirmation 세 축으로 통일했고, 승인은 A(자동) · B(묻고 기본값 진행) · C(멈춤) 세 등급과 지연 확인으로 정리했습니다. 도메인 상태 그래프는 삭제하지 않되 Phase 3 이후로 미루고, Phase 1에는 외부 계약 뷰(인터페이스·토픽·스키마·서빙 구조)만 남깁니다. 벤치마크는 완성 후의 자기 검증 계획으로 재분류했습니다.

PRODUCT REQUIREMENTS · READ-FIRST

00. 인계 에이전트: 먼저 읽을 것

무엇을 만드는지, 무엇이 표준 구조인지, 사람이 언제 개입하는지

제품 정의: For My Harness는 경쟁이나 제품화를 목표로 하지 않는 개인용 개발 하네스다. 범용으로 쓰일 수 있어야 하지만 그것이 목적은 아니다. 하네스의 표준 문서 구조는 SSOT Architecture Map + Feature Map이며, Markdown을 원본으로 두고 HTML을 함께 생성한다. 이 구조는 사용자가 운용해 온 체계를 그대로 잇는다. 사용자에게 사전 문서 작성을 요구하지 않는 것과, 그 구조를 표준으로 삼는 것은 양립한다: 구조는 하네스가 만들어 준다.

절대 놓치면 안 되는 10가지

  1. 표준 구조를 하네스가 만든다: 진입 경로는 greenfield(요구사항에서), code-only(코드·테스트·Git에서), adopt(비슷한 문서가 있으면 참고해 재구성) 세 가지이고, 어느 경로든 결과는 같은 SSOT Architecture/Feature Map + md/html이다. 기존 문서는 입력이지 전제조건이 아니다. 01A
  2. For My, not Best One: 다른 하네스보다 우수하다거나 제품화·수익화를 노리는 것이 아니다. 사용자별 작업 정책·개발 성향·언어·테스트 환경·문서 뷰를 조절할 수 있어야 하고, 그 결과 범용으로도 쓸 수 있다.
  3. 매 턴 현재 상태 기반: 먼저 현재 코드, 사용 가능하면 현재 Map/Intent/Decision, Git 이력과 검증 정보를 읽는다. 처음에는 Map이 없어도 되는 것이 정상이다.
  4. 사용자 요청은 신규 의도: 요청을 현재 관찰 사실 및 검증된 계약과 연결해 해석한다. 확인이 어려운 기능 목적은 가설로 표시하고 사용자에게 결정에 필요한 사항만 질문한다.
  5. 검증된 변경은 함께 반영: 구현과 실제 검증이 성공하면 Code/Feature/Architecture/Intent/Graph/HTML을 자동 동기화한다. 별도의 문서 승인으로 매 턴 정지시키지 않는다.
  6. 지식의 근거를 세 축으로 기록: 모든 사실에 origin(어디서 왔나) · verification(실행으로 확인됐나) · confirmation(사용자가 봤나)을 따로 기록한다. 어휘는 06장에서 한 번만 정의하고 다른 장은 그것을 쓴다. 초기 스캔만으로 설계 의도를 발명하지 않는다.
  7. pstack의 전체 루프를 참고: Feature Map 갱신만이 아니라 라우팅, how/why, architect, 구현, 실제 검증, blast-radius, 리뷰, correct/reflect를 각 턴에 적용한다. R01 R02 R04
  8. 완료 조건에 최신성 포함: 코드 변경 후 Map·Graph·HTML 갱신 실패 시 성공이라고 선언하지 않는다. 외부 변경은 감지해 재조정하고 불확실하면 상태를 노출한다.
  9. 승인은 세 등급: A(자동 실행·사후 보고), B(묻되 답이 없으면 기본값으로 진행), C(비가역·외부 효과만 멈춤). bootstrap은 절대 묻지 않고, 추정 항목은 어떤 턴이 그것을 처음 건드릴 때만 확인한다. 10장
  10. 장기 품질로 평가하되 필수는 아님: 연속 수정에 따른 회귀·설계 훼손·의도 왜곡·미래 변경 비용을 측정하는 계획은 부록으로 둔다. 개발 중에는 계측 훅만 유지한다. 기존 그래프 제품을 의무 의존성으로 두지 않는다.

시스템 생명주기: 처음 만나는 저장소 → 관찰·질문·기초 맵 생성 → 사용자 요청 → 개발/검증 → 문서·그래프 자동 동기화 → 다음 턴.

사람의 역할: 개발 의도·우선순위·실질적 선택을 제공하고, 중요한 모호성이나 위험을 판단한다. 모든 정상 코드/맵 갱신을 승인하는 관리자가 되는 것은 아니다.

v1.3 핵심 보완: 코드에 드러나지 않는 모듈 간 외부 인터페이스와 서빙 구조(HTTP/gRPC API, Kafka topic, DB 스키마 소유권, 설정 키, 배포 단위)는 Architecture Map의 1급 항목으로 Phase 1부터 다룬다(08A). 도메인 엔티티·상태 전이·불변조건 그래프는 스키마 자리만 예약하고 생성·추출·질의는 Phase 3 이후로 미룬다. 실시간 운영 상태는 어느 단계에서도 코드로 추측하지 않는다.

개선 보장은 없다: 구조적으로 기대되는 이점과 실제 품질 향상은 별개다. 그래프 조회가 도움이 되지 않으면 LSP/소스 검색으로 폴백하며, 지속 벤치마크에서 추가 효과가 증명되지 않는 기능은 비활성화할 수 있어야 한다.

선행 기술: pstack 외에 Graphify · GitNexus · CodeGraphContext의 검증 가능한 원문을 읽되, 기존 그래프 엔진을 제품에 필수 의존성으로 삼지 않는다.

01. 비전·사용자·비목표

개인용이되 범용으로 쓸 수 있고, 어떤 저장소에서 시작하든 같은 표준 구조로 수렴한다

문제 인식

에이전트는 단일 코드 변경을 잘해도 반복 개발에서 기능 의도, 모듈 경계, 과거 결정, 회귀 위험을 잃기 쉽다. 필요한 정보는 코드에 부분적으로만 존재하며, 전체 코드 그래프만으로 설계 의미를 확정할 수 없다.

기존 SSOT 구조의 위치: 사용자가 운용해 온 모듈 중심 SSOT Architecture Map과 HTML 인터페이스 문서는 배경 사례가 아니라 이 하네스가 가져야 할 초기 세팅이자 유지해야 할 표준 구조다. 하네스는 그 구조를 Markdown 원본 + 생성 HTML로 병기하며 유지한다. 달라지는 점은 하나다: 그 구조를 사람이 미리 준비해야만 동작하는 부가 도구가 아니라, 준비물 없이도 하네스가 직접 만들어 주는 제로베이스 하네스라는 것. 비슷한 문서가 이미 있는 프로젝트에서는 그것을 참고하되 이 하네스의 구조로 재구성한다.

핵심 이용 방식

  • Greenfield: 아직 코드나 맵이 없고, 자연어 요구사항만 주어지는 신규 프로젝트. 기능·아키텍처·검증 계약을 개발과 함께 만든다.
  • Brownfield code-only: 소스·Git·테스트·설정은 있지만 Architecture/Feature Map이 없는 프로젝트. 코드를 분석하고 관찰된 동작을 기반으로 초기 지식을 구축한다.
  • Adopt: 기존 SSOT, HTML, ADR 또는 다른 도구의 맵이 있으면 참고해 표준 구조로 재구성한다. 그대로 들여오는 이관이 아니라 재구성이며, 입력이지 전제조건이 아니다.
  • Host-neutral: Cursor/Codex/Claude Code/OpenCode/CLI 등 여러 호스트에서 공통 프로젝트 지식과 워크플로를 이용한다.

성공 기준

  • 사전 맵 없이 init/bootstrap 실행 후 증거 수준이 표시된 Feature/Architecture 후보, 초기 Graph 및 HTML 탐색 페이지가 만들어진다.
  • 프로젝트 사실과 사용자의 기능 목표가 결합되고, 모호한 부분은 적절하게 질의된다.
  • 매 개발 턴이 구현·검증·맵 자동 갱신·인계 가능 상태로 닫힌다.
  • 회귀 및 아키텍처 드리프트의 누적이 기본 에이전트와 pstack 기준선보다 유의하게 낮은지 실험한다.
  • 언어, 문서 화면, 승인 정책, 도구, 워크플로를 프로젝트에 맞게 교체할 수 있다.

비목표

  • 다른 하네스와 성능을 겨루거나 제품화·수익화를 목표로 하는 것.
  • 기존 문서를 사람이 먼저 준비해야만 동작하는 부가 도구가 되는 것.
  • 모든 초기 설계 의도를 소스코드만 보고 확정했다고 주장하는 것.
  • 새 LLM, 범용 IDE, 모든 언어를 완벽히 분석하는 컴파일러를 직접 개발하는 것.
  • 기존 그래프 제품의 기능이나 pstack을 무차별적으로 복제해 기능 개수 경쟁을 하는 것.

01A. 제로베이스 진입·Zero-Map Bootstrap

어느 경로로 들어오든 결과는 같은 표준 구조. 준비물은 없고, 질문도 없다

진입 모드와 기대 결과

모드필요한 입력하네스가 해야 할 일진입 차단 여부
greenfield빈 디렉터리 + 사용자의 목표/요구사항초기 Requirement/Feature/Architecture 초안을 만들고 개발·검증을 진행하며 근거를 쌓는다기존 코드/문서 불필요

adopt비슷한 기존 YAML/JSON/Markdown/HTML 등참고 문서를 읽고 표준 구조로 재구성한다. 출처를 origin: ADOPTED로 기록하고 충돌·누락을 보고한다선택 사항

초기화 파이프라인

  1. Discover: 저장소·언어·빌드·테스트·Git 기록·README·API/스키마·설정·엔트리포인트·기존 문서의 유무를 탐지한다.
  2. Observe: 가능한 빌드/테스트/실행으로 관찰한 동작을 확보한다. 실행 불가 항목은 UNKNOWN으로 둔다.
  3. Infer candidates: 소스 근거가 있는 Module/Interface 관계와 Feature 후보를 생성한다. 코드가 보여주는 사실과 기능의 목적에 관한 추론을 구별한다.
  4. Do not ask: bootstrap 단계에서는 질문하지 않는다. 의도·책임·호환 정책이 불확실한 항목은 INFERRED ∧ UNCONFIRMED로 두고 HTML의 "확인 대기" 목록에 올린다. 확인은 어떤 개발 턴이 그 항목을 처음 건드릴 때로 미룬다(10장 지연 확인).
  5. Seed project intelligence: 앵커 묶음 기반 안정 ID(06장)를 발급하고 features/, architecture/(외부 계약 뷰 포함), decisions/, Graph 및 HTML을 생성한다. 확실하지 않은 항목은 축별 상태로 표시한다.
  6. Handoff: 현재 revision, 확인된/추정된 계약, 검증 범위, 미해결 질문을 BootstrapReport에 기록하여 다음 개발 턴이 그대로 사용할 수 있게 한다.

지식 생성의 안전장치

코드에서 어떻게 동작하는지 관찰할 수 있어도 왜 그 동작을 의도했는지는 확정할 수 없다. 초기 맵의 모든 항목에 06장의 세 축(origin, verification, confirmation)과 위치·실행 증거를 붙인다. 사용자 확인 전 추정 의도를 강제 계약으로 승격하지 않는다.

# 하네스가 처음 생성한 Feature 후보 — 예시
id: FEAT-001
name: heartbeat ingestion
intent:
  purpose: "heartbeat를 검증해 저장한다"   # 에이전트 추정
  origin: INFERRED
  confirmation: UNCONFIRMED            # 확인 대기 목록에 등재
observations:
  - behavior: kafka heartbeat payload is parsed
    origin: EXTRACTED                  # AST/LSP에서 결정적으로 추출
    verification: NOT_RUN
  - behavior: result is passed to storage writer
    origin: EXTRACTED
    verification: NOT_RUN
external_contracts:                    # 외부 계약 뷰 (08A)
  - kind: kafka-topic
    direction: consumes
    selector: heartbeat-events
    origin: EXTRACTED
anchors:                               # 안정 ID 앵커 묶음 (06장)
  - { kind: symbol, ref: "go:service/heartbeat.Consumer.Run" }
  - { kind: path,   ref: src/heartbeat/consumer.go }

독립 실행 수용 기준

03. 변경 의도·현재 코드·맵의 관계

세 가지 '의도'를 혼동하지 않는다

항목 정의 예시
Current Intent 현재 프로젝트에 유효한 기능 의미·아키텍처 제약·과거 결정 “Heartbeat 재처리는 중복을 저장하지 않는다”

Resulting Intent 검증에 성공한 변경 이후의 유효한 동작 계약 “기존 중복 안전성을 보존하며 새 재시도 정책 지원”

Current Code와 Current Map도 매 턴 함께 읽는다. Requested Intent Delta를 반영한 구현이 검증되면 Resulting Intent와 실제 변경 내용을 Map/그래프/HTML에 반영한다. 사용자가 코드 변경을 직접 지시한 경우, 그 작업을 완료한 뒤 여전히 변경 전 SSOT를 남기는 것은 허용되지 않는다.

두 방향의 동기화

Forward (요청 기반 정상 개발): 사용자 요청 → 의도 해석 → 영향도/제약 조회 → 코드/테스트 변경 → 검증 → 최신 Feature/Architecture/Intent 문서 자동 갱신 → 그래프 리인덱싱 → HTML 재생성 → 일치 여부 검사.

Reconcile (외부/수동 코드 수정): 작업 시작 시 저장소 revision 또는 워킹트리 변경 감지 → intent_source: external인 CHG 레코드를 자동 생성 → EXTRACTED 사실(심볼·호출·바인딩)만 갱신 → 의미 필드(purpose, responsibility, invariant)는 손대지 않고 UNCONFIRMED로 표시 → 질문하지 않는다. 유일한 예외는 외부 변경이 CONFIRMED 계약과 명백히 충돌할 때이며, 그때만 등급 B로 묻는다(10장).

이때 '변경은 사용자 의도의 반영'이라는 기본 가정은 사용자 요청을 받아 정상 개발한 워크플로에 적용한다. 무관한 외부 커밋이나 검증 실패 변경을 같은 수준으로 신뢰해서는 안 된다. 코드만으로 의도를 역추론해 의미 필드를 다시 쓰지 않는다는 00장 규칙과 Reconcile은 이렇게 양립한다.

04. 각 개발 턴의 완전한 하네스 루프

pstack의 개발 습관 + 자동 동기화를 결합한 기본 플로우

Bootstrap gate: 프로젝트 지식이 비어 있으면 별도 준비를 요구하지 않고 첫 턴의 0단계에서 초기 Map/Intent/Graph/HTML을 생성한다. 빈 저장소면 사용자의 첫 요구를 기준으로, code-only 저장소면 소스/테스트 분석을 기준으로 한다.

항상 실행되는 turn router

이 루프는 사용자 요청마다 실행되며, 작은 작업일수록 가볍게 실행한다. 아래 단계의 행위는 보존하되 모든 단계에 별도 에이전트·도구 호출을 반드시 할 필요는 없다.

단계 수행 내용 산출물 / 게이트
0. Session bootstrap 지식 존재 여부 탐지 → 없는 경우 Zero-Map Bootstrap 실행, 있는 경우 Git revision/워킹트리/맵/그래프 최신성 점검 및 외부 변경 재조정 ProjectStateSnapshot
1. Route 구현·버그·리팩터링·성능·문서·설계 등 작업 분류 및 난도/위험도 평가 WorkflowPlan + 검증 수준
2. Understand current Feature Map, Architecture Map, 관련 테스트, 과거 결정, 실제 코드 조회 (how/why 개념) 근거 링크 있는 현재 상태
3. Resolve intent 사용자 요청 + 현재 상태로 신규 의도 도출, 애매한 가치 판단은 질의 IntentDelta / 필수 질문
4. Design / impact 책임 모듈·경계·타입/인터페이스 제안, 영향 Feature·테스트 선택 (architect/blast-radius) ChangePlan + 검증 계약
5. Implement 작은 단위 코드·테스트 변경; 복잡하면 격리 worktree/subagent 활용 diff + 단위별 증거
6. Prove 빌드, 테스트, 사용자 수준 기능 실행, 경계 위반·회귀 검사 EvidenceReport, 실패 시 재수정
7. Synchronize 검증된 변경을 Architecture/Feature/Intent/Decision으로 갱신, 그래프 갱신, HTML 생성 ConsistencyReport
8. Review / ship 코드/문서 diff 검토, 비용·부작용·미해결 위험 보고, 허용된 정책으로 반영 ChangeReceipt
9. Learn 반복 실수 교정, 필요한 정적 검사 추가, Skill 동작 개선 후보 도출 (correct/reflect) 규칙/Skill 변경 제안·평가

작업 타입에 따라 가변 실행

  • 단순 함수 버그: LSP+관련 feature/contract 조회 → 실패 재현 → 수정 → 관련 테스트 → 동기화. 불필요한 다중 모델 패널 생략.
  • 교차 모듈 API 변경: 구조 이해→의도 충돌 확인→계약 및 영향 분석→인터페이스 계획→코드→폭넓은 회귀→모듈/Feature Map 갱신.
  • 성능 개선: 병목·기준 환경 확인→설계 불변조건 조회→실측 루프→동일한 실험 조건에서 비교→벤치 결과와 맵/결정 기록 갱신.
  • 새 기능: 기능 계약/시나리오/검증 계획을 작성→코드 생성·테스트→Feature Map 신규 ID 및 Architecture 연결 확정.
  • 문서만 갱신: 원본 SSOT인지 생성 HTML인지 식별→원본 수정→재생성→코드와 계약의 증거 점검.

중요 행동 원칙

  • 변경 전에는 기존 맵을 무조건 신뢰하지 말고 최신 코드와 비교한다.
  • 변경 후에는 코드 diff를 기준으로 영향을 받은 기능/계약을 누락 없이 다시 확인한다.
  • 매 턴 '맵은 나중에 업데이트'라고 남기지 않는다. 완료 기준에 동기화를 포함한다.
  • 필요할 때만 인접 코드 그래프를 조회한다. 그래프 전체를 프롬프트로 주입하지 않는다.
  • 사용자의 피드백이 반복될 때는 같은 실수가 재현되지 않도록 시스템 규칙으로 개선한다.

증명 수준(Verification Tiers)

  • T0: 문서·표현만 변경 — 링크/스키마/생성물 일치.
  • T1: 국소 코드 수정 — 단위 테스트 + 타입/컴파일 확인.
  • T2: 교차 모듈 기능 — 관련 통합 테스트 + 경계/호환성 검사.
  • T3: 고위험 상태/동시성/데이터 — 장애 주입·회귀 범위 확대·사용자 수준 실행 증거.

구체적 기준은 프로젝트별 설정과 사용자 선호에 따라 조정한다. '실행했음'과 '실행할 수 없었음'을 명확히 구분한다.

외부 계약 포함: 각 턴의 Understand/Design/Prove/Synchronize는 외부 인터페이스·토픽·스키마·서빙 구조도 포함한다. 외부 계약을 건드리는 변경은 호환성 정책과 외부 소비자 유무를 먼저 확인하고(등급 B/C 트리거), 검증 후 Architecture Map의 외부 계약 뷰를 같은 턴에 갱신한다. 도메인 상태 전이·불변조건은 Phase 3 이후 이 루프에 추가된다.

턴당 예산: T0/T1 작업은 모델 호출·그래프 조회·테스트 실행 각각에 상한을 둔 경량 루프로 돈다. 상한은 프로젝트 설정(project.yaml)에 두고 ChangeReceipt에 실제 사용량을 기록한다. 구체 수치는 Phase 1 실측 후 확정한다.

06. 데이터 모델 및 참조 무결성

맵을 항상 현재 상태로 동기화하기 위한 최소 구조

Map은 제품의 산출물이다. 다음 스키마는 기존 파일을 가져온 예시가 아니라 하네스가 bootstrap 또는 개발 턴에서 생성·유지할 수 있는 목표 출력 형식이다. 초기 생성 시에는 아래 세 축의 근거 상태를 기록하고 확인되지 않은 불변조건을 지어내지 않는다. 예시의 PASSED/CONFIRMED는 해당 근거가 실제로 확보된 후에만 성립한다.

근거 어휘 — 이 문서의 유일한 정의

같은 개념을 장마다 다르게 부르지 않기 위해 축을 셋으로 나누고 여기서 한 번만 정의한다. 다른 장은 이 어휘만 쓴다. 이전 판의 source_kind·needs_confirmation 같은 표현을 만나면 이 세 축으로 읽는다.

축값뜻 / 적용 범위

산출물 단위의 CURRENT / STALE / DRAFT / UNKNOWN(07장)은 파일·그래프 단위의 최신성 신호라 축이 다르며 그대로 둔다.

규칙 세 줄:

  1. purpose, responsibility, rationale 같은 "왜" 필드는 origin이 USER_STATED / ADOPTED / INFERRED 중 하나만 가능하다. EXTRACTED / OBSERVED는 "무엇을 하는가"에만 쓴다.
  2. INFERRED는 사용자 CONFIRMED로만 승격된다. 테스트 PASSED는 verification을 바꾸지 origin을 바꾸지 않는다. purpose는 어떤 증거로도 자동 승격되지 않는다.
  3. HTML 배지는 세 축에서 계산한 파생값이다. 예: "확정" = USER_STATED 또는 CONFIRMED, "추정" = INFERRED ∧ UNCONFIRMED, "검증됨" = PASSED. 저장은 축 단위, 표시는 파생값.

의도의 원본은 한 곳: 기능의 의도는 FEAT-*.intent가 원본이다. CHG-*.intent_delta는 그 의도에 가한 변화의 기록이고, ADR-*은 선택의 근거다. 세 곳이 같은 문장을 중복 저장하지 않고 ID로 참조한다.

식별자·버전·근거 정책

영속 객체는 FEAT-*, MOD-*, IF-*, REQ-*, ADR-*, CHG-*, TEST-*와 같이 이름/파일경로와 무관한 안정적 ID를 갖는다. 파일 이동이나 함수 이름 변경으로 기능 ID가 바뀌지 않아야 한다.

안정 ID는 앵커 묶음으로 유지한다. 경로 하나에 묶으면 파일 이동에서 깨지고, 심볼 ID 하나에 묶으면 시그니처 변경에서 깨진다. 각 객체는 여러 종류의 앵커를 갖고, 재실행·재인덱싱 시 일치하는 앵커 수로 동일성을 판정한다.

anchors:
  - { kind: symbol, ref: "go:service/heartbeat.Consumer.Run" }   # LSP/SCIP 심볼
  - { kind: path,   ref: src/heartbeat/consumer.go }
  - { kind: test,   ref: TEST-019 }
  - { kind: entry,  ref: "kafka-topic:heartbeat-events" }
match_policy:
  same_id_if: anchors_matched >= 2
  candidate_if: anchors_matched == 1      # UNCONFIRMED 병합 후보로 제시
  new_if: anchors_matched == 0
  rename_hint: git-rename-detection      # 경로 앵커 갱신에 활용

모든 변경 레코드에 repo_revision, intent_source, changed_by, evidence, time, status 등을 기록하며, 요청에 근거한 의도와 소스에서 관측한 사실은 근거 유형으로 구별한다.

07. 자동 갱신·최신성 보장 계약

코드 수정 완료와 맵 동기화를 같은 완료 단위로 취급

최초 생성도 동기화 범위다: Map = ∅인 신규 프로젝트를 오류로 보지 않는다. 초기화 파이프라인이 처음부터 정합성 있는 Source/Intent/Map/Graph/HTML 기준 상태를 구축한다. 이후 코드 변경이 누적될 때 자동으로 유지한다.

갱신 트리거

  • 하네스가 실행한 코드/문서 변경의 각 완료 턴
  • Git revision 변화, branch 전환, worktree 변동, 외부 PR 병합, 수동 편집 감지
  • 신규 Feature/인터페이스/테스트 추가·삭제 및 파일 이동
  • 정기적인 전 범위 감사(프로젝트 크기와 비용에 따라 빈도 조절)

기본 동기화 알고리즘

on_turn_start:
  state = scan(repo, optional_ssot, optional_graph, optional_html)
  if not state.has_project_intelligence:
      state = bootstrap_from_source_and_user_intent(repo, request)
  if state.has_external_changes:
      reconcile_or_flag(state)
  context = select_relevant_context(request, state)
  intent = resolve_requested_intent(request, context)

on_verified_change:
  delta = diff(base_revision, working_tree)
  affected = impact(delta, graph, ssot)
  next_ssot = update_from(intent, delta, evidence, affected)
  validate_schema(next_ssot)
  validate_contract_consistency(next_ssot, delta)
  next_graph = rebuild_affected_subgraph(next_ssot, delta)
  next_html = render(next_ssot, next_graph)
  validate_cross_artifact_revisions()
  write_receipt_and_mark_complete()

원자성의 현실적 정의: 파일시스템과 Git·그래프 DB는 하나의 ACID 트랜잭션이 아닐 수 있다. 따라서 staging 디렉터리에서 새 산출물을 생성·검증하고, 원본 SSOT를 동일 Git 변경 단위로 기록하며, 그래프/HTML에는 대상 revision과 sync watermark를 기록한다. 중간 실패 시 완료 상태로 전환하지 않고 재시도 가능하도록 한다.

최신성 신호

  • CURRENT: 코드·SSOT·그래프·HTML이 동일한 대상 revision 또는 유효한 worktree snapshot에 연결됨.
  • STALE: 어느 하나가 더 오래된 revision을 가리킴. 영향도 질의를 허용하더라도 경고하고 재인덱싱.
  • DRAFT: 아직 검증·확정되지 않은 작업 중 상태.
  • UNKNOWN: 분석 범위나 외부 동작을 확인하지 못함.

최종 HTML은 최신성이 확인되지 않았을 때 이를 숨기지 않는다. '항상 최신'은 미관상의 상태 표시가 아니라, 완료 게이트와 세션 시작 감지로 실질적으로 강제하는 운영 요구사항이다. 외부 변경과 실패 가능성을 고려해 최신성을 거짓으로 주장하지 않는다.

실패 모드 테스트

  • 코드 수정 후 HTML 생성에 실패 → 완료 금지, 재생성 가능.
  • Graph 갱신 실패 → 이전 그래프 조회에 STALE 반환.
  • 두 에이전트가 서로 다른 worktree에서 같은 Feature 갱신 → 병합 시 intent conflict 검사.
  • feature renamed / function moved → 안정 ID 유지, 참조 업데이트.
  • 사용자가 맵 없이 코드를 직접 변경 → 세션 시작 시 차이 인식 및 reconciliation.
  • 테스트 실패 → 확정된 Feature 계약에 실패한 동작을 정상 동작처럼 덮어쓰지 않음.

외부 계약 동기화 불변조건: on_verified_change는 외부 인터페이스·토픽·스키마·서빙 구조 변경도 diff+IntentDelta+TestEvidence로 평가한다. 실행 검증하지 못한 계약은 verification: UNVERIFIABLE로 남기고 맵의 현재성만 주장하지 않는다. update_from() 안에서 기계적 층(심볼·간선·HTML 렌더)은 결정적으로 갱신하고, 의미 층(purpose·responsibility·invariant)은 에이전트가 작성하되 반드시 origin: INFERRED로 표시한다. 이 구분이 없으면 자동 동기화가 곧 문서 환각이 된다.

08. Knowledge Graph·Impact·Context Selector

그래프는 검색용이 아니라 안전한 변경을 위한 근거 제공 계층

그래프 구축 원칙

  1. Feature → Module → Interface → CodeSymbol → Test의 경로를 우선 구현한다.
  2. 호출 그래프만으로 런타임 관계를 모두 파악했다고 간주하지 않는다. Kafka topic·SQL·설정·동적 플러그인은 별도 추출 어댑터 또는 명시 매핑이 필요하다.
  3. 각 엣지의 출처와 신뢰도를 확인할 수 있어야 한다.
  4. 변경된 파일/심볼 위주의 증분 인덱싱을 하되 누락/정합성 이상 시 전체 재빌드가 가능해야 한다.
  5. 근거가 약한 관계는 '없음'이 아닌 UNVERIFIED로 처리한다.

Change Impact 분석

입력: intent delta, base/target revision, modified symbols, current feature/arch map.

출력: affected features, interfaces/contracts, dependent modules, suggested test scope, risks, unverified dependencies, evidence.

최우선 그래프 품질 지표는 Impact Recall. 실제로 영향을 받는 중요한 기능을 그래프가 놓치면 낮은 위험 점수 때문에 회귀 검증을 생략하는 문제가 발생한다. 추가로 precision, index freshness, graph build cost를 기록한다.

Context Selector

LLM에 전체 그래프를 넣지 않는다. resolve_feature 또는 analyze_change에서 먼저 Feature/계약 요약을 제공하고, 필요한 관계만 펼치는 bounded subgraph query를 제공한다. LSP/소스 직접 읽기와 병행하고, 그래프 탐색 결과에서 원본 파일 경로와 라인을 즉시 열 수 있게 한다.

Generated HTML Explorer (기본 제공)

  • Architecture View: 모듈 책임·허용 의존성·공개 인터페이스, 실제 의존성과의 비교.
  • Feature View: 사용자 기능·서버 API·배경 작업 등 기능별 목적·검증 절차·관련 모듈.
  • Change View: CHG 번호, 요청 목적, 수정 파일, 영향 기능, 실행 결과, 동기화 상태.
  • Graph View: 선택한 Feature/모듈 주변만 펼치고 출처·인덱싱 상태를 함께 표시.
  • Agent View: MCP 쿼리 결과 및 관련 파일/계약의 식별자를 그대로 복사할 수 있는 페이지.

최초 MVP부터 하네스가 검색 가능한 정적 HTML을 자체 생성한다. 과거 HTML을 가져오는 기능은 향후 선택 어댑터로 추가한다. 거대 그래프의 웹 렌더링은 가치가 입증된 뒤 추가한다.

그래프 범위: Phase 1의 그래프는 Feature → Module → Interface(외부 계약 포함) → CodeSymbol → Test 경로다. 도메인 상태·불변조건 층은 Phase 3 이후 같은 저장소에 타입 계층으로 추가한다. 그래프 조회 자체가 성능 개선을 보장하지 않으므로 부록 B의 선택적 조회 원칙을 지킨다.

08A. 외부 계약 뷰(Phase 1)와 도메인 상태 층(Phase 3 이후)

코드만으로 표현되지 않는 모듈 간 외부 인터페이스와 서빙 구조를 빠뜨리지 않는다. 상태 머신은 나중에.

이 장의 의도: 함수 호출 그래프는 모듈 안쪽은 잘 보여주지만, 모듈이 바깥 세계와 맺은 약속(어떤 토픽을 소비하는지, 어떤 API를 노출하는지, 어떤 테이블을 소유하는지, 어느 서비스에 실리는지)은 코드 곳곳에 흩어져 있거나 설정·매니페스트에만 있다. 이것을 Architecture Map의 1급 항목으로 끌어올리는 것이 Phase 1의 요구다. 도메인 엔티티·상태 전이·불변조건 그래프는 가치가 있지만 추출 난이도와 환각 위험이 다른 문제라 Phase 3 이후로 미룬다.

Phase 1 — 외부 계약 추출 원칙

  • 추출은 결정적 구조에서만 한다. 토픽 이름이 런타임에 조립되거나 플러그인으로 등록되면 origin: INFERRED 또는 UNKNOWN으로 두고 "없음"으로 단정하지 않는다.
  • 계약 한 건은 소유 모듈 한 곳에만 저장한다. 소비 측에서는 ID로 참조한다.
  • 외부 계약 변경은 blast-radius 조회의 1순위 입력이다. 호출 그래프보다 먼저 본다.
  • 실행 검증이 불가능한 계약(실서비스 토픽 등)은 verification: UNVERIFIABLE로 표시하고 이유를 적는다.

Phase 3 이후 — 도메인 상태 층 (예약)

아래는 삭제가 아니라 연기다. 06장에서 ID 접두사(DOM-*, STATE-*, TRN-*, INV-*)만 예약하고, 생성·추출·질의·HTML 뷰는 구현하지 않는다. 추가할 때의 원칙:

  • USER_STATED 우선. 도메인 상태 모델은 사용자가 적는 것이 기본이고, 추출은 명시적 구조(enum, 상태 필드, 상태 전이 switch, 테스트 이름)에 한정한다.
  • 코드에서 추정한 상태 전이·불변조건은 INFERRED ∧ UNCONFIRMED로 시작하며, 어떤 증거로도 purpose로 자동 승격되지 않는다.
  • 설계 상태(허용되는 상태와 전이 규칙)와 운영 상태(지금 어느 메시지가 어느 상태인지)를 섞지 않는다. 후자는 로그·트레이스가 있을 때만 다룬다.
  • 추가 효과는 부록 B의 사다리에서 "Code Graph vs Domain Graph 추가" 한 칸으로 따로 잰다. 그 측정이 가능하려면 Phase 1 출시에 이 층이 없어야 한다.
# 예약 스키마 — 구현 전, 설명용
domain_entity: Heartbeat            # DOM-*
states: [Received, Validated, Deduplicated, Persisted, Rejected]
transitions:
  - { from: Received, to: Validated, trigger: heartbeat.received,
      implemented_by: [CodeSymbol:ValidateHeartbeat], origin: INFERRED, confirmation: UNCONFIRMED }
invariants:
  - { id: INV-001, claim: 동일한 heartbeat 식별자의 중복 저장은 금지,
      origin: USER_STATED, verification: PASSED, evidence: [TEST-019] }

설계 채택 근거: Graphify의 근거 태그·다종 지식 결합(R30), GitNexus의 impact/detect_changes(R33), CodeGraphContext의 SCIP/LSP 수준 인덱싱(R35)을 참조한다. 완성된 도구를 사용하는 것이 본 요구의 필수 조건은 아니다. 턴 루프 의사코드는 07장이 유일한 원본이며 이 장에서 반복하지 않는다.

CLI 명령 (제안)

필수 진입점: myharness init .은 기존 Map 유무를 감지하고, 없으면 bootstrap을 실행한다. myharness bootstrap --mode greenfield|code-only|adopt는 초기화 모드를 선택한다. adopt만 기존 문서를 입력으로 받아 표준 구조로 재구성한다. 명령은 제안 인터페이스이며 실제 구현 전이다.

myharness init .             # 기존 맵이 없어도 초기 프로젝트 지식 자동 생성
myharness status             # revision 및 맵/그래프/HTML 최신성
myharness inspect FEAT-001   # 기능 / 관련 계약 / 소스 / 검증
myharness plan "retry 개선"    # 의도·영향·검증 계획
myharness verify --affected  # 필요한 검증 수행

10. 검수·질문·권한 정책

승인 큐가 아니라 세 등급 + 지연 확인 + 기본값 진행. 사람이 병목이 되는 순간 하네스는 안 쓰게 된다

세 등급 승인 구조 — 이 문서의 원본 정의

등급동작트리거기록
A — 자동 실행, 사후 보고진행하고 ChangeReceipt에만 남긴다읽기·탐색, 가역적 코드/테스트 수정, Map 동기화, 그래프·HTML 재생성, bootstrap의 INFERRED 후보 생성, 로컬 검증, 로컬 commit(설정에 따라)CHG 레코드
B — 묻고, 답 없으면 기본값으로 진행선택지 2~3개 + 추천 기본값 + 각 선택이 바꾸는 범위를 제시한다. 같은 턴 안에 답이 없으면 기본값으로 진행한다요청 해석이 둘 이상이고 결과 기능이 실질적으로 달라질 때 · 변경이 CONFIRMED 계약·불변조건과 충돌할 때 · 외부 인터페이스 호환성 정책을 건드릴 때 · 데이터 보존·비용·의존성 추가 같은 가치 판단일 때 · 외부 변경이 CONFIRMED 계약과 명백히 충돌할 때(Reconcile)ADR-* with origin: INFERRED, confirmation: UNCONFIRMED. 상태는 NEEDS_USER(진행됨, 뒤집을 수 있음)
C — 멈춤명시적 승인 없이는 실행하지 않는다. 가역적 준비 작업까지만 한다공유 브랜치 push/force-push · 배포 · 외부 리소스 삭제 · 비밀정보·권한 변경 · external_consumers: true인 인터페이스의 breaking change · 실서비스 데이터 변경상태 BLOCKED, 승인 요청과 준비된 변경을 함께 보고

지연 확인 (lazy confirmation)

  • bootstrap은 절대 묻지 않는다. 생성된 INFERRED 항목은 UNCONFIRMED로 쌓이고 HTML "확인 대기" 목록에 보인다. 사용자는 틈날 때 myharness confirm으로 일괄 정리할 수 있다.
  • INFERRED 항목은 어떤 턴이 그것을 처음 건드리고, 그 변경 결과가 해당 항목의 purpose·responsibility에 의존할 때만 등급 B로 묻는다. 건드리지 않는 추정은 영원히 안 물어도 된다.
  • 승격 규칙: 사용자 확인 → CONFIRMED. 테스트 통과 → verification: PASSED만. purpose는 어떤 증거로도 자동 승격되지 않는다(06장).

질문 예산과 중복 금지

  • 턴당 질문 상한 3개. 넘치면 가장 결과를 크게 바꾸는 것부터 묻고 나머지는 기본값 진행 + UNCONFIRMED ADR.
  • 한 번 답한 질문은 ADR-*로 저장하고 다시 묻지 않는다. 반복되는 선호는 project.yaml 정책으로 승격한다.
  • 질문에는 "답하지 않아도 진행되는 범위"를 항상 적는다.

자율 실행 기본값

  • 읽기, 탐색, 가역적인 코드/테스트/맵 수정, 로컬 검증, 그래프 갱신, HTML 재생성은 등급 A.
  • 외부 배포·실서비스 데이터 변경·공유 브랜치 파괴적 수정·비밀/권한 관련 비가역 작업은 등급 C.
  • 기능의 의미가 달라질 선택지가 둘 이상이면 등급 B로 설계 옵션 2~3개와 각 비용을 요약해 질문하고 기본값으로 진행한다.

매 턴 질의 정책

질문하기 전 수행: 사용자 요청 확인 → SSOT 존재 시 조회(없으면 자동 초기화) → 코드/테스트 확인 → Git 이력 확인 → ADR-*에 같은 질문의 답이 있는지 확인 → 기본값 제안. 이미 답한 질문은 되풀이하지 않는다.

질문 내용: 영향을 받는 사용자 관점, 선택지별 인터페이스/미래 변경 비용, 선호하는 디폴트, 답변 없이 진행 가능한 범위.

질문 후: 답변을 현재 작업의 IntentDelta에 즉시 반영한다. 중요하고 반복적인 선호는 프로젝트 설정에 반영할 수 있지만, 개인정보나 조직 비밀을 무분별하게 저장하지 않는다.

매 턴 종료 보고 (ChangeReceipt)

목적: 무엇을 바꾸려 했는가
변경: 코드/테스트/SSOT의 핵심 diff
영향: 관련 Feature/Module/Interface
증거: 실행한 검증과 결과, 실행 못한 항목

결정: 등급 A로 자동 적용한 선택 / 등급 B로 기본값 진행한 선택(UNCONFIRMED ADR) / 등급 C 대기 항목
의도 충실도: Requested Delta 항목 수 / 테스트 PASSED로 덮인 수 / 사용자 CONFIRMED 수

첫 번째 E2E 수용 시나리오 — Map이 없는 코드 저장소

  1. 코드와 테스트만 있고 .myharness와 기존 Feature/Architecture 문서가 없는 샘플 저장소를 준비한다.
  2. init --mode code-only을 실행한다. 소스/빌드/테스트를 탐색하고 증거가 연결된 임시 Feature/Module/Interface Map과 HTML을 자동 생성한다.
  3. 불확실한 기능 의도는 INFERRED ∧ UNCONFIRMED로 표시하고 확인 대기 목록에 올린다. bootstrap은 질문하지 않는다.
  4. 사용자가 수정 의도를 전달한다. 하네스는 생성한 최신 Map/실제 코드/외부 계약 뷰를 사용해 계획·구현·검증한다. 그 변경이 처음 건드리는 UNCONFIRMED 항목이 있고 결과가 그 purpose에 의존하면 그때 등급 B로 묻는다.
  5. 수정 후 Feature Map·Architecture Map·Intent/Decision·Graph·HTML이 같은 결과 revision으로 동기화된다.
  6. 별도 세션의 다른 에이전트가 다시 열었을 때 최신 구현·의도·검증 증거를 재사용한다.
  7. 외부 Git 수정 또는 검증 불가능 항목에 대해 최신성을 속이지 않고 재조정/미확인 상태를 표시한다.

두 번째 E2E 수용 시나리오 — 완전한 Greenfield

소스 파일 없이 사용자의 기능 요청만 제공한다. 초기 요구사항과 설계 후보를 만들고, 첫 구현·테스트·맵/HTML 생성·다음 개발 턴까지 수행해야 한다. 기존 자산이 없다는 이유로 사용자에게 문서 제출을 요구하면 실패다.

MVP 합격 기준: code-only 경로(첫 번째 시나리오)가 Phase 1 완료 기준이다. greenfield 경로는 합격 테스트로 함께 통과해야 하지만 설계 우선순위는 code-only가 앞선다(17장 Q1 기본값과 일치). 어느 경로든 사람이 Map 파일을 만들거나 HTML을 작성하지 않고, bootstrap이 질문하지 않고 첫 턴이 완료된다. adopt는 선택 검증 케이스로 다룬다.
